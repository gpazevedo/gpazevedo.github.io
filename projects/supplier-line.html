Supplier Line

A real-time voice agent on Amazon Nova 2 Sonic that answers purchase-order status from a browser softphone or an Amazon Connect call. A caller reads out a code; the agent looks it up and speaks the status back, and a handful of small components keep that answer trustworthy under the failure modes speech models actually have.

What it does

A supplier calls in, reads out a five-digit purchase-order code, and hears its status: shipped or not, the amount, the order date, the delivery date. Two front doors reach the same agent — a browser softphone that talks to a session host directly over a WebSocket, and an Amazon Connect phone call routed through a Lex bot running Nova Sonic speech-to-speech. Both give the same answer in the same words, because both call the same lookup and rendering code.

What makes a speech model trustworthy here

A speech-to-speech model will happily read out an order it misheard, answer from memory instead of looking a code up again, or go quiet after a lookup. Supplier Line prevents each of those with a small, specific component rather than a longer prompt:

  • A check digit in every code. The last digit is computed from the other four, so any single misheard digit fails validation and the agent asks the caller to repeat it, instead of reading out someone else's order.
  • An answer guard. If the model starts speaking order details in a turn with no lookup behind it, the host stops that audio before the caller hears it and tells the model to look the order up first.
  • A session rotator. Nova Sonic connections last at most eight minutes; the app allows fifteen-minute calls. Past six minutes, the host opens a second connection in the background, replays what the caller was actually heard to say, and switches over — a 1 ms gap and no lost caller audio in its live test.
  • A trace on every call. Each turn records what the model planned to say, what it generated, and what the caller actually heard, and six automated checks read every trace: no data spoken without a lookup, no unbounded silence, no audio lost across a rotation.

In its first live test on AWS, a spoken interruption stopped playback in 57 ms, and one request was misheard as PO-13345 — a code that fails its own check digit. The caller was asked to repeat it, one digit at a time, instead of getting an answer for the wrong order.

Built by an AI orchestrator, not by hand

The app's code was not written directly. One Claude orchestrator, working from a written plan and a shared CLAUDE.md brief, ran 23 work streams across parallel agents, each test-first in its own git worktree, model sized to the stream's risk. The orchestrator never wrote feature code itself — its job was verification: re-running what an agent reported, rather than trusting the report.

That check caught real gaps. Three streams reported success on work that did not work, including six silent audio files an agent had marked complete with ticks. A final review on a stronger model, with every automated test green, still found seven defects that would have broken the first real deploy — among them a teardown Lambda that had failed silently on all 81 of its runs. The full account, including the loop, the human checkpoints and what would change next time, is in the write-up below.

Running cost and scope

  • The web-facing stack — CloudFront, an ALB, one ARM64 Fargate task — deploys only through a GitHub workflow approved for a one-to-eight-hour window, and a reaper Lambda deletes it at expiry.
  • The persistent stack — the container registry, the traces bucket, Amazon Connect, the reaper — carries no hourly charges while idle.
  • English only, no phone number of its own, no login beyond an access code, and no reasoning model behind the lookup. Deliberate cuts for a short build, each recorded in the repository's decision records.
