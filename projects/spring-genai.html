Spring GenAI

Can an organisation put its existing Java stack on a managed agent runtime without rewriting it in Python? Amazon Bedrock AgentCore's reference material assumes Python, so the path for a Spring Boot team is undocumented rather than unsupported — and that difference is where projects stall. The agent is deliberately trivial; the deliverable is proof that everything around it works.

The problem

This question surfaces early in most enterprise GenAI conversations, and it is rarely about capability. An organisation with a decade of Spring Boot services, an established build pipeline, and operators who know how to read its telemetry asks whether a managed agent runtime is open to them, or whether adoption means standing up a parallel Python estate alongside everything they already run.

The honest answer is that nothing blocks them. Amazon Bedrock AgentCore contracts on HTTP endpoints, not on a language. But almost every worked example assumes a Python application, and the gap between undocumented and unsupported is invisible from the outside. Teams read the absence of a Java path as a prohibition, and the evaluation stops there. Closing that gap needs a deployed artefact, not an assurance.

What it proves

Spring GenAI is a small, fully deployed reference agent. Keeping it trivial is the point: with no domain logic to explain away, every difficulty encountered belongs to the platform integration, which makes the result reusable both as a starting template and as an honest account of the friction a Java team should expect.

Four things had to work, and each corresponds to a question that decides whether a workload reaches production:

  • The runtime contract. A Spring Boot 3 application serves the two endpoints AgentCore expects — POST /invocations, SSE-streamed on virtual threads, and GET /ping — and delegates inference to Amazon Nova Lite through the Bedrock Converse API via Spring AI's ChatClient.
  • Real user identity. Inbound requests carry a Cognito-issued JWT that AgentCore validates at the boundary. The application parses it only to derive a user ID, which it composes with the AgentCore session header into a userId:sessionId conversation key.
  • Managed conversation state. A custom AgentCoreChatMemoryRepository implements Spring AI's ChatMemoryRepository over the AgentCore Memory Events API, wired behind MessageWindowChatMemory. State lives in the managed store rather than in process, so the runtime is free to scale and replace instances.
  • Operator-grade visibility. Traces and logs reach X-Ray and CloudWatch through the same tooling used for everything else in the account — no bespoke dashboard, no separate pane of glass.

The whole environment is provisioned by Terraform: runtime, Cognito pool, IAM execution role, ARM64 ECR image, memory store, X-Ray configuration and vended log deliveries. An equivalent local stack — OTel Collector into Jaeger, Prometheus, Loki and Grafana under Docker Compose — runs the same instrumentation before anything is deployed.

Where the friction actually was

Not where a Java team would expect. The runtime contract and the Bedrock call were unremarkable. Observability carried nearly all of the non-obvious cost, and every item below is the kind of thing that produces an empty dashboard with no error anywhere to explain it:

  • The ADOT Java agent has to be loaded explicitly through JAVA_TOOL_OPTIONS. Auto-injection covers Python runtimes only.
  • Traces and logs are signed with SigV4 and exported over OTLP directly to X-Ray and CloudWatch Logs, with no sidecar collector in the deployed path.
  • Appearing in the CloudWatch GenAI Observability dashboard additionally required setting cloud.resource_id to the endpoint ARN rather than the runtime ARN — a distinction with no diagnostic if you get it wrong.
  • X-Ray Transaction Search has to be enabled, and root-span sampling forced to 100%, because Micrometer's default 5% decision silently drops every downstream Bedrock span. The parent trace still appears, which is what makes this one hard to spot: the data looks present until you go looking for the model call.

That list is the real deliverable. A Java team can satisfy the runtime contract in an afternoon; what costs them a week is discovering these four settings by elimination.

What it is not

It is not a product, and the agent has no capability worth using. It is a proof of path and a starting template — deliberately scoped so that nothing in it needs to be explained away as domain-specific.

Two limits worth stating plainly. The 100% root-span sampling that makes the traces complete is a development setting, not a production one; a real workload trades fidelity against observability spend, and that trade-off is left open rather than decided here. And the reference covers a single-container agent on AgentCore Runtime — it says nothing about multi-agent orchestration, which is a different problem with a different answer.
