AWS Agentic Generator

A production-ready IaC template and code generator that deploys a Python application to AWS in under thirty minutes. A modular Terraform codebase puts Lambda, App Runner and EKS behind a single API Gateway with path-based routing, so adding the next service is one command rather than another bespoke stack.

The problem

The gap between "we have a Python service" and "it is running in AWS with the controls our security team will sign off on" is measured in weeks, and it gets paid again for every new service. State backends, OIDC trust policies, least-privilege roles, image scanning, structured logging, tracing, a release process — none of it is interesting, all of it is required, and most of it gets rebuilt slightly differently each time because it was copied from the last project rather than generated.

The result is an estate where every service is nearly the same and no two are identical, which is the worst case for anyone who has to audit it. This is a production-ready IaC template and code generator that closes that gap: a modular Terraform codebase that deploys a Python application to AWS in under thirty minutes, and adds the next service with a single command.

Architecture

One API Gateway is the single entry point for an environment, routing by path to whichever compute target fits the workload. That is the decision the rest of the template hangs from — it is what makes adding a service a routing-table entry rather than a new stack with its own domain, its own certificate, and its own front door.

Three compute options sit behind that gateway, chosen per service rather than per project. Lambda on arm64 for request/response and scheduled work, App Runner for longer-lived containers that want auto-scaling without a cluster, and EKS when a workload genuinely needs Kubernetes. A team that starts on Lambda and outgrows it moves one service, not the platform.

Everything is per environment — dev, test and prod are the same code with different variables — over a one-time bootstrap that provisions the Terraform state bucket, the container registry, and the IAM roles the pipeline assumes.

Decisions and trade-offs

OIDC federation instead of stored credentials. GitHub Actions assumes a role through OIDC, so there is no long-lived AWS key in a repository secret to leak, rotate, or forget to rotate. The cost is a trust policy that has to be right the first time and is genuinely fiddly to debug; the benefit is that the most common way cloud credentials escape simply does not apply.

arm64 where it is free, amd64 where it is not. Lambda services build for Graviton2 and take roughly 20% off compute cost for no code change. App Runner services build amd64. The build is multi-architecture rather than picking one globally, because forcing a single architecture on every service to keep the pipeline simple would trade a recurring saving for a one-off convenience.

Quality gates in the pre-commit hook, not just CI. Ruff, Pyright and Pytest run before the commit lands. Failing fast locally is cheaper than failing in CI, and it keeps the main branch releasable, which is what makes semantic-release versioning safe to automate rather than something a human has to gate.

Observability wired in, not bolted on. Structured JSON logging, CloudWatch metrics and alarms, and OpenTelemetry tracing through ADOT into X-Ray are part of the generated service rather than a follow-up ticket. A service that reaches production without tracing rarely gets it afterwards.

What it is not

It is a starting point, not a platform. It generates a correct, observable, least-privilege deployment of a Python service; it does not manage the fleet afterwards, and there is no control plane, no service catalogue, no drift detection beyond what Terraform itself reports.

The thirty-minute figure is time to a first deployed service on a clean AWS account, not time to production readiness for a specific workload — the security review, the capacity work and the domain-specific IAM still belong to whoever adopts it. And the opinions are real opinions: FastAPI, Pydantic v2, structlog, Terraform. A team that disagrees with those is better served forking it than configuring around it.
