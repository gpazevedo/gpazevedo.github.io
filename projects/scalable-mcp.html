scalable-mcp

The auth, rate limiting, session lifecycle and sealed pause/resume convention that ATLAS Counsel's MCP server grew, extracted as a base other servers build on instead of re-deriving from the SDK's primitives. Current with the 2026-07-28 stateless transport revision and the stateful handshake before it — at the same endpoint, so adopting the new era costs older clients nothing.

The problem

The MCP SDK gives you primitives. It does not give you a production posture. Every team that puts an MCP server in front of real traffic re-derives the same set of concerns from those primitives — how to authenticate a caller without leaking which credentials exist, how to rate-limit before doing expensive work rather than after, how to keep the session manager's lifecycle attached to the application's own, and how to pause a tool call across two HTTP requests without handing the client a token it can replay somewhere else.

ATLAS Counsel's MCP server grew all of that. None of it was specific to legal-document retrieval. So it now ships on its own: scalable_mcp for the server side, scalable_mcp_client for the client — a base to build on rather than a pattern to copy.

The extraction was folded back, not forked. Counsel now runs on the package rather than on the code the package was taken from, which matters more than it sounds: a base generalised out of one system and then left behind drifts from it, and every guarantee below becomes a claim about code nobody exercises. These are exercised every time Counsel answers a question.

What building on it gets you

Five things, enforced by construction rather than by a checklist a consumer has to remember:

  • Auth. A pluggable AuthResolver protocol with reference implementations — JwtAuth, ApiKeyAuth, ChainAuth — that are constant-time and enumeration-safe by construction. Every failure mode returns the same string; comparisons use hmac.compare_digest.
  • Rate limiting. One RateLimiter protocol, in-memory or Redis-backed. The ordering that makes it effective — rate limit before auth — is built into create_app itself, so a consumer cannot assemble it the wrong way round.
  • Session lifecycle. The anyio threadpool raised past the SDK's default cap, the MCP session manager entered from the application's own lifespan, idle Streamable HTTP sessions reaped automatically.
  • Pause and resume. A sealed convention for REST handlers that pause an agent thread across separate requests, plus protection for the SDK's own mid-call tools/call round trip.
  • Protocol currency. Built on mcp>=2.0, serving both transport eras at one endpoint.

The server package is organised in three independently testable layers: primitives with no framework dependencies (rate_limit.py, crypto.py), transport-agnostic ASGI middleware, and the FastAPI app factory. Two ways in at the top — AppConfig with create_app for full control, or SimpleServerConfig with create_simple_server for an opinionated one-call setup. Neither pulls in more than it needs: no httpx, no boto3, and Redis is an optional extra rather than a hard dependency.

Two protocol eras, one endpoint

The MCP transport moved to a stateless-per-request revision on 2026-07-28 — the largest change to the protocol since authorization was added. A server built on scalable_mcp serves that revision and the earlier stateful handshake at the same /mcp/ endpoint.

That matters more than it sounds. Adopting the new revision would otherwise force a migration window on every client that hasn't moved yet; serving both means picking it up costs them nothing. The mounting details that make it work — streamable_http_path set to the root, the trailing slash, host validation against the proxy's Host header — are inherited rather than re-derived.

Two pause points, two protections

There are two structurally different round trips that each need to prove a pause was legitimate, and they are easy to conflate because both implement the same SEP-2322 requestState idea.

The first is the SDK's native tools/call elicitation, protected by passing RequestStateSecurity through create_mcp_server. A single-process deployment can omit it and rely on the SDK's ephemeral per-process key. A multi-instance deployment must pass a shared secret, or state minted mid-elicitation on one replica will fail to verify when the client's next request lands on another.

The second is the REST continuation convention behind consumer-defined endpoints, keyed by MCP_HMAC_SECRET. Its tokens carry {thread_id, tenant_id, iat} sealed with AES-256-GCM through the SDK's own AESGCMRequestStateCodec — encrypted and authenticated rather than merely signed, with a fresh nonce per call, so minting the same payload twice produces two different tokens that both verify to identical contents. scalable_mcp no longer carries cryptographic code of its own here; it owns the envelope the convention actually needs — the 120-second TTL, the thread and tenant binding that stops a token being replayed against a different thread or tenant, and clean degradation to checkpoint-only resume when the secret is unset.

Where the boundary sits

Worth being precise about, because it is the question a consumer asks second. scalable_mcp resolves a credential to a tenant and makes that identity available everywhere it is needed — current_tenant, the rate limiter's key, the SDK's session-ownership check. Deciding which tools a given tenant may call is still the application's job: AccessToken.scopes is empty by default, and there is no per-tool authorization model in the base itself.

Identity and transport are what the package gives you. What a tenant is allowed to do with that identity is yours.

One further limit: scalable_mcp is published; scalable_mcp_client follows the same install path once it publishes. The split is deliberate, so a client-only consumer never pulls in FastAPI.
