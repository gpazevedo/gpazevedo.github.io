Building ATLAS Counsel: grounding, escalation, and safety in a citation-first RAG agent

How Buyer Team built a LangGraph agent that cites every claim to a retrievable source span, refuses when the corpus doesn't cover a question, and escalates to a human across a stateless HTTP/MCP boundary when it isn't sure — with the decisions we actually made in production, and why.

Most RAG systems treat citation as a courtesy: ask the model to name its sources in the prompt, and hope it complies. That's tolerable for a search assistant. It's not tolerable for a system that answers "who approves a $60,000 purchase?" and expects a procurement director to act on the answer. A wrong citation there isn't a UX blemish — it's an audit finding.

ATLAS Counsel is Buyer Team's citation-grounded agentic RAG system: it answers procurement-policy and contract questions, grounds every claim in a retrievable source span, refuses when the corpus doesn't cover the question, and pauses for a human when it isn't sure. It runs as a bounded subsystem with its own stack — a LangGraph StateGraph over a hybrid retriever (OpenSearch Serverless NextGen in production, Qdrant for local dev) with an optional FalkorDB graph-retrieval channel for relationships plain similarity can't see — exposed to the rest of the platform as MCP tools (counsel_ask, counsel_resume, counsel_brief). The Step Functions orchestrator and six A2A agents covered in an earlier post call Counsel like any other tool; neither system knows the other's internals.

This post covers three problems that turned out to be harder than "add retrieval and prompt for citations": making grounding structurally unavoidable rather than a prompt request, giving the agent a bounded way to try harder before giving up, and making a human pause survive a protocol that has no concept of pausing. A fourth section covers what we defend against explicitly — indirect prompt injection and memory poisoning — because a doc-grounded agent exposed as a callable tool is exactly the shape that invites both.

Why citation-grounded RAG isn't the same problem as search

A search assistant that occasionally under-cites is annoying. A procurement agent that answers with unverifiable confidence, or guesses at a policy that doesn't exist, or blocks on a human indefinitely, produces a different class of failure — one with the same "no exception is thrown" invisibility as the multi-tenancy contamination described in that earlier post.

⚠
A citation can be wrong and still look right

An LLM asked to cite its sources will cite something, whether or not that something actually supports the claim. Prompt-level citation requests degrade silently — there's no error, no log line, just a plausible-looking reference to a document that says something else.

◎
Refusal needs a real signal, not a score threshold

The obvious refusal heuristic — decline when the top retrieval score is low — assumes retrieval scores carry absolute meaning. Fused rank-based scores don't. Getting refusal right required a different signal entirely (see the callout below).

↻
Self-correction has to be bounded

An agent that re-checks its own answer against the evidence is more reliable than one that doesn't — but only if the re-check loop has a hard ceiling. An unbounded verify-and-retry loop is a production incident with a UUID.

⇄
A pause has to survive the protocol

Escalating to a human is easy to draw on a whiteboard. It's a real integration problem when the agent is called over HTTP and MCP — both request/response — and the human might not respond for hours.

A note on the corpus

The corpus behind Counsel is fully seeded and template-driven — no LLM calls, no network, byte-identical output for the same generator inputs. That determinism is what makes the eval numbers in this post comparable run over run, and it's what keeps the repository public-safe. It ships 8 documents / 24 citable spans (procurement policies, vendor MSAs, a negotiation log) and 8 golden Q/A items tagged grounded, multi_hop, or unanswerable — plus four planted hard cases designed to break a naive implementation.

Trap Where What it tests
Contradiction AcmeCloud 99.9% vs. NorthLink 99.5% uptime cross-document reasoning
Threshold precision POL-001 ($50k) vs. near-duplicate POL-002 ($25k) reranker precision
Unanswerable supplier-gift question, planted with no supporting span refuse-if-ungrounded
Anti-splitting a $120k purchase phrased as smaller pieces policy reasoning, not just lookup

Layer one: grounding as a type contract

Every span in the corpus carries a stable, human-readable id — POL-001#S1 is, and will always be, the $50,000 single-source-purchase threshold clause. That id survives chunking, survives embedding, and shows up in every retrieval result, so a chunk is always traceable back to a specific sentence in a specific document. Citation grounding builds on top of that stable identity at three independent checkpoints, each one catching what the previous one might have missed. 

# Citation is a required field, not a prompt request
# synthesize() must emit a DraftAnswer or it fails validation

class Claim(BaseModel):
    text: str = Field(..., min_length=1)
    span_id: str   # required — no citation, no claim

class DraftAnswer(BaseModel):
    claims: list[Claim]

# verify() then independently checks each claim's span_id against
# the spans that were *actually* retrieved for this question — a
# claim citing an untouched span fails here even if synthesize()
# asserted it was faithful.

We tested checkpoint three with a deliberately hallucinating stub LLM that always cites a span it never retrieved. The graph catches it every time, retries up to the cap, and escalates to the human gate rather than shipping a fabricated citation. Reliability here isn't a matter of prompt wording — it's the type system plus a control-flow guarantee that runs whether or not the model behaves.

Why a retrieval score can't drive refusal

Our first refusal mechanism — decline when the top fused retrieval score is low — scored a flat 0.0 on refusal accuracy the moment the eval harness ran, because Reciprocal Rank Fusion scores are rank-based, not absolute. The top hit scores ≈ 1/(k+1) whether it's a perfect match or merely the least-bad candidate in the set. On the planted unanswerable question, retrieval scored 0.0325 against 0.0328 for questions with a clear answer — no threshold on a fused score can separate those. We rebuilt refusal around lexical grounding overlap — does the question's distinctive content actually appear in the retrieved spans — and refusal accuracy went to 1.0. That check became the validate node.

Layer two: the agent graph

Counsel's control flow is cyclic by necessity: the agent re-checks its own draft against the evidence and retries when a claim isn't supported, and — when the first retrieval pass comes up short — it tries a second, narrower retrieval before giving up. A DAG or a chain models that awkwardly at best. LangGraph's StateGraph gives us first-class conditional edges and cycles, so the graph on the whiteboard and the graph in code are the same graph.

Two properties of this graph carry the reliability story. First, gap-aware retrieval doesn't escalate on the first miss. When validate finds the retrieved spans insufficient, gap_analyze asks the LLM which of the question's content tokens are still uncovered, issues those as follow-up queries, and the results from retrieve merge into — not replace — the existing set, so coverage accumulates across iterations instead of resetting. Second, every loop is capped. MAX_GAP_ITERATIONS bounds the retrieval loop and MAX_ATTEMPTS bounds the verify/synthesize retry; once exhausted, the graph falls through to human_gate rather than spinning. A genuinely unanswerable question still escalates — just after exhausting cheap self-help first, which is the difference between a system that tries and a system that guesses.

Layer three: the interrupt that crosses a stateless boundary

The human gate is where the cleanest part of the design met the least clean part of the transport. LangGraph's interrupt() pauses a run mid-graph — but Counsel is consumed over HTTP and MCP, and both are strictly request/response. A pause can't hold a socket open while a procurement director is at lunch, and it shouldn't have to: the run might resume from a different process, hours later.

Our answer was to make the pause itself a normal result rather than a special case the caller has to detect. When a run hits the gate, the call returns status: "needs_input" plus a thread_id that acts as an opaque resume token. A later, entirely independent /resume call carries the human's decision, and the checkpointer reconstitutes the full run state from that thread and continues exactly where it stopped.

Call Carries Returns
POST /ask tenant_id, question answer + citations, or needs_input + thread_id
POST /resume tenant_id, thread_id, action (steer/decline), guidance? answer + citations, or a safe refusal
WS /ws/ask tenant_id, question streamed {event:"node", node} per step, then a terminal result/needs_input frame

Both transports — the FastAPI endpoints and the MCP tools the platform orchestrator calls — are thin wrappers over one shared CounselService object, and a test (test_mcp_and_http_agree) asserts they return identical results for identical inputs. That single-logic-path property is what lets us promise counsel_ask over MCP behaves exactly like POST /ask over HTTP, without a compatibility matrix to keep in sync.

A bug the pause itself created

Even the human gate surfaced a real production bug worth recounting. When a human steered an initially-ungrounded question toward a specific document, finalize would still refuse — the original automated grounded=False verdict was stale and silently outranked the human's override. The fix wasn't a patch, it was a precedence rule: a human steer always wins over the automated grounding decision. Human-in-the-loop is easy to draw on a diagram; the precedence semantics between "what the model decided" and "what the human just said" are where it gets real.

Multi-tenancy and auth

CounselService is tenant-aware end to end. Each tenant_id gets its own checkpointer — the code's local/dev default is still a SQLite file at ${CHECKPOINT_DIR}/{tenant_id}/checkpoints.db, but production has run exclusively on ATLAS_STATE_STORE=postgres (its own Postgres schema, CREATE SCHEMA tenant_<id>, per tenant) since we replaced the EFS-backed SQLite deployment — a single node-local EFS mount was quietly funneling every task's tenant through the same files, which Postgres closes for good — while the retriever, which is read-only corpus data, is shared. Graphs compile lazily per tenant and are cached rather than recompiled per request. A thread_id is only resumable by the tenant that created it; a cross-tenant resume attempt returns a structured error, never a leak or a crash.

The /mcp endpoint is guarded by a small ASGI middleware supporting either a JWT (tenant_id claim, HS256, optional audience check) or a constant-time-compared API key. Critically, the MCP tools themselves never accept a tenant_id argument — it's derived from the verified auth context, so a caller can't simply assert a different tenant the way it could with a plain request parameter. Auth defaults are fail-safe in the boring direction: with neither secret configured the endpoint runs unauthenticated but logs a startup warning, and if MCP_REQUIRE_AUTH is set without a secret the app refuses to boot rather than silently serving unauthenticated traffic it claims to have locked down.

Update — August 2026

Two details in this section describe v1 of the MCP server and have since changed. Authentication is now mandatory: MCP_REQUIRE_AUTH has been removed entirely, create_app refuses to boot without a credential, and there is no unauthenticated mode — alongside a third accepted credential, OAuth 2.1 with per-tenant Cognito machine-to-machine tokens. Retrieval is no longer shared either; each tenant is served from its own corpus, with no fallback. The tenant-binding rule described above — identity derived from the verified credential, never from a request argument — is unchanged, and everything new is built on it. See ATLAS Counsel MCP v2: an OAuth resource server, built for broad exposure.

What we defend against explicitly

A doc-grounded agent exposed as a callable tool has two correctness risks that are specific to its shape, not generic LLM concerns. Both are defended structurally, not through prompt instructions, and both are proven in an adversarial CI gate rather than asserted in a README.

✗
A retrieved span carries an injected instruction

Retrieved document spans and recalled memories are untrusted text — a supplier contract or a memory fragment can carry "ignore previous instructions" or an identity-reset attempt. A shield scans them at the retrieval boundary and redacts injection-bearing sentences (not whole chunks) before synthesis, preserving legitimate surrounding contract text. With the shield, adversarial detection is 100% and compliance 0%; the undefended baseline leaks the injected directive, so the CI gate can't pass vacuously.

⊘
A wrong answer gets remembered as fact

Multi-tier memory (semantic, episodic, procedural) is strictly additive — but a wrong or steered answer that persists as a remembered "fact" would poison every future session for that tenant. save_memory writes only answers that are grounded, faithful per verify, not refused, not human-escalated, and not from a run where an injection was detected. The wrong answer is still returned to the caller once; it's just never trusted twice.

⇄
Vector spaces from different embedders get mixed

Local (bge-m3) and production (Titan) embeddings live in incompatible vector spaces even where dimensions happen to match. Rather than documenting "don't mix them," each provider declares a space_id, and the store's collection or index name is derived from it — counsel_bge-m3 vs. counsel_titan-v2 are physically separate indexes on every backend, Qdrant or OpenSearch Serverless alike. There is no code path that lets you query one against the other.

◎
A retriever or store dependency goes down mid-request

Every real backend's ensure_collection/index/search calls carry exponential-backoff retries scoped to connection/timeout errors, with a bounded client timeout — 30s for OpenSearch Serverless, generous enough to ride out its ~10s cold start after 10 minutes idle without tripping the fallback. A FallbackRetriever wraps the configured primary and degrades to the pre-indexed in-memory index on failure, with a try_restore probe to detect recovery — so a transient store outage degrades answer quality rather than the whole request.

Evaluation-first, before the agent existed

The eval harness predates the agent, on purpose. We built the deterministic corpus and golden set first, so every later change — a new retrieval stage, a new prompt, a new model — is regression-checked against a fixed target rather than judged by feel. The refusal-mechanism failure above is what that sequencing bought us: the harness caught a broken refusal heuristic on day one, before it ever reached a user.

Dimension How it's measured Backend
Retrieval quality hit@k, context recall, AP-style context precision, MRR — exact, no LLM implemented
Answer faithfulness / relevancy discrete 0–3 rubric with mandatory reasoning per metric, normalized to [0,1] implemented
Refuse-if-ungrounded lexical grounding overlap, not retrieval score (see callout above) implemented
Judge fairness ("judging the judge") content-preserving perturbations (fluent vs. choppy, confident vs. hedging); a fair judge shows deltas near zero meta-eval
Injection defense planted adversarial cases, with-shield vs. without-shield detection/compliance adversarial gate
Regression current aggregate quality locked in; a future change that degrades it fails CI like a broken test, not a report someone has to remember to check implemented

The harness also keeps the project honest about its own features. When we added reranking and query decomposition, the ablation showed the offline lexical reranker lowering context precision (0.857 → 0.707) on this small corpus, where first-stage hybrid retrieval already nearly saturates the golden set. We shipped that number instead of tuning the CI proxy toward the golden answers to manufacture a win. The same harness scored the OpenSearch Serverless migration itself: swapping the sparse channel from a hashed-token approximation to real BM25 left hit@5 and context recall unchanged and moved the ranking metrics by roughly one item at n=8 — a wash, not a regression, so the migration is justified on cost and operational grounds, not retrieval quality, and the post says so rather than rounding a coin-flip up to a win. The +graph ablation row shows the same discipline: FalkorDB's channel moves no metric yet, because the corpus's one multi_hop golden item is already reachable by first-stage hybrid retrieval. The stages ship as correct, tested infrastructure with a measured baseline; the production cross-encoder, an LLM-based decomposer, and a larger corpus with graph-only-reachable answers are what's expected to move these numbers, on a harness that can't be gamed either way.

What we'd do differently

A bigger corpus, earlier. Eight documents and 24 spans are enough to prove the plumbing — fusion, ranking, the verify loop, the refusal mechanism — but they're small enough that first-stage hybrid retrieval nearly saturates the golden set. That's the right floor for CI, but it means rerank, decomposition, and graph retrieval can't yet demonstrate their value on the same harness that made the refusal fix credible. We should have paired the deterministic small corpus with a larger, still-offline one from the start, specifically to give the advanced retrieval stages something to win on.

Register the checkpointer's custom types explicitly. LangGraph's checkpointer serializes our custom Pydantic state types today, but emits forward-compatibility warnings while doing it. Registering them explicitly is a known hardening task we've documented rather than routed around with a private API — the kind of thing that's easy to defer until it isn't.

Update, 2026-08-08: rate limiting moved off per-process state. ATLAS_RATE_LIMIT_PER_MINUTE caps /ask//resume//health/deep and the /mcp prefix, keyed by client IP (the first hop of X-Forwarded-For when ATLAS_TRUST_FORWARDED_FOR is set, otherwise the socket peer). This originally ran on an in-process fixed-window counter, which a multi-instance ECS deployment enforced per task rather than globally — N tasks effectively allowed N× the configured rate. Setting ATLAS_REDIS_URL now routes the same counter through a shared Redis/Valkey store instead, so the cap holds across every task; without it, the in-process limiter remains the fallback. It's still IP-keyed, not tenant-keyed — a noisy tenant behind a shared NAT can still crowd out others on the same key — but the cross-task undercounting is fixed.

Summary

A citation-grounded RAG agent earns trust the same way the multi-tenant platform around it does: by making the guarantee an architectural property instead of a convention someone has to remember. Grounding is enforced at three independent checkpoints — stable span identity, a required field on every claim, and an independent re-check — so a hallucinated citation has to survive all three, and it never does. Escalation is bounded on both axes (gap-analysis retrieval, verify/synthesize retries) so the agent tries harder before it gives up, and the human pause is a first-class result that survives a stateless transport rather than a socket held open and hoping. And the two risks specific to a doc-grounded tool — injection and memory poisoning — are defended at the retrieval and write boundaries, proven in an adversarial CI gate that can't pass vacuously.

None of that required exotic tooling. It required measuring before building, making citation a type rather than a request, and treating "I don't know" and "ask a human" as first-class outcomes the graph is designed around — not failure modes bolted on after the fact.
