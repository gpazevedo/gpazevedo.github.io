scalable-mcp: a reusable base for MCP servers and clients, grown out of ATLAS Counsel

scalable_mcp and scalable_mcp_client are the server and client base that grew out of building and operating ATLAS Counsel's MCP server — auth, rate limiting, session lifecycle, and a sealed pause/resume convention, generalized so the next MCP server doesn't have to rederive them from the SDK's primitives. This round adds two capabilities: protection for the MCP SDK's own tools/call elicitation round trip, and continuation tokens sealed with the same AES-256-GCM codec the SDK now ships.

When we wrote up ATLAS Counsel MCP v2, the server had grown a full production posture: mandatory auth across three credential types, per-tenant rate limiting, a sealed continuation-token convention for pausing an agent thread across separate HTTP requests, and — because the protocol itself doesn't stand still — support for two eras of the MCP transport at one endpoint. None of that is specific to legal-document retrieval. It's what any MCP server taking real traffic needs, so it now ships on its own as scalable_mcp for the server side and scalable_mcp_client for the client side: a base other MCP servers and clients can build on directly, instead of re-deriving the same posture from the SDK's primitives each time.

This post is about what that base gives you today, and two things it does now that it didn't when we first wrote it up: it protects the SDK's own mid-call round trip, not just the REST convention layered on top of it, and its continuation tokens are sealed with the same cryptography the SDK maintains rather than a signature scalable_mcp computed on its own.

What building on it gets you

Five things, all enforced by construction rather than by a checklist a consumer has to remember:

auth
A pluggable AuthResolver protocol, plus reference implementations — JwtAuth, ApiKeyAuth, ChainAuth — that are constant-time and enumeration-safe by construction: every failure mode returns the same string, and comparisons use hmac.compare_digest.
limit
Rate limiting behind one RateLimiter protocol, with an in-memory or a Redis-backed implementation, and the ordering that makes it effective — rate-limit runs before auth — built into create_app itself, not documented as something a consumer has to get right.
session
Session lifecycle handled for you: the anyio threadpool raised past the SDK's default cap, the MCP session manager entered from the app's own lifespan, idle Streamable HTTP sessions reaped automatically.
resume
A sealed pause/resume convention for REST handlers that need to pause a LangGraph-style agent thread across separate HTTP requests, plus — new — protection for the SDK's own tools/call round trip.
protocol
Built on mcp>=2.0 and serves both the classic stateful handshake and the current stateless revision at the same endpoint, so a server built on scalable_mcp doesn't drop older clients to gain the new ones.

Two packages, matched to two audiences

scalable_mcp is the server side; scalable_mcp_client is the client side. Install only the one you need. Internally, the server package is organized in three layers, each independently testable:

Layer 1 Primitives rate_limit.py, crypto.py
no framework deps pure logic
Layer 2 Middleware middleware.py
ASGI FastAPI-aware transport-agnostic
Layer 3 App factory app.py, server.py, simple.py
FastAPI MCP SDK integration

Two ways in at the top of that stack: AppConfig + create_app for full control over auth, rate limiting, CORS, timeouts, and hooks — or SimpleServerConfig + create_simple_server for an opinionated one-call setup that's usually enough. Neither pulls in more than it needs: no httpx, no boto3, and Redis is an optional extra rather than a hard dependency.

Current with the protocol

The MCP transport moved to a stateless-per-request revision on 2026-07-28, the largest change to the protocol since authorization was added. A server built on scalable_mcp serves that revision and the earlier stateful handshake at the same /mcp/ endpoint, so picking up the new revision costs a client nothing and forces no migration window on the ones that haven't moved yet. The mounting details that make that work — streamable_http_path="/", the trailing slash, host validation against the proxy's Host header — are exactly the ones we covered in depth when ATLAS Counsel MCP v2 shipped them; a server built on scalable_mcp inherits all three without re-deriving them.

New: protecting the SDK's own tools/call round trip

The MCP SDK has its own multi-round-trip mechanism for tool parameters that need client input mid-call — elicitation, sampling, roots — built on a Resolve/InputRequiredResult pair inside the JSON-RPC tools/call request itself. create_mcp_server now threads a RequestStateSecurity straight through to it:

def create_mcp_server(
    name: str, *, request_state_security: RequestStateSecurity | None = None
) -> MCPServer:
    """Create an MCPServer with the given name. The caller registers tools on
    the returned server via @mcp.tool(...) decorators.

    Pass request_state_security to protect the native tools/call elicitation
    round trip (Resolve/InputRequiredResult — see mcp.server.mcpserver.resolve).
    Multi-instance deployments need RequestStateSecurity(keys=[shared_secret]);
    omitting it leaves the SDK's per-process ephemeral default, which rejects
    state minted before a restart or by another worker. This is independent of
    scalable_mcp's own crypto.mint_request_state, which protects the separate
    /ask-/resume-style REST continuation convention, not tools/call.
    """
    return MCPServer(name, request_state_security=request_state_security)

Single-process deployments — stdio, one HTTP worker — can leave the parameter out entirely; the SDK's ephemeral default covers them. A multi-instance HTTP deployment passes RequestStateSecurity(keys=[shared_secret]), so state minted mid-elicitation on one replica still verifies when the client's next request lands on another.

New: continuation tokens sealed with the SDK's own codec

scalable_mcp's own pause/resume convention — the one behind consumer-defined REST endpoints like /ask and /resume — now delegates sealing to the same primitive:

def mint_request_state(*, secret: str, thread_id: str, tenant_id: str, iat: int | None = None) -> str:
    payload = RequestStatePayload(
        thread_id=thread_id, tenant_id=tenant_id,
        iat=iat if iat is not None else int(time.time()),
    )
    codec = AESGCMRequestStateCodec(keys=[secret])
    return codec.seal(payload.model_dump_json().encode("utf-8"))

The payload — {thread_id, tenant_id, iat} — is sealed with AES-256-GCM via the MCP SDK's AESGCMRequestStateCodec: encrypted and authenticated, not merely signed, and a fresh nonce on every call so minting the same payload twice produces two different tokens that both verify to identical contents. scalable_mcp doesn't carry cryptographic code of its own for this anymore — it owns the envelope the convention actually needs: the 120-second TTL, the thread_id/tenant_id binding that stops a token minted for one thread or tenant from being replayed against another, and the degrade-to-checkpoint-only behavior when MCP_HMAC_SECRET is unset. Both of scalable_mcp's pause/resume mechanisms — the SDK's native one above, and this REST convention — now rest on the same AES-256-GCM codec, configured and keyed independently for the two different round trips they protect.

Two pause points, two protections

Both mechanisms implement the same SEP-2322 MRTR idea — a sealed token that proves a pause was legitimate — for two structurally different round trips, which is worth laying out side by side once rather than re-deriving from the docstrings each time:

Composed, not duplicated

The client side follows the same layering. MCPConnection is the primitive — it owns connect-retry and a background health-check loop over a Streamable HTTP session. SimpleMCPClient, the convenience client, is built by composing it rather than reimplementing connection lifecycle on its own:

class SimpleMCPClient:
    def __init__(self, url: str):
        self._connection = MCPConnection(ConnectionConfig(url=url))
        self._tool_proxy: ToolProxy | None = None
        self.cache = ResponseCache()

    async def _connect(self) -> None:
        await self._connection.connect()
        self._tool_proxy = ToolProxy(self._connection.session)

    async def _disconnect(self) -> None:
        await self._connection.close()
        self._tool_proxy = None

Any improvement to MCPConnection's retry policy or health-check cadence reaches SimpleMCPClient automatically, since it's the same object rather than a parallel copy. What SimpleMCPClient adds on top is genuinely its own: ToolProxy for calling tools as attributes, and ResponseCache for short-lived result caching — neither of which a caller using MCPConnection directly would necessarily want by default.

Getting started

A server:

from scalable_mcp import create_mcp_server, SimpleServerConfig, create_simple_server

mcp = create_mcp_server("my-app")

@mcp.tool()
def greet(name: str) -> str:
    return f"Hello, {name}"

app = create_simple_server(config=SimpleServerConfig(
    server_name="my-app",
    mcp=mcp,
    auth="api-key",
    api_keys={"my-secret-key"},
))

# Run with: uvicorn app:app

A client:

import asyncio
from scalable_mcp_client import SimpleMCPClient

async def main():
    async with SimpleMCPClient.connect("http://localhost:8000/mcp") as c:
        tools = await c.list_tools()
        print([t["name"] for t in tools])

asyncio.run(main())

And a CLI for exercising either side without writing a client at all:

scalable-mcp-client list-tools http://localhost:8000/mcp
scalable-mcp-client call http://localhost:8000/mcp greet --arg name World --pretty
scalable-mcp-client probe http://localhost:8000/mcp
Where the boundary sits

scalable_mcp resolves a credential to a tenant and makes that identity available everywhere — current_tenant, the rate limiter's key, the MCP SDK's session-ownership check. Deciding which tools a given tenant may call is still the consumer's job: AccessToken.scopes is empty by default, and there's no per-tool authorization model in the base itself. Identity and transport are what this package gives you; what a tenant is allowed to do with that identity is the application's.

What you get
A server and client base that already knows how to authenticate, rate-limit, manage session lifecycle, and pause/resume an agent thread safely — current with both eras of the MCP transport, and now covering the SDK's own mid-call round trip in addition to the REST convention layered on top of it. Two focused packages, 231 tests, and one cryptographic primitive — the SDK's own AES-256-GCM codec — backing both of its pause/resume mechanisms.

What generalises

Bake ordering guarantees into the framework, not the docs. A consumer building on scalable_mcp cannot get rate-limit-before-auth wrong — it isn't a checklist item, it's the only order create_app assembles.

When the protocol SDK ships a primitive you need, build on it. Both of scalable_mcp's pause/resume mechanisms now rest on the same AESGCMRequestStateCodec the SDK maintains, configured independently for the two round trips they protect.

Compose the convenience layer from the primitive, don't duplicate it. A one-call factory or a convenience client should be a thin wrapper over the flexible path, not a parallel implementation — that's what keeps create_simple_server and SimpleMCPClient current automatically as the primitives underneath them grow.

When two protections share a spec-derived name, say which is which where the reader will actually see it. tools/call elicitation and the REST continuation convention both implement SEP-2322 MRTR's requestState idea; each one's docstring names the other.
