Shipping agents safely
deployment, rollout, and rollback

Deploying a fleet of LLM-driven agents is not the same problem as deploying a stateless web service. When output quality can degrade in ways a health check will never catch, the release pipeline has to treat negotiation quality as a first-class signal — sitting right alongside error rate and latency.

A conventional canary asks one question: is the new version healthy? For an agent system that question is necessary but nowhere near sufficient. A bad agent deploy can return HTTP 200, respond in under a second, and still negotiate badly — concede too early, leak a competitor's price, misread a Kraljic quadrant. None of that shows up on a liveness probe. So the entire release model is built around a second question the pipeline asks continuously: is the new version good?

This is how Buyer Team, an autonomous multi-agent procurement negotiation system, handles deployment, gradual rollout, and rollback, and where AWS Bedrock AgentCore fits into each stage.

What is actually running, as of August 2026

Everything below is built and wired. Dev is the only environment that has ever been deployed. The production pipeline exists end to end in prod-deploy.yml but has never run: there is no image_tags.prod.tfvars.json, and the repository carries zero semver release tags. Where a mechanism has only ever been exercised in dev — or not at all — this post says so at the point it matters rather than in a disclaimer you have already skipped.

The release model in one sentence

Buyer Team is GitOps end-to-end. Git is the single source of truth, container images are built once and promoted — never rebuilt — and production releases are tagged with semver. The principle worth internalising is rollback-as-forward-deploy: there is no "undo" button, only a forward deploy back to a previous known-good SHA.

Why forward, not back

An "undo" implies mutating something in place. This system never mutates a release — it deploys a new one. Because images are immutable and the previous good one is still sitting in ECR, rolling back is just deploying an artifact that already exists and already passed every gate. Same mechanism, opposite direction.

The promotion pipeline

The design document describes five environments — local, CI, dev, staging, production. The pipeline that actually exists has two deploy targets and one gate. Dev deploys automatically on merge to main. Production is a manual dispatch that copies dev's images straight into production ECR. In between sits staging-eval-suite.yml, which is not a deploy at all: it is a weekly evaluation job that runs against dev and whose green run is a required precondition for promoting a given commit.

This matters more than a naming quibble. "Staging" in this system is a quality gate, not a tier — there is no staging AWS account, no staging image promotion, and no staging E2E run. The workflow's own header says it plainly: there is still no automated staging→production promotion pipeline.

Four details make this more than a generic CI/CD diagram.

Immutable promotion, with one asterisk. Images are built once during the dev deploy and the same artifact is copied into production ECR. Nothing is rebuilt, so what the gate evaluated is bit-for-bit what would serve production traffic. Production repositories are forced to IMMUTABLE regardless of the per-repo default, and a lifecycle policy retains the last ten tagged images so a rollback target stays pullable. The asterisk: dev repositories are MUTABLE, so within dev the retention window is a floor rather than a guarantee — a re-pushed identical tag overwrites the image it replaces. The promotion step itself is retry-safe by digest comparison: a matching digest is skipped, a mismatched one hard-fails rather than overwriting.

Evals are a gate, not a report. PR checks run three separate offline evaluation jobs before merge — the structural and ground-truth suite, a directional LLM-judge smoke check with a per-strategy consistency run, and a live Kraljic accuracy gate with a 0.80 floor. Promotion to production is then blocked unless the weekly judge suite has a green run against the exact SHA being promoted, updated within eight days. Quality is checked before exposure, not discovered after.

Manual gates where they matter. Dev auto-deploys on merge so engineers get fast feedback. Production requires a manual dispatch naming both the commit SHA and the semver release. Plan and apply are split into two jobs so a reviewer can open the uploaded plan artifact before apply starts — though nothing currently enforces that they do, because GitHub's required-reviewers rule is a paid-plan feature this private repo does not have. That is a recorded, accepted gap rather than an oversight.

The gate was deadlocked for a month, and the fix was a decision, not code. Five consecutive weekly runs, from 2026-07-13 through 2026-08-10, failed with the identical error: negotiation_quality: calibration SUSPENDED (mad=0.607 > 0.20). The calibration check compares live judge scores against "human" labels in a transcript panel that is still a synthetic placeholder seeded in July. The MAD is therefore deterministic, and the check could not pass until real dual-human-scored transcripts replaced the fixture. The gate was not red because a regression was caught; it was red because the reference data it grades against did not exist yet.

On 2026-08-19 that was settled explicitly: calibration is advisory while the panel is synthetic. The fixture declares synthetic_scores: true, and the suite reads that flag — a SUSPENDED calibration then prints a warning instead of failing the run, while judge consistency keeps blocking as before. The flag is checked as present-and-true, so a panel replaced with real labels re-enables blocking by default rather than needing someone to remember to switch it back on. The measurement still runs and is still reported every week; what changed is that a number measuring the fixture no longer gets a veto over promotion.

The honest limit

A gate that fails for a reason unrelated to the change under test is worse than no gate, because it trains people to route around it. The fix path was never judge tuning — it was a ground-truth labelling pipeline (built, never run) or an explicit gate-policy decision, and the actual engineering work is naming which of the two you are choosing. The second one is now named and in code. The first is still the way back to a blocking calibration gate, and until it runs this post should not claim the judges are calibrated — only that the suite is honest about not knowing.

PR   → pre-commit + unit/coverage/pyright + offline evals
       + judge smoke + live Kraljic accuracy gate → merge to main

Dev  (auto): detect changed components → build + push only those
       → terraform plan/apply → commit the image-tag map back to main

Gate (weekly, or dispatched against a SHA): Bedrock judges vs the
       transcript panel → consistency + human calibration

Prod (manual, SRE): verify gate green for this exact SHA
       → copy dev images to prod ECR → plan → apply
       → observe → per-quadrant smoke → confirm or roll forward

Gradual rollout: the production canary

A constraint worth being upfront about: AgentCore Runtimes have no fractional traffic routing — there is no microVM-level traffic split, so a true "send 10% of traffic to the new version" canary can't be built on top of it. Every image is promoted to production ECR and deployed to every Runtime at once. What this system calls the "canary" is therefore a monitoring-only observation window, not a traffic slice: it's a structured confirmation gate before rollout is declared complete, not a way to shrink the blast radius of a bad deploy.

  1. Deploy to all Runtimes at once. There is no partial fleet — the new image is live everywhere the moment the apply completes.
  2. Observe for fifteen minutes (the workflow's default; it is a dispatch input, so an operator can widen it), polling twenty CloudWatch alarms once a minute and failing the moment any one of them is in ALARM.
  3. Smoke test one negotiation per quadrant. The strategies fall into four Kraljic quadrants, so one representative negotiation is driven through each to confirm the real path works end-to-end — not just that the process boots.
  4. All pass and no alarms fire → rollout is confirmed, the image-tag map is committed and the semver tag is pushed. Any failure rolls forward instead (next section).

The twenty alarms are six evaluation-quality alarms plus an error alarm and a latency alarm for each of the seven Runtimes (six agents and the Skill Runtime). Three details are worth stating precisely rather than rounding off:

  • It is not a p99 gate. The design document says "p99 latency" and so did earlier versions of this post. The alarm is Maximum over a five-minute period with a 60-second threshold, and that threshold is a first pass that has never been tuned against real traffic. No p99 statistic is wired anywhere. The observation window inherits that imprecision.
  • It used to watch four of the six evaluation alarms. Rationale Defensibility and Kraljic Accuracy were added to Terraform later and never added to the workflow's hand-maintained list, so a regression on either would have passed the window unnoticed. Fixed on 2026-08-19 by deleting the list: eval alarms are now discovered by name prefix, so the watch set equals what Terraform actually provisions. Discovery fails closed — fewer than six matches aborts the promotion rather than looping vacuously over an empty set, which matters because these exact alarms were once deleted wholesale in a cost trim. That is a fix to the class of bug, not the instance.
  • One of the six is not live protection in production. eval-kraljic-accuracy is fed by a daily accuracy harness pinned to the dev environment — nothing emits that metric in prod. There it sits at INSUFFICIENT_DATA, so the window watches it for a carried-over ALARM state rather than for anything happening during the window itself. Pointing the harness at prod is what would make it protective.

The inclusion of eval quality in the observation window is still the important idea. By scoring negotiation quality during the window, a regression that a conventional health check would wave straight through gets caught fast — but it's caught while live on 100% of production traffic, not a contained slice. Detection-and-rollback speed is the safety lever here, not reduced exposure.

Scope boundary — the smoke test still needs data prod does not have

The per-quadrant smoke job runs a real all-four-quadrant negotiation test. It used to be built around a fixed dev fixture tenant with a pre-seeded non-critical item, which made it structurally unable to pass anywhere else; all four quadrants now seed and tear down their own items, so the suite is environment-portable. The sharper problem was the failure mode: on an unseeded environment the job failed like a quadrant regression, and in this pipeline a smoke failure fires the roll-forward path — so an environment that was merely empty would have presented as a bad release and triggered a rollback. A preflight fixture now checks the tenant row and the four categories' suppliers up front and fails with SMOKE FIXTURE MISSING … NOT a quadrant regression plus the exact seeding command.

What is left is genuine provisioning, and it stays manual on purpose: one-time tenant config rows plus category and supplier master data for the four quadrants. Seeding is not a pipeline step because the seed script writes the whole governance and model config groups — running it on every promotion would overwrite prod governance and clobber model/default and model/previous, the exact rows the model-rollback action below restores from. A provisioning step that silently disarms a rollback mechanism does not belong in the deploy path.

Getting real exposure control for a behavioral change — a model swap, a prompt rewrite, a threshold tweak — against real tenant traffic takes a different mechanism, covered next.

Real exposure control: tenant-scoped variant routing

The observation window catches operational regressions fast, but it can't answer a different question: does a behavioral change — a model swap, a rewritten prompt, a new threshold — actually negotiate better for real tenants, without exposing every tenant to it at once? That needs exposure control, and since AgentCore won't give it at the traffic layer, this is built one layer up: in the same config-driven registry ({env}-system-config) that already resolves which runtime serves each agent invocation. Each agent has a real sibling canary Runtime in Terraform, deployable independently, that these mechanisms route to.

The resolver that maps a logical agent name to a runtime ARN layers three additive mechanisms on top of that base lookup:

  1. Tenant pin. An operator pins one chosen tenant — an internal or design-partner account — to a named variant. Naming an undefined variant raises rather than silently falling back to the base runtime.
  2. Shadow testing. The live path fires an async, fire-and-forget replay of the same request against the variant runtime and records agreement — with zero effect on the response the tenant actually receives. It's a safety check with no tenant-visible risk.
  3. Deterministic population split. A tenant's bucket is a SHA-256 hash of the logical agent name and the tenant ID, so the same tenant lands in the same variant across its own repeat requests, while its bucket for one agent tells you nothing about its bucket for another. That is a real, statistically legible percentage rollout, which is exactly what the deploy-time observation window can't do.

Precedence runs env override > tenant pin > population split > base runtime — a deliberate single-tenant override always wins over an experiment running underneath it. The whole path was verified end-to-end on dev in July, including a 30% split across 2,000 synthetic tenants and the fail-fast behaviour on an unseeded variant.

The honest limit

This is an operator-driven mechanism. There is no automatic analysis of the shadow agreement rate and no automatic promotion or rollback of a variant — a human reads the comparison and decides. It buys real exposure control on a platform that offers none; it does not buy an automated experiment pipeline. It is also a second thing called "canary", which is why this post keeps the two apart: the deploy-time observation window confirms a build is safe to run at all; variant routing confirms a specific behavioral change is actually good, against real tenant traffic, before every tenant sees it.

Rollback: two mechanisms, one word

If either confirmation gate fails — the observation window or the quadrant smoke — the pipeline rolls forward to the previous known-good SHA, with a target of completing within five minutes of failure detection. Mechanically it is unglamorous, which is the point: the plan job snapshotted the previous image-tag map before overwriting it, so recovery is restoring that snapshot and running terraform apply against images already sitting in ECR. No separate rollback artifact, no new variables on the recovery path.

The mechanism has one cold-start hole, and it is why "cut one release" is still on this post's to-do list. The snapshot only exists if there was a previous deploy. On production's first promotion there is nothing to restore, and the workflow says so plainly instead of failing obscurely — it errors with "there is no previous prod deploy to roll forward to" and stops for manual intervention. The first release is the one that runs without a net; every release after it inherits one.

One deliberate asymmetry: the roll-forward step runs on the unprotected GitHub environment rather than the branch-restricted production one. Gating automatic recovery behind a second human approval would blow the five-minute bound — so the deploy is protected and the recovery is not.

There is a second, quieter mechanism that also gets called rollback, and it is not the same thing. Each evaluator is bound to a threshold, an alarm, and an automated action; when the negotiation-quality composite drops below 0.60, an alarm fires a remediation Lambda that restores the previous model-tier mapping in DynamoDB and bumps a model_epoch counter. Agents re-check that counter on a 30-second TTL, so already-warm execution environments pick up the change in about half a minute instead of never. No image moves. No deploy happens. It can fire on a completely stable codebase — model drift, a bad config change, an upstream data issue — which is exactly the class of problem it exists for.

A naming wrinkle, now settled

The evaluation threshold table labels this action Model rollback; the operational runbook calls it Configuration rollback. Earlier versions of this post said the two names described one forward-deploy mechanism. They don't. As built, the runbook is right: it is a configuration rollback of the model-tier map, with no relationship to the deploy pipeline's roll-forward beyond sharing a word. Rolling the image back is still a manual dispatch.

That closed loop now has all five of its actions built, deployed to dev, and verified end-to-end against synthetic alarm events — a state it reached only in mid-August 2026, after more than a month during which the alarms existed but drove nothing, and a stretch where they were deleted outright as an unsubscribed cost line:

< 0.60
Negotiation Quality
model tier rollback

Restores the previous tier map and bumps model_epoch; warm agents re-resolve within ~30s.

< 0.80
Communication Tone
disable auto-send

Flips auto_send_communications off. Node 7 sends before the async judge scores, so this protects the next message, never the one that tripped the alarm.

< 0.70
Rationale Defensibility
block auto-award

The approval gate returns PENDING_APPROVAL with an explicit block reason instead of auto-awarding.

< 0.90
Kraljic Accuracy

Bumps a cache_epoch threaded into the cache-key hash — an epoch, not a scan-and-delete, so there's no repopulation race.

< 1.00
Format / Governance
halt new negotiations

Node 1 returns CANCELLED instead of creating a negotiation. In-flight work is untouched; the source request stays validated and resumes when cleared.

The part that looked configured and wasn't

Those five actions fire automatically, which is what let the next problem hide for so long: until 2026-08-19, every alarm in this system notified an SNS topic with no subscriber. The automated remediations ran; no human was ever told that one had. The cause is worth naming because it generalises — the alert email lived in a .tfvars file that .gitignore excluded, so it reached a local apply but never reached CI. In CI the address resolved empty, the subscription's count evaluated to zero, and Terraform destroyed the subscription someone had added by hand. Every manual fix worked, and every subsequent pipeline run silently undid it.

The lesson is not "remember to subscribe to the topic." It is that a value which is invisible to the automated path will be reverted by the automated path, on a schedule, forever — and that the alerting channel is exactly the component whose failure suppresses its own alarm. It has to be verified by observation, not by reading the config that claims it.

Two design choices run through all five. None of them auto-re-enables — a human clears each flag through a dedicated script, so the system can protect itself but cannot quietly decide it has recovered. And all five reach already-running agents through a 30-second TTL re-read rather than a restart, because agents resolve config once at container boot and a flag nothing re-reads is a flag that takes effect never.

Where AgentCore participates

AWS Bedrock AgentCore is the managed runtime the agents and the Skill actually run on, and it shapes each stage of the release lifecycle. Six agents and the Integration Skill run on it — and four distinct consequences follow from that single fact.

It is the deployment target — and every update is a full replace

Each of the six agents is deployed as an independent AgentCore Runtime speaking the A2A protocol on port 9000, and the Integration Skill is deployed as a separate AgentCore Runtime speaking MCP on port 8000. (The design calls for one Skill Runtime per tenant; as built there is exactly one, serving the test tenant.) The pipeline's deploy step is, mechanically, a set of AgentCore Runtime deployments.

The sharp edge here is one this post previously got backwards. The original design asserted that a Runtime's protocol type is immutable after creation and that a Terraform plan-time check was a sufficient guard. Both premises turned out to be false in production use. update_agent_runtime is a full-replace control-plane call: it flips serverProtocol in place, same runtime id, no destroy-and-recreate. Worse, because the call replaces the entire definition, any field omitted from it silently resets to a default — omit protocolConfiguration and the runtime reverts to A2A; omit environmentVariables and the environment is simply gone.

The failure mode this produced was genuinely misleading. A hand-written boto3 call copied the six agents' A2A protocol onto the one MCP Skill Runtime. The Skill serves MCP on :8000; once reset to A2A, the platform routed gateway invokes to the :9000 contract where nothing listens, so every invoke returned 424 — but only after the ~130-second microVM provision, which made it present as a cold-start problem and cost an entire investigation cycle to a wrong diagnosis.

The real guard is not a plan-time check — the Skill Runtime is updated out-of-band via boto3, precisely the path Terraform never sees. It is a guarded helper that re-asserts the full definition every time: the protocol is hardcoded, not a parameter; the IAM role and VPC config are re-read live; the environment is rebuilt to the Terraform canonical rather than carried forward. Hand-writing a bare update call is prohibited. The invariant generalises — full-replace semantics apply to every AgentCore Runtime and Gateway, not just the Skill.

It removes the "instances" you would normally roll out — and the traffic split with them

In a traditional canary you shift traffic across a pool of instances you sized yourself. AgentCore has no instances to size, and no fractional traffic routing at the microVM level. It provisions a dedicated microVM per session and scales horizontally as a fully managed service; there is no per-instance concurrency to tune and no fleet to drain, but also no traffic-layer dial to turn. That's why the production "canary" is a monitoring window rather than an exposure slice, and why real exposure control had to be built one layer up.

Capacity is governed instead by an account-level active-session quota — 1,000 in us-east-1 and us-west-2, 500 elsewhere. At the planned ceiling of ~100 concurrent negotiations consuming roughly ten sessions each, the default is exactly consumed at full load with zero headroom, so the production runbook calls for requesting an increase to ≥1,500. That is a documented recommendation, not a quota that has been raised. Per-tenant fairness is enforced upstream by the Step Functions orchestrator's admission control, not by the runtime scheduler, which does not partition slots by tenant.

Traceability comes from the image tag, not an injected variable

Earlier versions of this post claimed every Runtime is launched with DEPLOY_VERSION, ENVIRONMENT and GIT_SHA injected. Only ENVIRONMENT is real (the Skill Runtime also gets its state-machine ARN); there is no GIT_SHA or DEPLOY_VERSION environment variable anywhere in the infrastructure.

The traceability guarantee still holds — it is just delivered differently, and arguably better. Every image tag is the commit SHA, so a Runtime's container URI is its provenance, and the committed tag map records which SHA every component is pinned to. Separately, GitSHA is set in Terraform's default_tags, so every managed AWS resource carries the commit it was applied from. Rollback stays auditable because the artifact identity and the commit identity are the same string, not because a process announces its own version.

Its evaluations are sampled monitoring — not the gate, and not the trigger

This is the correction that matters most, because the previous version of this post inverted it. AgentCore Evaluations is real and running: six online-evaluation configs, one per agent, are ACTIVE, scoring Builtin.Helpfulness and Builtin.ToolSelectionAccuracy on a sampled slice of live sessions, with two alert-only alarms watching the aggregate. Builtin.Correctness can't run on that path at all — the online-sampling API has no per-invocation reference-inputs field.

But the scores that gate a promotion and drive every remediation action do not come from it. They come from this system's own harness: LLM-as-Judge evaluators calling Bedrock converse() directly, plus code-based and ground-truth evaluators running as plain Python inside the orchestrator's Lambdas, all emitting procurement/evaluation metrics that the six alarms watch. Only the Kraljic Classifier and Award Comms agents are registered with AgentCore Evaluations for on-demand runs; the judges are not registered with it at all.

The honest limit

At last check the AgentCore online-eval namespace had seen zero sampled sessions, and the exact metric name remains unconfirmed until real traffic flows — both alarms sit on treat_missing_data = notBreaching so they stay inert rather than firing on absence. It is provisioned, not yet proven. The custom evals/ package is the real harness today, and saying otherwise would credit a managed service for work the codebase is doing itself.

Operational prerequisite

CloudWatch Transaction Search must be enabled on the account, because AgentCore Evaluations reads agent traces to score sessions. Without it, neither on-demand nor online evaluations can run — and that half of the quality picture goes blind. It is also, at 100% sampling, dev's single largest CloudWatch cost line, billed even while the environment sits idle — so the dev VPC pause script deliberately withdraws it and the restore script puts it back. A scoped exception, safe only because nothing that depends on it runs during the pause.

It even constrains where you can deploy

Because the quality strategy depends on AgentCore Evaluations, every non-local environment must run in a region where Evaluations is generally available — nine of sixteen regions as of May 2026. This system standardises on us-east-1, which carries the higher session quota and full feature coverage, with us-west-2 as the secondary option. The release strategy literally pins the deployment region.

The shape of it

Pulling the threads together, release safety here rests on three ideas — and one honest caveat about how much of it has been proven.

01
Build once, promote immutably
ECR · semver

The artifact dev built is the artifact production would run, untouched, so rollback is redeploying a known-good image that already exists. Production repositories are forced immutable and retain the last ten tags; dev's are mutable, which is a real caveat on dev rollback targets rather than a footnote.

02
Gate on quality, not just liveness
custom judges + ground truth

Evaluation scores act before exposure (PR checks and the weekly suite), during exposure (the observation window), and after exposure (six alarms bound to five automated remediations). The scoring is this system's own, not the platform's — and one of those gates is currently red on a fixture problem, which is exactly the kind of thing a gate is supposed to make impossible to ignore.

03
Detect fast, expose deliberately
observation window + tenant variants

AgentCore gives no traffic-layer exposure control, so operational regressions are caught by a fast observation window with a five-minute roll-forward instead of a smaller blast radius — and real gradual exposure for behavioral changes runs through operator-driven tenant-scoped variant routing, one layer up.

AgentCore is woven through all three, though not always in the role you would expect. It is the target the pipeline deploys to; the managed runtime whose absent fractional routing is precisely why the deploy-time canary is a monitoring window rather than an exposure slice; the platform whose full-replace update semantics turn "I'll just patch one field" into an outage; and a sampled evaluation service that is genuinely useful and genuinely not the thing holding the release gate. The scores that gate and remediate are the ones this codebase computes itself.

✓
Deterministic release plumbing

Immutable images, semver tags, SHA-as-artifact-identity, split plan/apply, and forward-only rollback — the parts that must be boring and reproducible are exactly that, and the recovery path deliberately reuses the deploy path so it introduces no new variables.

⚡
Quality as a live signal

Evaluation scores treated as a first-class release signal at every stage, so the failure mode unique to agents — healthy but wrong — is caught fast, with five automated responses that change behaviour in ~30s and none that quietly re-enable themselves.

What would make this real

Three things were on this list. One is now done: the gate decision is made and in code — calibration is advisory while the panel is synthetic, judge consistency still blocks, and the labelling pipeline became an upgrade path rather than a blocker.

Two remain. Seed a production smoke tenant — tenant config rows plus category and supplier master data for the four quadrants — so the quadrant test fails for regressions rather than for emptiness. Then cut one release, because a promotion path with zero runs is a design, not a pipeline, and because the first release is the one that establishes the rollback target every later release depends on.

Both are blocked on the same unglamorous fact, and it is worth saying out loud rather than filing under "zero runs": as of 2026-08-19 there is no production environment to seed. No production Terraform state, no production tables, no production image repositories. The pipeline's first run would also be production's first apply. Everything in this post is built and most of it is now verified in dev; none of it has been proven under the conditions it was built for.
