No users table: the OAuth 2.0 resource server pattern, adapted

Buyer Team is an AI procurement system that sits next to an ERP, not next to a directory. We never wanted to manage user lifecycle — we wanted to validate JWTs at the edge and authorise off the claims, so that when a tenant deprovisions someone upstream, their tokens stop being minted and our system stops accepting them within a token lifetime — minutes — with nothing for us to revoke. No webhook, no users table, no cascade delete.

This post is about the decisions behind that property, not the property itself. The canonical OAuth 2.0 resource server / OIDC relying party pattern got us most of the way there; the interesting engineering was in the places it didn't fit, and the trade-offs we accepted to make it fit. Each section below is one decision: what we chose, what we gave up, and why the thing we gave up was cheaper than the thing we kept.

Decision 1: Be a resource server, not an identity provider

The first decision was the most consequential, and almost a non-decision once we framed it correctly: Buyer Team would not own user identity. Multi-tenant procurement customers already operate identity infrastructure — Okta, Azure AD, Keycloak, or an ERP that issues OIDC tokens directly. Asking them to provision a second set of users in our system would reproduce exactly the friction we were trying to remove from the procurement workflow itself.

So Buyer Team is the resource server: it validates access tokens to authorise API calls and consumes assertions issued by an IdP that both our system and the customer's ERP trust. (The OIDC relying party that actually runs the login/federation flow is Cognito, not us — more on that in Decision 2.) Users, group memberships, and entitlements live upstream; we validate tokens and authorise off the claims. The result is a clean division of ownership across three systems.

The trust configuration is global, not per-tenant: one issuer URL, one JWKS endpoint, one expected audience, one clock-skew tolerance, all pointing at a single Cognito pool. What is per-tenant is the federation connection into Cognito and the M2M app client — not a separate set of validation parameters.

The trade

We give up the ability to add an "internal-only" user without going through the customer's IdP, and the ability to short-circuit lifecycle when a customer is slow to deprovision. What we gain is everything a users table would otherwise cost us: no password storage, no MFA enrolment flows, no invitation emails, no compliance reviews on a table that doesn't exist, no cascade-delete logic when a user leaves, no lifecycle webhooks to debug at 3 a.m. when a customer rotates their HR system. The asymmetry is large enough that this isn't really a trade — it's a recognition that identity management is somebody else's core business, not ours.

The token shape that decision produces, for an AI-over-ERP system, looks like this:

{
  "iss": "https://cognito-idp.ap-southeast-2.amazonaws.com/ap-southeast-2_AbC123",
  "sub": "5b1c…",
  "aud": "ai.buyer-team.com",
  "exp": 1716800000,
  "tenantId": "org-acme",            // multi-tenancy isolation key
  "userRole": "buyer-manager",       // coarse role, normalised from the IdP
  "groups": ["procurement-ops"],     // coarse group membership
  "scope": "read approve",           // OAuth resource-server scopes
  "ext": { "erp_user_id": "U12345" } // back-reference into the ERP
}

tenantId is non-negotiable. The Gateway Request Interceptor canonicalises it onto every request body as tenant_id (snake_case is the project convention from the JWT outward — partition keys, cache keys, storage prefixes), and from there it scopes every query in the system. sub identifies the principal for audit. userRole, groups, and scope drive coarse authorisation. ext.erp_user_id lets the AI map back to the ERP's notion of the user. Everything coarse goes in the token; everything fine-grained is checked elsewhere, against a source of truth, at the moment of decision — which is Decision 4.

Decision 2: One federation hub, not N direct trust relationships

Most resource-server diagrams show one IdP and one relying party. Buyer Team has two layers, and the second layer is the decision that holds the whole pattern together.

Layer one is the tenant's own IdP — whatever the customer brings. Layer two is a single Cognito User Pool we operate — the OIDC relying party in the strict sense, the component that runs federation with the tenant IdPs — with a Pre-Token-Generation Lambda attached that normalises tenant identity to a top-level tenantId claim with a predictable shape. Tenant IdPs federate into Cognito via SAML or OIDC; Cognito issues the JWT that Buyer Team actually sees.

The two viewpoints differ, and that's the point. From the customer's perspective, their IdP is the source of truth: deprovision a user, and no new tokens are issued, federation stops, the trust chain breaks at the top. From Buyer Team's perspective, Cognito is the IdP it trusts: one issuer, one JWKS, one audience, one normalised claim shape.

The critical part is how the hub stamps tenantId — and it's symmetric across principal types. For human/user tokens the trust anchor is the tenant's federated IdP, registered as a per-tenant Cognito Identity Provider at onboarding; its attribute mapping stamps custom:tenantId into every JIT-provisioned user, and the Lambda promotes that to a top-level claim. For M2M client_credentials tokens, which carry no user, the trust anchor is the tenant's M2M App Client — also one per tenant — and the Lambda resolves tenantId from the authenticated App Client id, never from caller-supplied ClientMetadata. A user authenticating through tenant A's IdP can only ever carry tenant A's tenantId; an ERP holding tenant A's credentials can only ever resolve to tenant A.

The trade

We accept one extra hop in the trust chain and a Lambda whose entire job is to canonicalise a single claim. The alternative — make the resource server validate N issuers directly — saves a little infrastructure but produces a resource server with N issuer URLs to know about, N JWKS endpoints to cache, N audiences to special-case. And operational cost is the smaller problem: in a system whose entire isolation model scopes off tenantId, letting N independent tenant IdPs each assert that claim directly is a cross-tenant escalation waiting to happen. One misconfigured upstream realm could mint a token claiming another tenant's tenantId, and a resource server that trusts the issuer would honour it. The hub is what makes the isolation key non-spoofable in the first place.

Decision 3: Two principals, two API surfaces, two authorisation planes

This is the most distinctive adaptation, and the one that took the most thinking to land cleanly. Two kinds of principal hit our APIs. ERP service accounts (machine-to-machine, client_credentials) push purchase requisitions into the system on a schedule. Human users (federated through their tenant's IdP) approve high-value awards or resolve negotiations that need attention. Both hold Cognito-issued JWTs, and both go through the same boundary validation. Same trust model, all the way through. What differs is where they enter and what they're authorised against.

ERPs land at the AgentCore Gateway. They're invoking ingest_purchase_requisitions via the Integration Skill — a tool call, from Buyer Team's perspective. The authorisation question is "can this agent, acting on behalf of this principal, call this tool?" The answer comes from the tool-access Cedar plane. The Request Interceptor rewrites the tenant_id argument on every tool invocation from the JWT's tenantId claim, and Cedar decides. Humans land at the Graph Orchestrator's interrupt-resume API. They hit /approval or /resolve with a Bearer JWT, submitting decisions on Purchase Requisitions and Purchase Orders. The authorisation question is "can this user perform this operation on this entity?" — answered by a separate entity-access Cedar plane.

The trade

We could have collapsed both into a single Cedar plane and modelled everything as a tool call. We tried it and rejected it. The semantics of "agent X may invoke tool Y" are different enough from "user U may approve PO P" that mixing them produced policies that were either too generic to be useful or too special-cased to maintain. Splitting them gave us two policy stores with clear, narrow concerns. The cost is one extra abstraction; the benefit is that adding a new tool no longer touches user-authorisation policies, and changing approver rules no longer touches agent-tool policies. Each plane evolves on its own cadence.

There's a subtle layering inside the human plane worth calling out, because it's another deliberate separation. The coarse OAuth scope claim (negotiate / read / approve) and the fine-grained action set (pr:read / pr:ops / po:approve) are not the same namespace. The scope is the outer capability gate, minted uniformly across a tenant — "may this principal touch reads / negotiations / approvals at all?" The action set is the inner per-entity gate — "may this user act on this PR/PO?" Both gates must pass. Note there is intentionally no OAuth scope corresponding to pr:ops: resolution authority is expressed only through the role/group/scope claims a tenant chooses, not a dedicated scope.

Decision 4: Coarse claims at the edge, fine entitlements at the source of truth

The token carries coarse claims: tenantId, sub, userRole, groups, scope, erp_user_id. It does not carry "this user may approve POs under $50K from supplier S in category C with an effective date after 2026-01-01." Keeping that kind of fine-grained payload out of the token is a deliberate constraint, for two reasons. First, tokens have a lifetime — typically minutes to an hour — and entitlements drift faster than that. If a buyer's approval limit changes from $50K to $75K mid-day, you don't want yesterday's token still authorising under the old limit. Second, the token is small for a reason: every request carries it, every service reads it, every audit log keeps a reference. Stuffing entitlements in is the road to 8 KB JWTs and brittle policy.

So the discipline is: use the token for coarse role and scope; re-check fine-grained entitlements against the source of truth at decision time. When a negotiation enters PENDING_APPROVAL, only a user whose JWT satisfies the claim requirement on that specific PR can act on the approval. When a negotiation enters REQUIRES_ATTENTION — one of the 16 explicit triggers in the Graph Orchestrator spec: zero bids, token-ceiling overruns, communication delivery failures, proposal delivery failures, and so on — only a user satisfying that PR's ops claim requirement can work on it.

The trade

A token with full entitlements baked in produces a fast, stateless decision. The pattern we chose pays one DynamoDB read per entity-access decision to fetch the PR's claim requirements and re-check fine-grained authorisation — and that read sits on the hot path for human approval traffic. The price of accurate, current authorisation is a few milliseconds per decision. The price of stuffing entitlements into the token is silent authorisation drift, larger tokens on every request, and approver rules that effectively only update after every active user has re-authenticated. We chose the milliseconds.

Decision 5: How to handle the ERP acting on a user's behalf

The architecture above covers two interaction shapes cleanly: an ERP system account pushing data in (M2M), and a human reaching us directly for an approval. There's a third shape that comes up often enough to design for: ERP-mediated access, where the user is "online" inside the ERP — an embedded panel, an event handler, a workflow step — but isn't presenting a token directly to Buyer Team. Three reasonable approaches, ordered by operational complexity:

Pattern 1
Forward the user's token
The ERP passes the user's existing access token to Buyer Team; we validate it as any direct user request.
When to use The ERP can include ai.buyer-team.com in the token's aud. Trade-off Simplest. Couples the ERP's token audience to ours — less strict separation of authority.
Pattern 2
Token exchange (RFC 8693)
The ERP exchanges the user's token for a Buyer Team-scoped token with the user as sub and the ERP as act.
When to use Strict audience separation, or multi-hop delegation with a verifiable actor chain. Trade-off Cleanest provenance. But you operate a token-exchange endpoint and verify actor chains.
Pattern 3
S2S token + user envelope
A service-to-service token authenticates the ERP; a verifiable user-context envelope rides alongside.
When to use Autonomous or system-initiated work with no live user — where most agentic flows land. Trade-off Necessary for that case. Trust shifts to envelope signing; harder to audit than act.

We landed on a combination, spanning all our invocation paths rather than just the ERP-on-behalf case. M2M client credentials for system ingestion (no user behind it at all). Token forwarding for interactive ERP-embedded scenarios. Service-to-service plus a user-context envelope for autonomous background runs where there's no live user to forward a token from — which, for the token-lifetime reason in the next decision, is where most agentic flows land. The right answer is rarely just one pattern; most production deployments combine all three.

Decision 6: Snapshot the authorisation context — don't re-validate mid-chain

The OAuth 2.0 resource server pattern was designed for the request-response web. AI systems aren't quite that. Tool chains outlive the tokens that authorised them; agentic flows call downstream across multiple hops; result caches and embedding stores hold data that crosses request boundaries. The canonical pattern says nothing about any of this. Four practices close the gap, each a small decision with a clear trade-off.

Snapshot the authorisation context at entry. Validate the token at request entry — signature, iss, aud, exp, clock skew, kid — and snapshot the relevant claims (sub, tenantId, scopes, original jti for audit) into the job or conversation record. Downstream work executes under the captured context; we never re-validate mid-chain. Token lifetimes are minutes; agent chains routinely run longer. Re-validating mid-chain would mean either rejecting legitimate work because a token expired naturally, or carrying a refresh token — which moves us back toward owning credentials we don't want to hold. The trade is explicit: a token revoked mid-chain won't stop already-authorised work, in exchange for not holding refresh credentials and not breaking long-running flows.

Background and async work uses the same snapshot. Recovery workflows, cost-attribution batches, long-running auctions that span days — none has a live user holding a token. They run under the context captured when the work was originated, scoped by tenant_id, with sub recorded for audit. Same property: no live user, no live token, no users table — just a captured context.

Cache keys include tenant_id by construction. This is the single most common multi-tenancy bug in AI systems, and the hardest to catch in review because it surfaces only when two tenants send semantically similar requests. Every LLM result cache, every embedding cache, every semantic cache includes tenant_id in the key. Buyer Team's Kraljic classification cache, for example, is partitioned with PK = {tenant_id}#kraljic_classifier and SK = {category_id}#{hash(profit_impact, supply_risk, thresholds)} — never by category and hash alone. The threshold hash in the sort key is a second decision: it makes a config change to the classification thresholds invalidate the cache automatically on the next classification, rather than serving a stale quadrant.

JWKS caching respects kid. Cache aggressively; on an unknown kid, refetch once (rate-limited) rather than erroring out. Cognito rotates keys, and a stale cache that errors on a rotated kid produces a brittle dependency on cache freshness. "Refetch once on unknown kid" keeps validation resilient to expected rotations without opening a window where a forged kid could trigger unbounded JWKS fetches.

The property that falls out: no users table, end to end

The point of the resource server pattern was always the lifecycle property. The decisions above were taken to preserve it; here's the check that they did. The persistent per-tenant identity artefacts Buyer Team owns are configuration objects, not user records: an M2M Cognito App Client for the tenant's ERP service account, and — for tenants whose people sign in interactively — a federated Identity Provider registered in our shared pool together with a per-tenant user App Client bound to it. All three are created once per tenant at onboarding. Three small config objects between us and the tenant's IdP; no users table beside them.

Human users are entirely upstream. They surface inside Buyer Team only as JWT claims at the moment they hit /approval or /resolve. Our application state holds nothing about them beyond audit rows keyed by sub and tenant_id. Cognito JIT-provisions an identity-layer record on first federated sign-in, but that record lives inside the pool as identity infrastructure, not as application state we write code against.

When a tenant deprovisions a user upstream, their IdP stops issuing tokens; federation through Cognito stops minting normalised JWTs; once the last already-issued token expires — minutes, given our lifetimes — Buyer Team stops accepting that user at the next request boundary. The JIT'd Cognito record stays put, dormant: it has no password to authenticate against, only the federation trust the upstream IdP just severed. No webhook fires. No application row is deleted, because none ever existed. No cascade runs. The user simply stops appearing in incoming requests, and the only thing the system ever recorded about them — the audit trail — is the only thing left.

The IdP owns identity. The ERP owns business records. Buyer Team owns operations and decisions. JWT claims are the contract between them — coarse at the edge, fine at the source of truth, snapshotted into long-running work, scoped by tenant_id through every cache and storage prefix in the system. Six decisions, each with a trade we'd make again; the property the architecture set out to deliver is the property we got.
