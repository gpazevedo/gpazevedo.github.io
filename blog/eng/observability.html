Observing the Unobservable:
how a multi-agent system watches itself think

Agentic systems fail silently. They don't crash — they drift. Here's the architecture we built to catch quality degradation in a multi-agent procurement system before it costs anyone a contract.

Traditional software fails loudly. A service throws a 500, the latency alarm fires, the on-call engineer wakes up. Agentic systems have a much more sinister failure mode: they keep running, returning HTTP 200s, spending tokens — and producing subtly wrong outputs that no dashboard catches until a procurement decision is already made.

Buyer Team is a multi-agent AI system that automates procurement negotiation end-to-end: classifying purchase requisitions, selecting bid strategies, communicating autonomously with suppliers, and recommending contract awards. The agents run on AWS Bedrock AgentCore and the Strands Agents SDK. When something goes wrong here, it isn't a null pointer exception — it's a negotiation that saves 4% instead of 12%, or a supplier rejection notification that inadvertently reveals who won the auction.

This post walks through the observability architecture we designed to catch those failures, and the trade-offs behind every major decision.

The core problem: four failure modes unique to agents

Before designing anything, we mapped the failure modes that make agentic systems hard to observe. There are four.

Non-determinism. The same input doesn't produce the same output. A traditional function is easy to regression-test; an LLM agent requires statistical evaluation over distributions.

Multi-hop reasoning opacity. A negotiation spans dozens of tool calls across six specialized agents. The final output is only as good as the weakest reasoning step in the chain — and the weakest step is invisible unless every hop is traced.

Cost opacity. Every agent invocation burns tokens. A single buggy retry loop in one agent can silently 3× the cost per negotiation before anyone notices.

Silent quality drift. The model doesn't know it's getting worse. Evaluation scores degrade gradually — a Communication Tone score drifting from 0.95 to 0.79 over two weeks doesn't trigger any infrastructure alarm on its own.

"The agents keep running, returning 200s, spending tokens — and producing subtly wrong outputs that no dashboard catches until a procurement decision is already made."

Our architecture addresses all four with a four-layer observability model layered on top of continuous automated evaluation. The two concerns are deliberately separated: observability tells you what happened; evaluations tell you how well.

The four-layer observability model

Each layer has a different granularity, owner, and instrumentation cost. Together they create complete coverage from raw infrastructure to business outcome to dollar cost.

Trade-off: why not a single observability plane?

The obvious simplification would be to emit everything to one system. We rejected this for three reasons. First, Layer 1 is free — AgentCore emits platform metrics with zero instrumentation. Routing those through our OTEL pipeline would add latency and cost for no benefit. Second, the audiences diverge: SRE reads Layer 1 (is the agent up?), engineering reads Layer 2 (what did the agent do?), procurement reads Layer 3 (did the negotiation succeed?), and finance reads Layer 4 (what did it cost?). Separate namespaces (AWS/Bedrock-AgentCore, procurement/business, procurement/kpi, procurement/cost, and — most relevant to the rest of this post — procurement/evaluation, plus narrower ones for resilience, security and observability internals) let each team build dashboards without fighting over metric cardinality. Third, FinOps sits at a different altitude, not just a different namespace: Layers 1–3 are separated by how they're instrumented, but Layer 4 shares Domain's EMF mechanism and is split out on audience and unit economics. The reconciled aws_cost.usd figure Cost Explorer republishes belongs to no other layer.

Distributed tracing across agents

Buyer Team uses a Step Functions orchestrator whose node Lambdas invoke six specialized A2A agents: a Kraljic Classifier routes each category into one of four Kraljic-quadrant strategy agents — Strategic Partnership, Bottleneck Negotiation, Leverage Auction, and Spot Bidding — while an Award Communications agent handles all supplier messaging. A complete negotiation is not a single request — it's a choreography that spans several of them.

The key architectural decision here is W3C traceparent propagation across every A2A invocation. Every agent-to-agent call carries the same root trace context, so the entire negotiation — from purchase requisition intake to award recommendation — appears as a single distributed trace in X-Ray. This is not the default behavior; it requires explicit instrumentation on every tool call boundary.

Why does this matter? Because the failure we're trying to catch often lives at a boundary. An Award Communications agent that calls a generate_rejection_notification tool and leaks winner information to losing suppliers is invisible in Layer 1 metrics — error rate is zero, latency is fine. What catches it is the WinnerDisclosureGuard steering hook, which runs pre-call: it inspects the tool's render map for any winner-identifying field (winner_name, awarded_price, score, rank, and nine more), and on a hit returns Strands' Guide — cancelling the tool call and feeding the model back exactly which fields to remove, so the leak never reaches a supplier and the model recomposes a winner-free call.

The observable trace of that block is a metric, not a span event: governance.violation_count in procurement/business, dimensioned violation_type = confidentiality_leak. Two alarms watch that one metric at different severities, which is what makes the guard auditable rather than merely effective.

Span attribute design: procurement-native semantics

Spans on the orchestrator's node Lambdas carry procurement-native attributes rather than generic HTTP ones — procurement.negotiation_id and procurement.tenant_id on every node, plus procurement.strategy on strategy execution and procurement.agent.model_id on each A2A hop, so a trace answers "which tenant, which negotiation, which quadrant, which model" without a join. Config resolution tags its own span with config.source, which is how a fallback to security_critical_fallback becomes visible instead of silent — the failure mode that bit us before (see the resilience-layer reseed problem) was agents quietly running on defaults.

The honest limitation: this is a useful set, not a uniform schema. Attribute coverage grew per node as each one needed it, so which attributes you can filter on depends on which span you caught — a real seam we call out again at the end of this post.

Three evaluator types, zero guessing

Observability tells you what happened. Evaluation tells you whether it was any good. We rely on three evaluator types, each chosen for different reasons.

Type A
LLM-as-Judge
qualitative
Three rubrics — Communication Tone, Rationale Defensibility, and the Negotiation Quality Composite — all scoring live production output. Tone reads the persisted supplier communications; the other two score the strategy agents' persisted reasoning text post-award. All three run in Node 7's asynchronous _eval_only self-invoke, deliberately off the synchronous PO-issuance path so a Bedrock judge call can never stall a purchase order. Costs ~$0.004/eval. Reserve for criteria that require reasoning, not parsing.
Type B
Ground Truth
deterministic
Compares Kraljic classification, bid-ranking coverage, and six Lambda-tier evaluators against fixture-based golden datasets. Offline, no AWS calls, sub-second. The CI gate is strict — it asserts 100% pass/fail agreement on every known-good and known-bad fixture row, not a tolerance threshold — and blocks the PR outright on any regression.
Type C
Code-based (Lambda)
structural
Deterministic Lambda functions validate bid JSON schema, required fields, and governance policy adherence. Scores are binary: 1.0 or 0.0. Any non-1.0 triggers an immediate alarm — there is no "partial compliance."

Trade-off: the communication tone sampling problem

Communication Tone is the most expensive evaluator to run at scale — it fires per supplier message, not per negotiation. A busy auction with 12 suppliers generates 12+ messages, each needing evaluation. Running LLM-as-Judge on all of them at $0.004/eval adds up quickly.

The solution is a tiered sampling strategy driven by risk, not randomness.

Always 100% — award notifications. These are legally binding, and there are far fewer of them than rejections (one per negotiation, versus one per losing supplier). Full coverage here is cheap and non-negotiable.

Value-threshold 100% — rejections above $50,000. For negotiations at or above a configurable awarded-price threshold (default $50,000), rejection notifications also get full tone coverage. High-value purchases warrant full scrutiny.

Sampled (10% default) — rejections below the threshold. Everything else gets a configurable sampling rate. Both the threshold and the rate are read from the governance config's evaluation block with per-tenant DynamoDB overrides, so an enterprise tenant can set their own risk appetite.

Two details matter more than the tiers. First, sampling is deterministic, not random: the gate is a SHA-256 hash of the communication ID compared against the rate, so a communication's sampling decision cannot flip when Step Functions retries the node — random.random() would have made replay non-reproducible and quietly double-billed the judge. Second, tone sampling is not the confidentiality control, and it would be a mistake to read it as one. Winner-disclosure protection doesn't depend on sampling at all: rejection notifications are template-rendered from a bounded, winner-free field set, and WinnerDisclosureGuard inspects every rejection render pre-call. The 10% tier risks missing a clumsily-worded rejection, not a leaked winner.

The quality composite: a 25-point rubric

The Negotiation Quality Composite is a 25-point score across six equally-weighted components — an LLM judge scores each 0.0–1.0, and the composite is simply the average of the six, scaled to 25.

Component Weight Max points
Ranking Accuracy16.7%4.17
Rationale Defensibility16.7%4.17
Risk Detection Accuracy16.7%4.17
Scoring Consistency16.7%4.17
Completeness16.7%4.17
Savings Calculation16.7%4.17

We deliberately kept the weighting flat rather than hand-tuning per-component weights up front — we have no data yet that would justify weighting Ranking Accuracy above Savings Calculation. Differentiated weights are a plausible future iteration once we have enough scored transcripts to validate them against real outcomes, not a decision we wanted to make blind.

What this composite scores is worth being precise about, because it isn't what the rubric was originally written for. Its first call site was the bid-evaluation agent, which we removed. Rather than delete the rubric, we re-pointed it in August 2026 at negotiations.reasoning — the strategy agents' persisted free-text rationale, written at the strategy-execution node and now the only rationale text on a negotiation. The scoring path is live: Node 7's asynchronous eval branch reads that field post-award and emits the composite, normalized to 0–1 by dividing by the 25-point maximum so the alarm threshold keeps its original semantics.

The honest caveat isn't that it doesn't run — it's that a six-component rubric written to grade a bid evaluation is now grading strategy reasoning. Components like Ranking Accuracy and Savings Calculation fit that text less naturally than Rationale Defensibility does. It's a deliberate re-purposing that keeps the signal alive, and re-validating those six components against what they now actually read is on the list.

Alarms that actually do something

Most observability implementations stop at "alert the on-call." Our design goal was to go further and map every alarm to a defined automated response — model rollback on a quality drop, auto-send disabled on a tone drop, negotiations halted on a governance breach. For most of this system's life that second half was unbuilt, and earlier versions of this post said so. It closed in August 2026: all five automated responses are now live Lambdas subscribed to the evaluation-alerts SNS topic, each verified end-to-end with a synthetic alarm payload.

The wiring is deliberately blunt. Every alarm in the repo publishes to the same shared topic, so all five remediation Lambdas receive every alarm notification and each one filters to exactly the alarm name it owns, acting only on the ALARM transition. Every action is a single DynamoDB update_item against the governance config — flip auto_send_communications off, set negotiations_halted, bump cache_epoch, swap the model tier map back to its previous snapshot.

The most important property is what they don't do: none of them re-enable on the OK transition. Recovery is deliberately manual. An alarm that auto-disables and auto-re-enables would flap a production safety control on a metric's noise floor, and the whole point of these actions is to fail toward caution and make a human look.

Alarm Status Threshold Routes to
Negotiation Quality Drop live avg < 0.60 model rollback
Communication Tone Drop live avg < 0.80 disable auto-send
Rationale Defensibility Drop live avg < 0.70 block auto-award
Kraljic Accuracy Drop live min < 0.90, daily invalidate cache
Bid Format / Governance Policy Compliance live min < 1.0 halt negotiations
Governance Violation (any type) live count ≥ 1 warning tier
Confidentiality / Winner-Disclosure Violation live count ≥ 1 critical tier
Token-Volume Spike live ≥ 1M tokens/hr, flat warning tier
Node / Workflow Errors live count ≥ 1 per 5 min warning tier
DLQ Redrive Exhausted live count ≥ 1 per 5 min warning tier

A few things are worth being explicit about, since they don't match what a tidier version of this table would suggest. Every threshold in the "Threshold" column is a first-pass guess. None are tuned against real production volume, because we don't have real production volume yet — this is a dev environment with synthetic traffic. A number like 0.80 for tone reads authoritative in a table and is, honestly, a starting point.

The token-volume spike alarm is a flat threshold across all agents and tenants, not the per-tenant moving-average comparison a real FinOps signal needs, and there's no dedicated FinOps SNS topic — it alarms on raw token counts because a per-token dollar metric doesn't exist. The error alarms are raw counts (any error in a 5-minute window), not percentage rates, which will get noisy the moment volume is real. The Kraljic accuracy alarm evaluates one datapoint per day, emitted by a scheduled harness rather than by production traffic, so it's closer to a daily regression check than a live signal — and it's deliberately configured to stay silent rather than emit a bogus 0.0 when the dev environment is cost-paused, since a spurious 0.0 would invalidate the semantic cache for no reason.

There's also a routing wrinkle worth naming. Only the confidentiality violation goes to the critical tier; everything else shares one topic. That's not a considered severity taxonomy so much as the fact that both topics currently resolve to the same single email address. And that address only started working recently: the subscription was gated on a Terraform variable set in a gitignored .tfvars file, so CI resolved it to an empty string and actively destroyed any subscriber applied by hand. Alarms fired correctly into a topic nobody was listening to. Detection being correct is not the same as detection reaching a human, and it took an audit rather than an incident to notice.

Trade-off: 100% online evaluation coverage

Sampling creates systematic blind spots in an agentic system: a governance violation that happens to land outside a 10% sample is a violation the system never catches. So for the Code-based evaluators — which run inline in milliseconds and cost fractions of a cent — we made 100% online coverage the default, and it's live: Bid Format Compliance and Governance Policy Compliance score every real bid, not a sample. Ground Truth is a different story, and we're not overclaiming it: it needs a known-correct label, which live production requisitions don't have, so it can't run online against real traffic the way the Code-based evaluators do. It's a PR-time gate against a fixture golden set. AgentCore's built-in Evaluations SDK runs a complementary sampled monitor — six configs now (Kraljic Classifier, Award Comms, and the four strategy agents) at 5–10% sampling — but that lives in an isolated Terraform root behind a manual dispatch, deliberately kept out of the automatic deploy because those APIs are still marked preview and a hiccup there must not be able to block a normal deploy. Of the LLM judges, only Communication Tone is sampled; Negotiation Quality and Rationale Defensibility score every award, since there is one of each per negotiation rather than one per supplier.

Trade-off: a quality gate we deliberately stopped enforcing

The human-calibration check (REQ-O221) compares the judge's scores against human labels and suspends the judge past 0.20 mean absolute deviation. It blocked prod promotion through five consecutive weekly runs, every one failing identically at MAD 0.607 — and the diagnosis was not judge drift. The "human" labels in the fixture panel are a generated placeholder whose own header disclaims any evidentiary weight. The MAD was deterministic, and the gate was structurally unpassable.

So we downgraded it: while the fixture declares synthetic_scores: true, calibration reports as an advisory warning instead of blocking. Judge consistency still blocks unconditionally, because that measures something real — the same transcript scored repeatedly should land in the same place. The fail-safe direction matters: the downgrade requires the synthetic flag to be present and true, so dropping in real dual-human-scored transcripts restores blocking automatically with no code change. Grading a judge against labels we invented measures nothing, and a gate that cannot pass only teaches people to route around it. But it is still a weakened gate, and calling it anything else would be dishonest.

Graceful degradation under memory failure

Cross-negotiation context — supplier performance history, previous award patterns, category expertise — was specified to come from AgentCore Memory and Mem0. Mem0 is not wired (AD-073); the strategy agents read a DynamoDB-derived supplier history as a substitute, and the Mem0 circuit breaker guards a call path that nothing currently takes. When AgentCore Memory is unavailable, agents don't crash: the breaker catches the failure and the negotiation continues with a memory_degraded boolean persisted on it.

That flag is the entire observability surface today, and it isn't what we designed. The original design (PRD-014 §5.2) called for relaxed numeric quality thresholds under degradation and a dedicated memory.fallback_activated metric; neither exists in code, and there is no alarm on degraded-state quality. No automatic post-completion re-evaluation, no incident record. The flag is queryable by a human or a future check, but nothing consumes it.

We're leaving this gap in rather than quietly upgrading the boolean to match the original design, because the honest version is more useful: right now, "the system degraded gracefully" means the negotiation didn't crash and the fact that it ran without memory is recorded — not that quality was measured and compensated for. Closing that gap is on the backlog, not shipped.

Architectural trade-offs: the summary

⊕
Separate observability layers

Four distinct metric namespaces instead of one unified pipeline. Added complexity, but gives each audience (SRE, engineering, procurement, FinOps) clean separation without metric cardinality explosions.

⊕
W3C traceparent across all A2A

Requires explicit instrumentation at every agent boundary. The overhead is ~2ms per hop. The return: every negotiation appears as a single distributed trace, making cross-agent failures visible instead of invisible.

⊕
Risk-tiered evaluation sampling

Saves ~90% of Communication Tone evaluation cost on routine low-value messages. Accepted risk: 10% of non-critical, below-threshold communications go unevaluated. Mitigated by 100% coverage on legally binding and confidentiality-sensitive messages.

⊕
Detection first, then actions

Alarm-to-action pipelines require threshold calibration to avoid false rollbacks, so we built detection and severity routing first and wired the five automated responses afterward. Both halves are now live, with recovery deliberately left manual — nothing re-enables itself on the OK transition. The remaining weakness is underneath: the thresholds those actions fire on are untuned first-pass guesses, so the loop is closed but not yet calibrated.

What we'd do differently

The four-layer model is clean, but the span attribute schema grew organically and shows its seams. Attributes were added per node as each one needed them, so coverage is uneven — procurement.negotiation_id and procurement.tenant_id are everywhere, but strategy and model attributes exist only where someone had a reason to add them. Deciding the full attribute set once, up front, and enforcing it in a shared helper would have cost a day and saved the "which spans can I actually filter on?" question that recurs every time someone writes a new Logs Insights query.

The bigger regret is that we let observability follow the code instead of leading it. The evaluation metrics existed for months behind alarms that had been deleted in a cost trim, then restored, then pointed at a metric whose emitter had been removed by an unrelated PR — each state individually reasonable, and the aggregate quietly meaningless. The alarm-to-nobody SNS bug is the same shape. Nothing in the pipeline tests the pipeline: we have alarms on the agents and no alarm on "this alarm's metric has received no data in 30 days," which is exactly the check that would have caught all three.

Finally, a naming collision we only caught while writing this piece: the per-tenant governance override called negotiation_quality_composite_minimum sounds like it should gate the LLM-judge Negotiation Quality Composite this post spends a whole section on. It doesn't — it gates a completely different, deterministic bid-ranking composite (price/delivery/quality/compliance weighted, computed at bid-evaluation time) that decides whether an award auto-approves or escalates to a human. Two unrelated scores share adjacent vocabulary in the codebase, and it's the kind of thing that looks fine in a code review and only becomes confusing when someone's trying to explain the system end-to-end, the way we're doing here. Renaming one of them is now on the list.

The broader lesson

The investment in observability and evaluation is proportional to the autonomy of the system. A traditional CRUD application fails loudly and recovers quickly — you can afford to observe it lightly. An autonomous negotiation agent that makes decisions on behalf of an organization, communicates directly with external suppliers, and recommends contract awards needs to be observed at every layer, evaluated continuously, and designed to roll itself back before a human notices the problem. That last part is now built rather than aspirational — but closing the loop moved the risk rather than removing it. The thresholds those automated actions fire on are untuned guesses against synthetic traffic, and an automated response on a badly-calibrated threshold is a new failure mode, not just a safety net. That is the honest current risk surface, and naming it precisely is more useful than a diagram implying the problem is solved.

The goal isn't to make the system easier to debug. It's to make it safe to trust — which starts with the observability layer telling the truth about itself.
