One microkernel, six plug-ins: the patterns behind Buyer Team

Buyer Team runs six LLM agents. Each one boots in about forty-five lines — import a spec, hand it to a factory, serve — and everything that makes it a running service lives once, in a runtime none of them can override. That's not an accident of refactoring — it's a microkernel, and once you name the governing pattern, a couple of dozen classical design and architectural patterns fall out of it in order. This post walks the whole set, from Factory Method to graceful drain, and is honest about the one thing pattern catalogues usually hide: which guarantees the code actually enforces, and which are just a CI test standing in for a promise the runtime can't make.

The shared runtime, buyer_agent_core, is the machinery underneath every agent. This post reads that same system through a different lens — not "what does the runtime guarantee," but "what are the named shapes it's built from, and why those." Patterns are a vocabulary, not a scorecard; the value here is that naming them exposes where the design is load-bearing and where it's leaning on convention.

The governing pattern: microkernel / plug-in

Everything starts here. buyer_agent_core is the core — the invariant runtime baked into the agent-base Docker image. Each of the six agents is a plug-in that contributes exactly one thing: a declaration. The kernel supplies model resolution, serving, prompt caching, guardrails, admission control, and drain. The plug-in supplies a name, a tier, a prompt, some tools, and a schema — and nothing else.

Plug-in AgentSpec — the contract per-agent, 67–143 lines
14 required fields 6 optional fields name · tier · prompt · tools · schema
Boundary DynamicAgentFactory.build(spec) one call, six callers
spec goes up, never subclassed down
Core buyer_agent_core — the invariant runtime shared, lives once
model ladder serving caching guardrails admission drain

The line between the top row and the bottom two is the whole design. Everything below it is 100% fixed across all six agents. That single boundary is what makes the rest of the pattern list possible — and a plug-in author genuinely cannot override it, because there is no base agent class to subclass and the code they'd need to replace doesn't exist in their module. It exists once, in the base image.

What they can still do is go around it — import boto3 or strands directly and talk to the platform without the kernel's knowledge. Nothing in the runtime prevents that, and it isn't hypothetical: six copies of the same boto3.resource(...) construction had already accumulated across the agents' tools.py files, and steering decisions were being imported straight from strands.vended_plugins, before anything was watching. What watches now is a test. Hold that thought — it's the subject of the last section.

"Things the architecture makes it impossible to get wrong, because that logic lives once."

That sentence is the design's north star. The word for it is poka-yoke — mistake-proofing; design-by-constraint. The reason the runtime owns model selection, guardrail wiring, and the drain sequence isn't tidiness. It's that an agent author can't misconfigure what they're never handed. Every pattern below is in service of that one idea, and the honest ones among them admit exactly how far the mistake-proofing reaches.

Not the only shared kernel in this codebase

The same instinct shows up twice more outside the agent fleet, at a smaller scale. lambda_core is a shared Lambda Layer — cached boto3/DynamoDB clients, structured logging, metric emission, and the guarded() / http_error_response() failure-handling primitives — attached to all twelve Lambda handlers, with a shared DLQ wired for eight of them. mcp_servers/shared plays the same role for the three MCP servers: one build_mcp_app() factory, one opaque-error decorator, one tenant-trust check, imported instead of reimplemented per server. Both are Shared Kernel in the same DDD sense as buyer_agent_core — one implementation instead of N copies — but neither is a microkernel in the fuller sense this post uses for the agent fleet: there's no AgentSpec-style declarative contract, just functions and decorators imported piecemeal rather than a spec handed over for a blueprint back.

Both now have the agent fleet's own reach-around guarantee, not just its aspiration: an AST-walk boundary test per area, added after the fact, the same way the agent-layer test was. Writing the Lambda one reran the agent fleet's origin story in miniature — two handlers were already importing Key/TypeDeserializer straight from boto3.dynamodb, so the test would have gone red on day one. Both now import them from lambda_core instead, which re-exports them the way buyer_agent_core re-exports Attr, and the test that would have caught the old version is what's running now. The MCP test stops one check short of parity, honestly: mcp_servers/shared has no top-level __all__ to check membership against, so every server still builds its own boto3 client — approved in that test's allow-list, and named as a real gap rather than quietly closed.

Design patterns — the object level

Zoom into the boundary and the classical Gang-of-Four vocabulary shows up almost one-to-one. None of these were reached for by name; they're what you get when you insist that per-agent behaviour be data the kernel consumes rather than code the agent overrides.

Pattern Where it lives What it buys
Factory Method DynamicAgentFactory.build(spec) → AgentBlueprint; make_runner, build_app as factory functions. The agent never news its own runtime. It hands over a spec and gets a fully wired object back.
Builder (two-phase) "Build once, mint per request." AgentBlueprint assembles the expensive shared parts once; new_agent(req) mints a fresh instance per request. The standout of the set — the cost of construction is paid at boot; the isolation of statelessness is paid per call.
Strategy Injected callables on the spec: prompt_builder, response_builder, context_builder, summary, plugins. Pluggable per-agent behaviour over a fixed runtime — swap the algorithm, keep the machine.
Template Method make_runner's fixed two-step skeleton: analysis → coercion, with the coercion step overridable via response_builder vs. structured_output(). The shape of a run is fixed; only the marked step varies.
Specification / Parameter Object AgentSpec itself — a frozen, declarative data object the rest of the system reads. Behaviour becomes inspectable data. You can print an agent's whole identity.
Chain of Responsibility The model-resolution precedence ladder: live config → env var → seed mirror. Each link answers or defers; boot never depends on any one source being up.
Interceptor / Middleware AdmissionControl ASGI middleware; Strands hooks log_tool_call / compact_tool_output; steering plug-ins like WinnerDisclosureGuard. Cross-cutting behaviour wraps the request path without any agent knowing it's there.
Null Object plugins defaulting to lambda req: []; the _unknown tenant bucket; an absent trace-carrier yielding the root context as a safe no-op; a partially-configured guardrail collapsed to a clean unset rather than a malformed Converse call. The "nothing configured" path is a real, tested object — not a branch someone forgot to write.
Decorator (fail-closed) GuardHandler wrapping Strands' SteeringHandler: the framework's own steer_before_tool swallows a guard's exception at DEBUG and returns without setting cancel_tool, so a guard that trips on a malformed payload silently lets its tool run unguarded. The subclass catches anything escaping check() and converts it into a Guide that cancels the call. A confidentiality guard fails closed — the one moment it's most likely to break is the one moment it must not disappear.
Adapter _remote_context adapting A2A message.metadata into an OTEL parent span; guardrail_kwargs() adapting env vars into Converse kwargs. Two vocabularies that shouldn't know about each other meet at a translation seam.
Dependency Injection / IoC Agents inject their spec up into the shared runtime rather than subclassing down. "You never subclass a base agent class." Inversion is the whole point — the kernel calls you.
The one to remember

If you take a single pattern from this section, take the two-phase Builder. "Build once, mint per request" is where the cost model and the isolation model meet: the expensive, shared, read-only scaffolding is constructed a single time at boot, and every incoming request gets a fresh, disposable Agent minted from it. That one split is simultaneously a performance decision and a security decision, which is why it recurs in the architectural section below as stateless worker.

Architectural patterns — the system level

Step back from the object graph to the running service and a second, mostly-disjoint vocabulary appears — the resilience and operability patterns. These aren't about how the code is shaped; they're about how the process behaves when config tables blink, when a tenant floods it, and when the orchestrator sends SIGTERM.

Pattern Where it lives What it buys
Shared Kernel (DDD) buyer_agent_core baked into agent-base — "the only place this logic physically exists, so there's no local copy of it to drift." Reuse without a versioning treadmill; drift is prevented by physics, not policy.
Load shedding / backpressure Fast-reject with 503 + Retry-After: 1 instead of unbounded queuing. An overloaded worker fails fast and cheap rather than degrading everyone behind a growing queue.
Graceful degradation / fallback A config-table outage degrades model selection but never fails boot; an unparseable guardrail assessment is read as a block, not a pass. The dependency being down costs you the best answer, not the service.
Health check / readiness probe /ping as readiness (not liveness), gating rotation. A draining or warming instance is pulled from rotation without being killed.
Graceful shutdown (drain) SIGTERM → flip readiness → drain in-flight runs within a bounded timeout. Deploys and scale-downs don't sever active negotiations mid-run.
Stateless worker / share-nothing Per-request Agent minting as the isolation mechanism — "tenant isolation is per-request, not per-tenant." No cross-request state means no cross-tenant leakage; isolation is structural.
Pipeline The two-step analysis → coercion run; the executor's streaming tool-status artifacts. Each stage has one job; the seams are observable.
Distributed tracing / context propagation A W3C trace carrier smuggled through the A2A message body because AgentCore strips HTTP headers. A single trace survives the hop even when the transport won't carry the headers.
Twelve-factor config Behaviour tuned entirely through env vars — prompt-cache toggles, tool-output caps, per-tenant concurrency limits. Tuning is a deploy variable, not a code change; the same image behaves differently per environment.
⊕
Load shedding

Chose: cap concurrent in-flight runs and reject overflow fast with 503. Trade-off: a burst is shed even though the work would eventually fit if it queued. Gain: an overloaded replica fails fast and cheap instead of degrading everyone behind a growing queue.

⊕
Stateless worker

Chose: mint a fresh Agent per request. Trade-off: you pay per-request construction instead of reusing a warm object. Gain: tenant isolation you can't accidentally break, because there's nothing shared to leak.

The nuance worth calling out

Here's where a pattern catalogue usually lies by omission. Naming a pattern is not the same as enforcing it, and this design is unusually candid about the difference. There are three rungs a guarantee can sit on, not two. Some are structurally enforced — the code physically cannot do the wrong thing. Some are conventionally enforced — the wrong thing is possible, and a test, or a fatal exception on a misconfigured deploy, is what keeps it from shipping. And the lowest rung is merely observed — the wrong thing is possible, nothing stops it, and an alarm tells you afterwards. One row below used to sit there; it's since climbed to conventional, and how it got there is worth watching closely.

Guarantee How it's held What could still break it
No agent overrides the runtime Structural. There is no base agent class to subclass; the overridable code doesn't exist in the agent module. Nothing at the agent level — you'd have to edit the base image.
No agent reaches around the runtime Conventional. An AST test walks every agent module and rejects any import root outside the stdlib, its flat siblings, and three approved packages — plus a ban on dynamic-import machinery to keep the first check sound, and an __all__ membership check so a re-export is distinguishable from an import artifact that merely happens to be reachable. Nothing at runtime. This one had already been breached before the test existed, which is why the test exists.
Per-request statelessness Structural. A new instance is minted per request; there's no shared object to reuse. Nothing on the normal path — isolation is a property of the object graph.
Guardrail block short-circuit Structural. Only an affirmatively anonymize-only intervention is allowed through; an empty or unparseable assessment, or any BLOCKED action anywhere in it, is treated as a real block — and that block is re-raised past the retry loop rather than retried. Nothing — the secure reading is the default branch.
Cache byte-identity Structural. The prefix is assembled once per blueprint; a spec's per-request context_builder block is appended after the cachePoint, so variable data can't move the cached bytes. Nothing a spec author writes — the breakpoint is upstream of anything they control.
Guardrails are actually attached Conventional. guardrail_kwargs() raises a required-config error when guardrails are mandated but the guardrail ID/version are unset; since every agent's entrypoint calls DynamicAgentFactory.build() at module import time, the raise crashes the process before it ever binds its port. The Terraform for the primary and canary runtimes sets the guardrail-required flag, and it's live — confirmed in Terraform state on both, with a targeted plan showing no drift. Local runs and tests still leave it unset by design, so unset stays legitimate off the deployed path. A CloudWatch alarm and a live SNS email subscriber also make an unconfigured deploy pageable, not just fatal. The flag is hand-set on two runtime blocks; a new runtime added later without it silently reverts to fail-open, and nothing would catch that but a reviewer. The check only fires at process boot, too — it can't catch a guardrail that goes missing from under an agent already serving. This was proven fail-open live once, before the fix — an adversarial replay scored 0/60 blocked because no agent was passing the guardrail config.
Seed-mirror invariant (the model ladder) Conventional. A CI drift test parses the seeding script and asserts the in-image mirror matches its tier map literal. The test locks the mirror to the seed script, not to live config — both can drift away from what's actually in the config table, and nothing checks that.

The amber rows are the honest part, and note where they fall. The seam that the whole microkernel story rests on is one of them: an agent can reach past the kernel to boto3 or strands, and what stops it is a test in CI, not the shape of the code. The guardrail-attachment guarantee used to be the extreme case — merely observed, nothing stopping a deploy from serving unprotected but an alarm after the fact. It isn't anymore: a fix now makes an unconfigured guardrail crash the process at boot, and the terraform that arms it on the deployed runtimes has actually been applied, not just merged — checked directly against Terraform state, not assumed from the commit. It's still only conventional, not structural — a new runtime block that forgets the flag reverts to fail-open with nothing to catch it but review — but that's a real rung climbed, not a promise of one. These are patterns the design aspires to make mistake-proof; some have arrived, some are a test or an alarm standing in for a guarantee the code can't fully make yet.

That's worth sitting with, because the temptation is to describe the boundary as physics and move on. It isn't physics. It's a very good habit, written down as an assertion, that had already been broken once before anyone wrote the assertion. Poka-yoke is the goal everywhere; the design earns its credibility by saying plainly where it's still only convention with a safety net.

Why the candor matters

The failure mode of pattern-driven design is treating the pattern as the guarantee — assuming that because a thing has a pattern name, it's enforced like one. Every entry above is paired with its cost rather than presented as a free win, and the conventional-vs-structural split tells you exactly which patterns you can lean your weight on and which ones want a green CI run before you trust them. That pairing — guarantee with its price, pattern with its enforcement level — is itself the most transferable thing in the design.

The takeaway
One pattern governs; the rest are consequences. Commit to a microkernel where per-agent behaviour is data the core consumes, add a poka-yoke rule that shared logic lives exactly once, and the Factory Method, two-phase Builder, Strategy, load-shedding, and graceful-drain patterns aren't decisions you make separately — they're the shape the constraint forces. The craft is in knowing, and saying, which of them the code enforces and which a test merely watches.
