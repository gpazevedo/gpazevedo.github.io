Every requirement has a test, and you can check it

"The tests cover all the requirements" is a sentence every code review says and nobody verifies. With an AI agent writing both the code and the tests, it becomes the sentence that matters most. requirement-traceability is a skill that makes it a command you run: one that fails, by name, when a requirement has no test.

I have been working on a set of agent skills in my fork of Matt Pocock's skills repo. The main chain goes from a grilling session to a spec (to-spec), from the spec to tickets (to-tickets), then test-first implementation (tdd, implement) and a two-axis review (code-review). One axis of that review asks whether the code matches the spec. And for a long time, the only way to answer "is every requirement tested?" was for a model to read the spec, read the tests, and form an opinion.

That opinion is usually right. It is also unrepeatable, and it gets worse exactly when you need it most: large specs, long sessions, many small tickets. A missing test for requirement 14 out of 22 is precisely the kind of thing attention skips. The gap was reported upstream as issue #341: decisions made during grilling were not traceable through spec, tickets and implementation. This skill closes the spec-to-test half of it.

The idea: one ID, carried end to end

Nothing here is new. Requirement traceability matrices are older than most of the people reading this. What is new is the cost: when an agent writes the spec, the tickets and the tests, keeping a stable ID attached to each requirement across all of them costs nothing, so there is no reason not to.

Each requirement gets an ID of the form <KEY>-<n>, like CPN-3. KEY is two to five uppercase letters chosen per spec. (A bare R3 would collide across specs and count another spec's test as coverage.) Four pieces carry the ID from the spec to the tests:

PieceWhere it livesShape
Requirement IDThe spec's user stories, after the list number1. CPN-1: As a shopper, I want to apply a coupon…
Seam tableThe spec's testing decisionsEach seam mapped to the IDs it covers, or a waived: <reason> row
Covers: lineEach ticket to-tickets producesCovers: CPN-1, CPN-4
Test tagThe start of the test nameit('CPN-3: rejects expired coupons', …)

A spec looks like this:

Requirement key: CPN

1. CPN-1: As a shopper, I want to apply a coupon at checkout, so that I pay less.
2. CPN-2: As a shopper, I want an expired coupon rejected with a reason, so that I know why it failed.
3. CPN-3: (dropped) As a shopper, I want to stack coupons.

The rules are few and strict. One behaviour per ID, so compound stories get split. IDs are never renumbered or reused. A withdrawn requirement keeps its ID and is marked (dropped), so an old test tagged CPN-3: shows up as stale instead of silently counting for something new.

The colon is load-bearing

The single most important design decision is one character. The ID is always followed by a colon, and every match anchors on the colon.

The reason is prefixes. CPN-1 is a prefix of CPN-10. Grep for CPN-1 and the moment someone writes a test for CPN-10, the untested CPN-1 looks covered. Nothing fails, nothing warns. You get a green check that is a lie, and silent false coverage is the one failure this whole convention exists to prevent.

A traceability check that can report "covered" when it is not is worse than no check, because now people stop looking.

So every grep, every runner filter and every comparison uses CPN-3:, never CPN-3. Runner filters quote it: -t "CPN-3:". The final comparison uses comm on whole lines with the colon included, which keeps CPN-1: and CPN-10: apart without any cleverness. One of the eval cases exists only to guard this: twelve requirements, where only CPN-1 is untested and its ID is a prefix of CPN-10, CPN-11 and CPN-12.

Gaps visible before code exists

Most coverage tools tell you about gaps after the code is written. The seam table moves that earlier. In the spec's testing decisions, each test seam lists the IDs it will cover:

| Seam | Requirement IDs |
| --- | --- |
| POST /checkout | CPN-1, CPN-2 |
| waived: needs a real payment provider | CPN-4 |

An ID that appears in no row is a gap you can see while the spec is still a draft. And an ID that genuinely will not be tested does not just disappear: it gets a waived: row with a reason. A requirement is waived explicitly, never dropped silently. Anyone reading the spec can see what is untested and why, and argue with it.

The Covers: line on tickets carries the same idea into the work breakdown. Every ID lands on exactly one ticket, and Covers: means the IDs this ticket makes fully testable, not the ones it touches. A requirement built across two slices goes on the later slice only. That sounds pedantic until you run the check per ticket: the first slice's check passes honestly, instead of failing on a requirement it was never meant to finish.

The check is a handful of greps

No tooling, no dependency, no config. The check is a short bash block inside the skill's SKILL.md. It builds three sorted lists and compares them:

  • defined: the IDs the spec's user stories declare, dropped ones excluded;
  • waived: the IDs in waived: rows of the seam table;
  • tagged: the IDs that start a quoted string in a test file.

The heart of it is three lines:

echo "UNTESTED (fails):";      comm -23 $T/defined $T/tagged | comm -23 - $T/waived
echo "UNDEFINED ID (warns):";  comm -13 $T/defined $T/tagged
echo "NO ID (warns):";         # tests whose name carries no ID

That yields three classes, with deliberately different weights:

ReportMeaningEffect
UntestedA defined, non-waived requirement no test namesFails
Undefined IDA test tagged with an ID the spec does not define, or has droppedWarns: a typo or a stale test
No IDA test with no ID at allWarns: scope creep, or a test worth tying to a requirement

Here is the check against the fixture the repo tests it with. The test file has a commented-out test for CPN-1 and a skipped one for CPN-5:

it('CPN-2: rejects an expired coupon with a reason', () => {});
it('CPN-10: accepts a lowercase coupon code', () => {});
it('CPN-99: does something the spec never asked for', () => {});
it('applies a discount', () => {});
// it('CPN-1: applies a coupon at checkout', () => {});
it.skip('CPN-5: records coupon analytics', () => {});

And the output:

UNTESTED (fails):
CPN-1:
CPN-5:
UNDEFINED ID (warns):
CPN-99:
NO ID (warns):
tests/checkout.test.ts:4:it('applies a discount', () => {});

Note what is not there. CPN-1 is untested even though CPN-10 has a test. CPN-4 has no test but is waived, so it is not reported. CPN-3 is dropped, so it is not expected. And the two switched-off tests do not count: a commented-out or skip/todo/xit test is not a passing test, so its requirement goes straight back on the untested list.

Known blind spot

The check reads text, so it errs in both directions, but unevenly. Switched-off tests err on the safe side (reported untested). The unsafe direction is narrow: a string that merely starts with an ID and a colon counts as a tag, even outside a test name. Keep IDs out of other string literals.

Because the check lives as prose-plus-code inside a skill, it could rot without anyone noticing. So the repo tests the block as the skill writes it: scripts/test-traceability-check.sh extracts the bash from SKILL.md, runs it against the fixture, and diffs the output against the recorded expectation. Edit the skill's text in a way that breaks the check, and that script goes red.

A repo that already has its own coverage tooling can name it in docs/agents/traceability.md with a Check command: line. It has the same contract: exit 1 when any ID is untested, and take IDs as trailing arguments to narrow the check to one ticket.

Where it runs

You rarely type /requirement-traceability. It is a cross-cutting reference that the main chain's skills consult once a spec carries IDs:

Spec
to-spec
Writes IDs on the user stories and the seam table, when asked.
Tickets
to-tickets
Puts a Covers: line on every ticket; each ID on exactly one.
Tests
tdd
Names each test with its ID and a colon (or the docstring's first line, in Python).
Gate
implement
Runs the gap check for the ticket's Covers: IDs before review.
✓ every ID tagged → review
✗ untested ID → named, before anyone reads the diff
Review
code-review
The Spec axis gets the tagged tests and the gap list, and judges whether each test asserts what its requirement says.

It is opt-in, and the switch is the spec itself. A spec with IDs turns everything above on. A spec without them changes nothing: no skill invents IDs, no ticket gets a Covers: line, and the chain runs as it always did. Pointed at a spec without IDs, the skill says so in one line and stops. There is no config and no setup question, which matters for a plugin that installs into other people's repos.

Presence is not correctness

The gap check proves that every requirement has a test that names it. It cannot tell whether that test asserts anything. it('CPN-2: rejects an expired coupon', () => {}) passes the check with an empty body. That is judgement, and the skill splits it into two tiers.

The first tier is an optional Judgement pass. A small bundled script, judge.mjs (Node, no packages), sends each requirement line and its tagged test excerpt (at most 60 lines) to Jev, a small fast model from TypeSafe, and sorts the results:

ClassMeaningWhat happens next
okHigh-confidence assertsNot re-read
flagHigh-confidence partial or unrelatedFix the test, or let review confirm
uncertainLow confidence, or no assertion call in the excerptRead by the agent
not judgedNo tagged testThe gap check owns presence

The second tier is code-review's Spec sub-agent, which then reads only the flagged and uncertain tests instead of all of them. That is the whole value of the pass: it narrows what the expensive reader has to read. It gates nothing. A flag is a lead, not a failure, and a test whose assertion hides inside a helper is never trusted as ok; it goes straight to a human-grade read.

Sending repo content to a third party from a skill that installs anywhere needed a rule, and it got an ADR. The pass runs only when both TYPESAFE_API_KEY is set in the environment and the repo's own docs/agents/traceability.md carries a Judgement: jev line. A key in your shell is not consent for every repo that shell touches; the opt-in line is per repo and visible to anyone reading it. If either is missing, the skill says "Judgement pass skipped" and behaves exactly as before. An outage costs the saving and nothing else.

What the evals say, honestly

The repo has a small claude plugin eval suite for this skill: a gap check with a commented-out test, the prefix collision, a spec without IDs left untouched, and the Judgement pass staying off without a key. Every case passes with the plugin.

Every case also passes without it. On fixtures this size, a current model answers "which requirement has no test" correctly on its own, and the evals do not show the skill adding accuracy. I think that is worth saying plainly rather than burying.

The evals are still worth running: they pin the behaviour against regressions, and they prove the skill fires when a spec has IDs and stays silent when it does not. But they do not measure where the convention actually pays:

  • Timing. IDs and the seam table exist before any code, so gaps show up in the spec review, not the code review.
  • Determinism. The check returns the same answer whatever the model's attention is doing that day. A grep does not get tired at story 14.
  • Scale. Twelve stories is easy for anyone. Sixty stories across nine tickets and three sessions is where "looks covered to me" starts to drift.

Building an eval that shows that honestly is open work. Along the way the suite taught two lessons about graders: one early delta of +1.00 turned out to be the fixture's empty test bodies being penalised, not the skill helping; and a grader that bundled two questions flipped between pass and fail on identical runs until it was cut back to one.

What it does not do

  • It starts at the spec. A decision from a grilling session that never became a user story has no ID and is invisible to the check. That half of issue #341 is still open.
  • It does not retrofit IDs onto existing specs. That is deliberately out of scope.
  • A passing check means every requirement has a test that names it. Whether that test is any good is the Judgement pass's lead and the reviewer's call.

That last point is the design in one sentence. The skill takes the part of "are the requirements covered?" that can be mechanical and makes it mechanical, so the judgement left over is smaller, better targeted, and spent on the question that actually needs it.
