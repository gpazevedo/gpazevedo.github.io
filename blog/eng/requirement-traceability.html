Every requirement has a test, and a check that proves it

When an agent writes the code, you stop reading every line. What you trust instead is the tests. So the question that decides whether agent-written code can be trusted is simple: do the tests cover every requirement, completely? requirement-traceability turns the first half of that question into a check you can run, and the second half into a narrow question a model can answer and you can review.

I built it as an addition to Matt Pocock's skills, one of the most widely used agentic engineering skill sets, and applied it to his spec, ticket and test-first flow. Nothing in it depends on that repo: the same traceability check fits any skill set that goes from a spec to tests.

The argument

Suppose a feature is well defined: its architecture, design and requirements have been written down and reviewed. Then a short chain of reasoning follows.

  1. The spec says what the feature must do. That is what the review was for.
  2. The tests check everything the spec says. Every requirement has tests, and together they check all of it, not part of it.
  3. Therefore, code that passes the tests does what the spec says, at every point the tests check. It does not matter who or what wrote it.

Step 1 is a human job, and teams already do it. Step 3 is what a CI run tells you. Tests sample behaviour, they do not prove it, so step 3 is only as strong as step 2. And step 2 is the weak link. Everyone says "the tests cover the requirements" in code review, and almost nobody verifies it. With a human writing the code, that gap is survivable, because the human also carries the intent in their head. With an agent writing the code, the tests are the only thing carrying the intent. If a requirement has no test, nothing stops the agent from getting it wrong, and nothing tells you it did.

Step 2 has two parts, and they are not equally checkable:

  • Presence: every requirement has at least one test. That is a fact about text, and a script can check it.
  • Completeness: those tests check all of what the requirement says. That is a judgement, and the best you can do is make it narrow, repeatable and visible.
The goal
  • Trace every test to its requirement. For any requirement, list every test that checks it. For any test, name the requirement it serves.
  • Guarantee every requirement has a test. A requirement with no test fails the check, by name, unless the spec explicitly waives it with a reason.
  • Judge whether each requirement is covered in full. An optional pass asks a fast model to read a requirement's tests and say whether they check all of it. It flags gaps for the agent to fix. It is a lead, not a gate.

The skill lives in my fork of Pocock's repo and plugs into its main flow: grill the idea, write a spec (/to-spec), split it into tickets (/to-tickets), build each ticket test-first (/implement, which drives /tdd), review (/code-review). Until now, the only answer to "is every requirement tested?" was a model reading the spec and the tests and forming an opinion. That opinion is usually right. It is also unrepeatable, and it fails exactly where you need it most: a missing test for requirement 14 of 22, in a long session, across many small tickets. The gap was reported upstream as issue #341 (which uses the skills' older names, /to-prd and /to-issues). This skill closes the spec-to-test half of it.

One ID, carried from spec to test

Requirement traceability is an old idea. What is new is the cost. When an agent writes the spec, the tickets and the tests, keeping a stable ID on each requirement costs nothing, so there is no reason not to.

Each requirement gets an ID like CPN-3: a key of two to five capital letters chosen per spec, then a number. (A bare R3 would collide across specs and count another spec's test as coverage.) The ID travels through four places:

PieceWhere it livesExample
Requirement IDThe spec's user stories1. CPN-1: As a shopper, I want to apply a coupon…
Seam tableThe spec's testing decisionsEach test seam mapped to the IDs it covers
Covers: lineEach ticketCovers: CPN-1, CPN-4
Test tagThe start of every test name (or the first docstring line)it('CPN-3: rejects expired coupons', …)

A spec with IDs looks like this:

Requirement key: CPN

1. CPN-1: As a shopper, I want to apply a coupon at checkout, so that I pay less.
2. CPN-2: As a shopper, I want an expired coupon rejected with a reason, so that I know why it failed.
3. CPN-3: (dropped) As a shopper, I want to stack coupons.

Three rules keep the IDs honest. One behaviour per ID, so compound stories get split. IDs are never renumbered or reused. A withdrawn requirement keeps its ID and is marked (dropped), so an old test tagged CPN-3: shows up as stale instead of quietly counting for something new.

One behaviour per ID does not mean one test per ID. A requirement usually needs several tests (the main case, edge cases, errors), and each carries the same tag:

it('CPN-2: rejects a coupon past its expiry date', () => { … });
it('CPN-2: rejects a coupon expiring today at 00:00', () => { … });
it('CPN-2: shows the expiry reason to the shopper', () => { … });

Where the language cannot put the ID in the test name, as with a Python function, it goes on the first line of the docstring:

def test_coupon_survives_refresh():
    """CPN-6: the coupon survives a page refresh."""

Grep for CPN-2: and you get every test for that requirement.

The colon does the heavy lifting

The most important design decision is a single character: the ID is always followed by a colon, and every search includes it.

Here is why. CPN-1 is a prefix of CPN-10. Search for CPN-1, and the moment someone writes a test for CPN-10, the untested CPN-1 looks covered. Nothing fails. Nothing warns. You get a green check that is a lie.

A coverage check that can say "covered" when it is not is worse than no check, because people stop looking.

So every search, every test-runner filter and every comparison uses CPN-1:, never CPN-1. One of the eval cases exists only to guard this: twelve requirements, where only CPN-1 is untested and CPN-10, CPN-11 and CPN-12 all have tests.

The colon guards the end of the ID. The start needs care too. A spec keyed PN would have its PN-2: match inside CPN-2: in a plain grep or a runner filter. The skill's own check anchors on the opening quote of the test name, so it is not fooled. For manual searches, pick keys that are not the tail of another key already in the repo. The skill lists the keys in use before you choose one.

Gaps you can see before any code exists

Most coverage tools report gaps after the code is written. This convention surfaces them earlier, in two places.

The seam table. In the spec's testing decisions, each test seam lists the requirements it will check:

SeamRequirement IDs
POST /checkoutCPN-1, CPN-2
waived: needs a real payment providerCPN-4

A requirement in no row is a gap, visible before a line of code. A requirement that genuinely will not be tested does not just vanish: it gets a waived: row with a reason. Requirements are waived in writing, never dropped in silence. Anyone reading the spec can see what is untested and why, and argue with it.

The Covers: line. Each ticket names the requirements it makes fully testable, not the ones it merely touches. A requirement built across two tickets goes on the later one. That sounds pedantic until you run the check per ticket: the first ticket passes honestly, instead of failing on a requirement it was never meant to finish.

The mapping from requirements to tickets is checked mechanically: every requirement on exactly one ticket, and no ticket naming a requirement the spec does not define. That is a count, not a judgement, so the agent fixes violations itself. It only asks you about a requirement that fits no ticket at all, because that is a real gap in how the work was split.

The check is one small script

No test framework plugin, no package, no config. The check is a small Node script that ships with the skill, check.mjs, with no dependencies. It knows JS/TS, pytest and Go tests without being told which runner you use. It builds three lists (the requirements the spec defines, the ones it waives, and the IDs found in test names) and compares them. It reports three things:

ReportMeaningEffect
UntestedA requirement that no test names, and that is not waivedFails
Undefined IDA test tagged with an ID the spec does not define, or has droppedWarns: a typo or a stale test
No IDA test with no ID at allWarns: scope creep, or a test worth tying to a requirement

Here it is on the repo's test fixture. The spec defines CPN-1 to CPN-6 and CPN-10, drops CPN-3 and waives CPN-4. There are two test files. tests/checkout.test.ts:

it('CPN-2: rejects an expired coupon with a reason', () => {});
it('CPN-10: accepts a lowercase coupon code', () => {});
it('CPN-99: does something the spec never asked for', () => {});
it('applies a discount', () => {});
// it('CPN-1: applies a coupon at checkout', () => {});
it.skip('CPN-5: records coupon analytics', () => {});
it.skip(
  'CPN-1: applies a coupon with a name long enough to wrap',
  () => {},
);

And tests/test_refresh.py:

def test_coupon_survives_refresh():
    """CPN-6: the coupon survives a page refresh."""
    assert True


def test_refresh_without_a_tag():
    assert True


@pytest.mark.skip
def test_records_analytics():
    """CPN-5: records coupon analytics."""
    assert True

The output:

UNTESTED (fails):
CPN-1:
CPN-5:
UNDEFINED ID (warns):
CPN-99:
NO ID (warns):
tests/checkout.test.ts:4:it('applies a discount', () => {});
tests/test_refresh.py:6:def test_refresh_without_a_tag():

Notice what the check refused to be fooled by. CPN-1 is untested even though CPN-10 has a test. One of its tests is commented out and the other is skipped, and neither is a passing test. The skipped one has a name long enough to wrap, so .skip( sits on the line above the tag; the check reads both lines. CPN-5 is untested for the same reason: one test is skipped with it.skip, the other with a @pytest.mark.skip decorator two lines above its docstring tag. CPN-6 is covered by its docstring tag in the Python file. CPN-4 has no test but is waived, so it is not reported, and dropped CPN-3 is not expected at all.

And test_refresh_without_a_tag gets a NO ID warning. A Python test cannot carry the ID in its name, so the check reads the docstring line after each def test_.

The check began as a handful of greps inside the skill's text. It moved to a script when the Jev pass below needed the same rules (which files are tests, which tests are skipped, where a test ends) and the two copies drifted the first time a rule changed. Now both read one set of rules.

Where it can still be wrong

The check reads text, not the language, so it can misread unusual code, but it errs toward the safe side. A switched-off test is reported untested, including a skip whose test name wraps onto the next line and a Python skip decorator. And an ID counts only where a test name sits (the first argument of it(, test( or t.Run(, or a pytest docstring's first line), so expect(label).toBe('CPN-1: shown') does not make an untested CPN-1 look covered. The one unsafe case left is other languages (Java, Kotlin and so on), where any quoted string that starts with an ID still counts. Keep IDs out of other string literals there.

Because the check is code the skill ships, it could break without anyone noticing. So the repo tests it: a script runs it on the fixture and compares the output and exit codes with the expected result. The same script tests the ticket-mapping check exactly as SKILL.md writes it, and a second suite pins the shared rules: where a tag counts, which tests are skipped, and which lines of each tagged test the Jev pass below would send. A repo with its own coverage tooling can plug it in instead, as long as it follows the same contract: exit 1 when any requirement is untested.

Having a test is not the same as being fully covered

The check proves that every requirement has at least one test that names it. It cannot tell whether those tests check everything the requirement asks for. it('CPN-2: rejects an expired coupon', () => {}) passes with an empty body. So does a test that checks the rejection but never the reason, when CPN-2 asks for both.

That is exactly the gap that matters for the argument above. A requirement that is only half tested is a requirement the agent can half implement, with every check green.

So there is an optional second pass. A small bundled script, judge.mjs, sends Jev, TypeSafe's new model built for fast, structured decisions with calibrated confidence, one question per requirement, along with every test tagged with it, cut from its tag to the end of that test: how much of the behaviour this requirement describes do these assertions check? Because the tests are judged together, a requirement split across three tests counts as fully covered when the three together check all of it. Jev answers with a verdict and a confidence:

ClassMeaningWhat happens next
okConfidently fully coveredNothing
flagConfidently only partly covered, or checking something elseThe agent adds the missing tests and asks again
uncertainLow confidence, or no assertion in the test itselfThe agent reads the tests itself
not judgedNo tagged testAlready reported by the check

Jev was in early access when I wrote this, so not every reader can run this pass yet. Without it, everything above still holds. You get the presence guarantee, and the completeness question falls back to /code-review, as it always did.

A flag is an instruction, not a report. The agent compares the requirement with its tests, names the behaviour no assertion checks, writes tests for it, and runs the pass again. If it reads the tests and genuinely judges them complete, it can disagree with Jev, but it has to say why.

The loop has a hard limit of three rounds. If a requirement is still flagged after the third, the agent stops and hands you the decision: which requirements, what it thinks is still unchecked, and what it tried. The requirement may be vague, the code may be hard to test at that seam, or Jev may simply be wrong. Those are calls for a person, and a fourth round only starts if you ask for it.

It is a lead, not a gate. No build fails on a Jev verdict alone. Its confidence also moves by about 0.03 between runs, so a requirement near the threshold can switch between ok and uncertain. That is why an uncertain row sends the agent to read the tests, and why /code-review still reads them against the spec afterwards.

Sending code to a third party, from a skill that installs into anyone's repo, needed a rule. The pass runs only when both a TYPESAFE_API_KEY is set and the repo itself opts in with a Judgement: jev line in docs/agents/traceability.md. A key in your shell is not consent for every repo that shell touches. Even then, only spec lines and the tagged tests themselves are sent. Each excerpt stops where its test ends, so helpers and neighbouring tests stay home, and a test longer than 200 lines is cut there and marked, so the agent reads it whole before acting on a flag. Without both, the skill says "Judgement pass skipped" and carries on as before.

How it fits the Pocock skills workflow

The integration is deliberately small: one extra command, and one line in each of two existing skills. /to-spec, /to-tickets and /code-review are not modified at all.

You turn it on by running /requirement-traceability once per feature, right after /to-tickets (or after /to-spec for a small build with no tickets). It adds the IDs, the seam table and the Covers: lines to what those skills wrote, checks the mapping, and shows you the result. From there, the flow runs as usual:

Idea
/grill-with-docs
Unchanged. Sharpens the idea; its decisions become the spec's user stories.
Spec
/to-spec
Unchanged. Writes the user stories and the testing decisions.
Tickets
/to-tickets
Unchanged. Slices the spec into tickets.
Trace
/requirement-traceability
The one added step. IDs on the stories, a seam table in the spec, a Covers: line on each ticket, and a check that every requirement lands on exactly one ticket.
Tests
/tdd (inside /implement)
One added line. Starts every test name with its requirement ID and a colon.
Gate
/implement
One added line. Runs the gap check for the ticket's requirements (all of them, on the last ticket) and fixes what it finds. If the repo opted in, runs the Jev pass and works through its flags.
✓ every requirement has a test (mechanical, blocks review)
✓ each requirement's tests judged to cover all of it (if the Jev pass is on; a lead, then your call)
✗ an untested requirement is named before anyone reads the diff
Review
/code-review
Unchanged. Reviews the diff against the spec, including whether the tests check what the requirements say.

Because each ticket carries its Covers: line, a fresh /implement session knows exactly which requirements it must prove, with none of the earlier conversation in context.

The whole spec is checked once, at the end. On the last ticket still open for the spec, /implement checks every requirement, not just that ticket's. This catches what per-ticket checks cannot: a ticket that never wrote its test, or a test that a later ticket removed. "Last open" relies on you closing tickets, which /implement never does itself. The flow already depends on that, but a forgotten close would skip the final check silently, so on every earlier ticket /implement names the tickets still open.

And it stays out of the way when you do not want it. A spec without IDs changes nothing: /tdd and /implement notice, say so in one line, and carry on as they always did. There is no config and no setup question.

What the evals say, honestly

The skill has a small claude plugin eval suite: a gap check with a commented-out test, the prefix collision, a spec without IDs left alone, the Jev pass staying off without a key, and annotating a spec and tickets. Every case passed with the plugin when I recorded the suite.

The four checking cases also pass without it. On fixtures this small, a current model answers "which requirement has no test?" correctly on its own. The evals do not show the skill making the model smarter, and I think that is worth saying plainly.

A later run exposed a hole in how I graded them. Every shell command inside the eval runner's sandbox failed with a bwrap error (anthropics/claude-code#97171), so no agent could run the check. They answered correctly anyway, by reading the files, and the graders passed them. The checking cases now require the check's own output in the run's transcript. Until that bug is fixed they score below 1.00, which is the honest result: the check did not run.

The annotation case is the one with a gap: 1.00 with the plugin, 0.00 without. It measures the convention, not intelligence. Asked to "make the spec traceable", the model without the skill does something sensible but different every time: REQ-1 IDs, Gherkin tags, a separate TRACEABILITY.md. None of that gives the next step a Covers: line to check against.

The Jev pass itself is not in the suite. The eval sandbox has no way to pass in an API key, so the pass cannot run there. I checked it by hand instead, against a set of hand-built cases (partial tests, missing assertions, an assertion hidden in a helper) and the no-key and no-opt-in paths. That is a smoke test, not a calibration. What the pass sends is tested offline, though: fixtures pin where each test ends in Python, TypeScript and Go, that a helper after the last test stays out, that a skipped test is never sent, and that a test past 200 lines is cut and marked.

Where the convention really pays is not something small evals measure:

  • Timing. Gaps show up when the spec is annotated, before any code, instead of in code review.
  • Determinism. The gap check gives the same answer whatever the model's attention is doing that day. A script does not get tired at story 14.
  • Scale. Twelve stories is easy for anyone. Sixty stories across nine tickets and three sessions is where "looks covered to me" starts to drift.

Building an eval that shows this honestly is still open work.

What this guarantees, and what it does not

Back to the argument. With this skill in the flow, the presence half of step 2 is no longer an opinion: every requirement has a test, checked mechanically, before review. The completeness half is still a judgement, but a narrow one, asked per requirement, with a loop that adds tests where they fall short and a hard stop that hands the rest to you. If the spec was reviewed and the gate passes, the code an agent wrote does what the spec says, at every point the tests check, to the extent the spec says it.

The remaining risk lives in the qualifiers of that sentence, so it is worth being precise about it:

  • The spec must be right. The skill checks code against the spec, not the spec against reality. A decision from a design session that never became a user story has no ID and is invisible to the check. That half of issue #341 is still open.
  • Unstated behaviour is unchecked. Performance, security and anything else the user stories do not say are outside the guarantee, unless you write them as requirements.
  • Tests must be honest. The same agent writes the tests and the code, so a test could drift toward what the code does rather than what the requirement says. The flow pushes back: /tdd writes each test before the code exists, Jev judges tests against the requirement text rather than the code, and review reads the diff against the spec. It reduces the risk; it does not remove it.
  • "Fully covered" is a model's judgement. Jev can be wrong in both directions, and its confidence moves a little between runs. It is a strong lead, backed by a three-round loop and your decision after that, not a proof. It never fails a build on its own.
  • Tests sample, they do not prove. Even tests that check every clause of a requirement check it on the inputs they chose.
  • IDs are added after the tickets are cut. This keeps /to-spec and /to-tickets untouched, at the price that requirements do not shape how the work is split.

None of this makes agent-written code risk-free. What it does is move the risk to where it belongs. The part of "are the requirements covered?" that can be mechanical becomes mechanical. The part that needs judgement gets a narrow, targeted question and a hard stop. And the part that needs a human (is the spec right?) stays with the human, which is where you wanted it all along.
