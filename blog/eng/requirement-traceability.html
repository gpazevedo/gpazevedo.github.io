Every requirement is covered by tests

"The tests cover all the requirements" is a sentence every code review says and nobody verifies. With an AI agent writing both the code and the tests, it becomes the sentence that matters most. requirement-traceability is a skill that makes it a command you run: one that fails, by name, when a requirement has no test.

The goal

Three things: two checked mechanically, one judged by a model:

  • Trace every test to its requirement. For any requirement in the spec, you can list every test that exercises it, and for any test, you can say which requirement it serves.
  • Guarantee every requirement is covered. A requirement with no test is reported by name and fails the check, unless the spec explicitly waives it with a reason.
  • Check that each requirement is covered in full. An optional pass has a small model, Jev, read all the tests tagged with a requirement and judge whether their assertions check the whole behaviour, only part of it, or something else.

I have been working on a set of agent skills in my fork of Matt Pocock's skills repo. The main chain goes from a grilling session to a spec (to-spec), from the spec to tickets (to-tickets), then test-first implementation (tdd, implement) and a two-axis review (code-review). One axis of that review asks whether the code matches the spec. And for a long time, the only way to answer "is every requirement tested?" was for a model to read the spec, read the tests, and form an opinion.

That opinion is usually right. It is also unrepeatable, and it gets worse exactly when you need it most: large specs, long sessions, many small tickets. A missing test for requirement 14 out of 22 is precisely the kind of thing attention skips. The gap was reported upstream as issue #341: decisions made during grilling were not traceable through spec, tickets and implementation. This skill closes the spec-to-test half of it. It is not a new flow: it plugs into the existing one, and the workflow section shows exactly where.

The idea: one ID, carried end to end

Nothing here is new. Requirement traceability matrices are older than most of the people reading this. What is new is the cost: when an agent writes the spec, the tickets and the tests, keeping a stable ID attached to each requirement across all of them costs nothing, so there is no reason not to.

Each requirement gets an ID of the form <KEY>-<n>, like CPN-3. KEY is two to five uppercase letters chosen per spec. (A bare R3 would collide across specs and count another spec's test as coverage.) Four pieces carry the ID from the spec to the tests:

PieceWhere it livesShape
Requirement IDThe spec's user stories, after the list number1. CPN-1: As a shopper, I want to apply a coupon…
Seam tableThe spec's testing decisionsEach seam mapped to the IDs it covers, or a waived: <reason> row
Covers: lineEach ticket, added by annotationCovers: CPN-1, CPN-4
Test tagThe start of the test nameit('CPN-3: rejects expired coupons', …), on every test for that requirement

A spec looks like this:

Requirement key: CPN

1. CPN-1: As a shopper, I want to apply a coupon at checkout, so that I pay less.
2. CPN-2: As a shopper, I want an expired coupon rejected with a reason, so that I know why it failed.
3. CPN-3: (dropped) As a shopper, I want to stack coupons.

The rules are few and strict. One behaviour per ID, so compound stories get split. IDs are never renumbered or reused. A withdrawn requirement keeps its ID and is marked (dropped), so an old test tagged CPN-3: shows up as stale instead of silently counting for something new.

One behaviour per ID does not mean one test per ID. A requirement usually needs several tests (the main case, edge cases, errors), and every one carries the same tag:

it('CPN-2: rejects a coupon past its expiry date', () => { … });
it('CPN-2: rejects a coupon expiring today at 00:00', () => { … });
it('CPN-2: shows the expiry reason to the shopper', () => { … });

The ID is the link from the requirement to all of its tests, and grepping for CPN-2: lists them.

The colon is load-bearing

The single most important design decision is one character. The ID is always followed by a colon, and every match anchors on the colon.

The reason is prefixes. CPN-1 is a prefix of CPN-10. Grep for CPN-1 and the moment someone writes a test for CPN-10, the untested CPN-1 looks covered. Nothing fails, nothing warns. You get a green check that is a lie, and silent false coverage is the one failure this whole convention exists to prevent.

A traceability check that can report "covered" when it is not is worse than no check, because now people stop looking.

So every grep, every runner filter and every comparison uses CPN-3:, never CPN-3. Runner filters quote it: -t "CPN-3:". The final comparison uses comm on whole lines with the colon included, which keeps CPN-1: and CPN-10: apart without any cleverness. One of the eval cases exists only to guard this: twelve requirements, where only CPN-1 is untested and its ID is a prefix of CPN-10, CPN-11 and CPN-12.

Gaps visible before code exists

Most coverage tools tell you about gaps after the code is written. The seam table moves that earlier. In the spec's testing decisions, each test seam lists the IDs it will cover:

SeamRequirement IDs
POST /checkoutCPN-1, CPN-2
waived: needs a real payment providerCPN-4

An ID that appears in no row is a gap you can see before any code exists. And an ID that genuinely will not be tested does not just disappear: it gets a waived: row with a reason. A requirement is waived explicitly, never dropped silently. Anyone reading the spec can see what is untested and why, and argue with it.

The Covers: line on tickets carries the same idea into the work breakdown. Every ID lands on exactly one ticket, and Covers: means the IDs this ticket makes fully testable, not the ones it touches. A requirement built across two slices goes on the later slice only. That sounds pedantic until you run the check per ticket: the first slice's check passes honestly, instead of failing on a requirement it was never meant to finish.

The check is a handful of greps

No tooling, no dependency, no config. The check is a short bash block inside the skill's SKILL.md. It builds three sorted lists and compares them:

  • defined: the IDs the spec's user stories declare, dropped ones excluded;
  • waived: the IDs in waived: rows of the seam table;
  • tagged: the IDs that start a quoted string in a test file.

The heart of it is three lines:

echo "UNTESTED (fails):";      comm -23 $T/defined $T/tagged | comm -23 - $T/waived
echo "UNDEFINED ID (warns):";  comm -13 $T/defined $T/tagged
echo "NO ID (warns):";         # tests whose name carries no ID

That yields three classes, with deliberately different weights:

ReportMeaningEffect
UntestedA defined, non-waived requirement no test namesFails
Undefined IDA test tagged with an ID the spec does not define, or has droppedWarns: a typo or a stale test
No IDA test with no ID at allWarns: scope creep, or a test worth tying to a requirement

Here is the check against the fixture the repo tests it with. The test file has a commented-out test for CPN-1 and a skipped one for CPN-5:

it('CPN-2: rejects an expired coupon with a reason', () => {});
it('CPN-10: accepts a lowercase coupon code', () => {});
it('CPN-99: does something the spec never asked for', () => {});
it('applies a discount', () => {});
// it('CPN-1: applies a coupon at checkout', () => {});
it.skip('CPN-5: records coupon analytics', () => {});

And the output:

UNTESTED (fails):
CPN-1:
CPN-5:
UNDEFINED ID (warns):
CPN-99:
NO ID (warns):
tests/checkout.test.ts:4:it('applies a discount', () => {});

Note what is not there. CPN-1 is untested even though CPN-10 has a test. CPN-4 has no test but is waived, so it is not reported. CPN-3 is dropped, so it is not expected. And the two switched-off tests do not count: a commented-out or skip/todo/xit test is not a passing test, so its requirement goes straight back on the untested list.

Known blind spot

The check reads text, so it errs in both directions, but unevenly. Switched-off tests err on the safe side (reported untested). The unsafe direction is narrow: a string that merely starts with an ID and a colon counts as a tag, even outside a test name. Keep IDs out of other string literals.

Because the check lives as prose-plus-code inside a skill, it could rot without anyone noticing. So the repo tests the block as the skill writes it: scripts/test-traceability-check.sh extracts the bash from SKILL.md, runs it against the fixture, and diffs the output against the recorded expectation. Edit the skill's text in a way that breaks the check, and that script goes red.

A repo that already has its own coverage tooling can name it in docs/agents/traceability.md with a Check command: line. It has the same contract: exit 1 when any ID is untested, and take IDs as trailing arguments to narrow the check to one ticket.

Using it in the Pocock skills workflow

Matt Pocock's skills already have a main flow from idea to shipped code: grill the idea, write a spec, split it into tickets, implement each ticket test-first, review. Traceability rides on that flow with the smallest footprint I could find: one extra command, and one line in each of two existing skills. /to-spec, /to-tickets and /code-review are not modified at all.

Turn it on by running /requirement-traceability once per feature, right after /to-tickets. It annotates what the two earlier skills wrote: an ID on each user story, the seam table in the spec, and a Covers: line on each ticket. It then shows you the annotated lines and asks you to confirm that every requirement lands on exactly one ticket. For a one-session build with no tickets, run it after /to-spec instead.

Then run the flow as usual. From here the IDs carry themselves:

Idea
/grill-with-docs
Unchanged. Sharpens the idea; its decisions become the spec's user stories.
Spec
/to-spec
Unchanged. Writes the user stories and the testing decisions, with no IDs.
Tickets
/to-tickets
Unchanged. Slices the spec into tracer-bullet tickets.
Trace
/requirement-traceability
The one added step. Puts an ID on each story, a seam table in the spec and a Covers: line on each ticket. Requirements no seam or ticket covers are visible here, before any code.
Tests
/tdd (inside /implement)
One added line. Confirms the seam table, then names each test with its ID and a colon (or the docstring's first line, in Python).
Gate

One added line. Runs the gap check for the ticket's Covers: IDs, then the Jev pass for the same IDs, and fixes gaps and partial coverage before review (at most three Jev rounds, then it asks you).

Review
/code-review
Unchanged. Reviews the diff against the spec as it always did, on tests that already passed the gate.

The flow's own context rules still apply: keep grilling, spec and tickets in one session, then /clear between tickets and run /implement on each. Because each ticket carries its Covers: line, a fresh /implement session knows exactly which requirements it must prove, with none of the earlier conversation in context.

Check the whole spec whenever you like. The per-ticket checks cover one slice each. Before a release, or after the last ticket, run /requirement-traceability against the spec without narrowing it to a ticket, and you get the full untested, undefined and no-ID report for the feature.

It is opt-in, and the switch is the spec itself. A spec without IDs changes nothing: nothing invents IDs unless you run the annotation, no ticket gets a Covers: line, and the chain runs as it always did. When /tdd or /implement meet a spec without IDs, the skill says so in one line and they carry on as before. There is no config and no setup question, which matters for a plugin that installs into other people's repos.

Present is not the same as fully covered

The gap check proves that every requirement has at least one test that names it. It cannot tell whether those tests check everything the requirement asks for. it('CPN-2: rejects an expired coupon', () => {}) passes the check with an empty body. So does a test that checks the rejection but never the reason, when CPN-2 asks for both. Telling full coverage from partial coverage takes judgement, and the skill splits it into two tiers.

The first tier is an optional Judgement pass. A small bundled script, judge.mjs (Node, no packages), sends Jev, a small fast model from TypeSafe, one call per requirement: the requirement line plus every test tagged with its ID (an excerpt of up to 60 lines each). It asks one question: how much of the behaviour the requirement describes do these assertions check? Jev answers asserts (all of it), partial (part of it, with another part unchecked) or unrelated (something else, or nothing), with a confidence. Because the tests are judged together, a requirement split across three tests counts as fully covered when the three together check all of it. The script sorts the answers:

ClassMeaningWhat happens next
okHigh-confidence asserts: fully coveredNot re-read
flagHigh-confidence partial or unrelated: not fully coveredThe agent adds tests for the missing part and re-runs the pass, up to three rounds, then asks you
uncertainLow confidence, or no assertion call in the excerptRead by the agent
not judgedNo tagged testThe gap check owns presence

A flag is not just a report. The agent is told which requirements are not fully covered and has to act on them: compare the requirement with its tests, name the behaviour no assertion checks, add tests for it, and run the pass again for those IDs. Only when it reads the tests and still judges them complete does it leave the flag for review, saying why.

The loop has a hard cap: at most three rounds of adding tests and re-running the pass. If a requirement is still flagged after the third, the agent stops and hands the decision to you, with each remaining ID, the behaviour it judges still unchecked, and what it tried. The requirement may be vague, the code may be hard to test at that seam, or Jev may simply be wrong; those are calls for a person, and a fourth round only starts if you ask for one.

The second tier is code-review's Spec sub-agent, which reviews the tests against the spec as it always has, but now on requirements the gate already sent back until they were fully covered. The review itself is unchanged; it just starts from tests that already passed the gate. The pass still fails no build, and a test whose assertion hides inside a helper is never trusted as ok; it goes straight to a human-grade read.

Sending repo content to a third party from a skill that installs anywhere needed a rule, and it got an ADR. The pass runs only when both TYPESAFE_API_KEY is set in the environment and the repo's own docs/agents/traceability.md carries a Judgement: jev line. A key in your shell is not consent for every repo that shell touches; the opt-in line is per repo and visible to anyone reading it. If either is missing, the skill says "Judgement pass skipped" and behaves exactly as before. An outage costs the saving and nothing else.

What the evals say, honestly

The repo has a small claude plugin eval suite for this skill: a gap check with a commented-out test, the prefix collision, a spec without IDs left untouched, the Judgement pass staying off without a key, and annotating a spec and tickets that carry no IDs. Every case passes with the plugin.

The four checking cases also pass without it. On fixtures this size, a current model answers "which requirement has no test" correctly on its own, and the evals do not show the skill adding accuracy. I think that is worth saying plainly rather than burying.

The annotation case is the one with a gap (1.00 with the plugin, 0.00 without), and it measures the convention, not intelligence. Asked to make a spec traceable, the model without the skill does something sensible but different every run: REQ-1 IDs, Gherkin tags, a separate TRACEABILITY.md. None of those give /implement a Covers: line to narrow its check by.

The evals are still worth running: they pin the behaviour against regressions, and they prove the skill fires when a spec has IDs, annotates when asked, and stays silent otherwise. But they do not measure where the convention actually pays:

  • Timing. IDs and the seam table exist before any code, so gaps show up when you confirm the annotation, not in the code review.
  • Determinism. The check returns the same answer whatever the model's attention is doing that day. A grep does not get tired at story 14.
  • Scale. Twelve stories is easy for anyone. Sixty stories across nine tickets and three sessions is where "looks covered to me" starts to drift.

Building an eval that shows that honestly is open work. Along the way the suite taught two lessons about graders: one early delta of +1.00 turned out to be the fixture's empty test bodies being penalised, not the skill helping; and a grader that bundled two questions flipped between pass and fail on identical runs until it was cut back to one.

What it does not do

  • It starts at the spec. A decision from a grilling session that never became a user story has no ID and is invisible to the check. That half of issue #341 is still open.
  • It annotates a spec and tickets you have just written, before any /implement. Retrofitting IDs onto a spec whose code already exists is out of scope.
  • IDs are assigned after the spec is sliced into tickets, not during. A requirement built across two tickets lands on the later one, but it does not shape how the tickets are cut. That is the price of leaving /to-spec and /to-tickets untouched.
  • A passing gap check means every requirement has at least one test that names it. Whether those tests cover the requirement in full is Jev's verdict: a model's judgement that sends a requirement back for more tests, three rounds at most, and then hands the call to you. It never fails a build.

That last point is the design in one sentence. The skill takes the part of "are the requirements covered?" that can be mechanical and makes it mechanical, so the judgement left over is smaller, better targeted, and spent on the question that actually needs it.
