How an orchestrator-driven AI SDLC built a real-time AI voice app

I built Supplier Line, a real-time voice agent on Amazon Nova 2 Sonic reachable from a browser or an Amazon Connect call, without writing its code. One Claude orchestrator, working in Herdr terminal panes, ran 23 work streams from a written plan, each agent test-first in its own git worktree. The process is worth copying for what it caught. Three agents reported success on work that did not work, and the orchestrator found out by running it. With every test green, a final review found seven defects, each of which would have broken the first deploy. And a human check found that the Lambda that tears down my deploys had failed on all 81 of its runs. This post lays out the loop, the gates and the human checkpoints that caught them, and what I would change, so you can use them on your own agent-built projects.

The app answers one question: a supplier reads out a purchase-order code and hears its status. What it does on a call, and which component does what, is in the companion post; the code is on GitHub. This post is about how it was built. It made a good test of an AI-driven process because much of it, from barge-in to IAM, can only be verified against the real model and the real cloud.

From a conversation to a plan agents could run

The plan started in a conversation with Claude on September 26. I wanted a voice app to go alongside Buyer Team, so that suppliers could ask about a purchase order by phone and hear its status. We first wrote a full design, then reviewed it and cut it down to a two-day slice. The slice kept one headline, precise barge-in proven by traces. The review also produced findings that shaped the build, such as Amazon Connect keeping its own orchestration when Sonic is the speech model. Every stream got a row with its output, a "done when" test and a skill, for most streams Matt Pocock's test-driven development skill. The plan ended with four trace checks that decide acceptance; the build grew them to six.

In a second conversation I turned that plan into something agents could run. We wrote CLAUDE.md as the shared brief: the fixed decisions, the out-of-scope list, the trace contract and an honesty rule for the README. Then we worked through how to run it. Herdr would keep parallel agents visible. Pure-code streams could run anywhere, but anything that needed Bedrock, my ears or the Connect console stayed with me. Claude Managed Agents would add setup without speeding up the critical path, so I left it out. The most useful idea from that session was to match the model to the stream. That became the model column, and the plan grew to 23 streams as the build taught me more.

The result was two files. docs/build-plan.md gives each work stream its output, its done criteria, its skill and its model. CLAUDE.md holds the rules every agent reads first: which AWS profile to use, never deploy, never skip a hook, stop and report on any access-denied error. The model column is a budget decision: Haiku 4.5 for mechanical work, Sonnet 5 by default, and Opus 5.5 for the orchestrator, the real-time audio streams, IAM and Connect, the reaper that enforces my consent, and the final review. Opus costs twice what Sonnet does, so escalating a failing stream is cheap next to a broken demo.

The loop

The orchestrator never writes feature code. For each stream it follows the same eight steps, with up to four agents running at once, each visible in its own Herdr pane.

  1. Brief. The stream's row from the plan, plus anything learned since.
  2. Isolate. A git worktree and branch, a sibling pane, and an agent on the stream's model.
  3. Build. Test-first, root cause before any fix, checked against real Bedrock.
  4. Commit. pre-commit hooks: formatting, linting, secret scanning, workflow and config checks.
  5. Verify. The orchestrator re-runs the tests and trace checks, and its own replay against real Bedrock.
  6. Merge into main, in plan order.
  7. Push. pre-push hooks: typecheck, tests including an axe accessibility check, CDK checks, trace checks.
  8. CI. The same hooks on GitHub, plus the ARM64 image build and a health check, with no AWS credentials.

Step 5 is the one that earns its keep. It is the only step where someone other than the agent runs the agent's work.

Three streams reported success on work that did not work. Each was caught because the orchestrator ran the thing instead of reading the report.

So the orchestrator's check is written from the outside: the command the workflow uses, the audio the caller hears, the CI runner rather than the notebook. The third row also has a lesson for the orchestrator: it merged before CI had seen that branch and turned main red for a few minutes. CI is a gate, so it belongs before the merge.

Prove the cause, measure the change

Every audio stream is done only when recorded caller clips, replayed against real Bedrock, pass: the answer spoken word for word, no caller audio lost at a rotation, and every trace passing six automated checks. Two rules sat on top of that: prove the root cause before fixing, and keep only changes you can measure.

  • A bug hiding behind old fixtures. After I re-recorded the caller clips with less noise, session rotation stopped working. I pause after "purchase order P O", so Sonic started replying and I talked over it, and the code that tracks when a reply is complete kept waiting for the interrupted one. The old clips never caused a barge-in, so the bug had been there all along.
  • A guess stopped. When a call looked up the wrong code, the agent logged every tool call next to the caller's transcript before changing anything. Sonic had ended my turn in the pause between digit groups and filled in the rest. Less sensitive turn detection fixed it. AWS's guidance suggests temperature 0 for tool calls; the agent measured it, saw no gain, and kept 0.7.
  • My own diagnosis overturned. Codes were misheard only after a rotation, so I asked for a rotation fix. The agent dumped every event each connection received, found them identical, and reproduced the bug on a connection that had never rotated. The cause was the paused "dash" in "P O, dash, one zero four eight two". The agent stopped saying "dash", the host began holding lookups for digits not yet spoken, and I re-recorded the clip the way callers would now speak. The agent's wording shapes the caller's wording.

The checkpoints only I could pass

The plan has five human checkpoints, H0 to H4. Agents cannot pass them, by design: they need my credentials, my ears or my approval.

The listening check, H2, mattered most during the build. Every automated check was green, and the first thing I said on the softphone was looked up as PO-12345, the example code written into the system prompt. No replay had ever produced it. Recording the clips was a checkpoint too: the first take had room noise only 10 dB below my voice, which would have made every later audio test partly a test of the room.

Design that saved the demo

Every purchase-order code carries a check digit, and any single wrong digit fails it. So a misheard code never read out another order's data: the agent asked me to repeat instead. It happened in the live test too, when one request was heard as PO-13345. A later rule, enforced by a trace check, made sure order data is never spoken without a lookup.

The most useful checkpoint was the dullest one: a reaper self-test, a tiny stack tagged to expire in five minutes, and two emails to watch for. Neither came. The reaper had failed on all 81 runs since the first deploy: it lists stacks with a call AWS authorises as ListStacks, and its role only had DescribeStacks. The unit tests mocked AWS, and cdk-nag flags permissions that are too broad, not missing ones. The emails had a second cause: I had never confirmed the alert subscription, and the topic's HTTPS-only policy blocked the alarm from publishing anyway. The guardrail that enforces my consent had never worked, and only a human running it end to end, then asking "where are my emails?", found out. A safety net is not tested until you have watched it catch something.

The final review found what no check could

The plan ends with a review stream on Opus: security, least-privilege IAM, the consent controls, accessibility, correctness. Every test passed and CI was green, and it still found seven blocking defects, each of which would have broken the first real deploy: the image crashed at startup because files were missing from it; the host's role granted an IAM action that does not exist, which IAM accepts without complaint; the host could not start Connect calls outside my developer profile; deployed traces went nowhere and the smoke test checked old files; the web pages were never uploaded; and one unauthenticated request crashed the host.

They share a pattern with the reaper. Local tests run with broad developer credentials, mocked AWS clients and files on disk, so whatever exists only in the deployed environment stays invisible until someone reads the code against what AWS actually does. CI now builds the image and waits for it to report healthy, and the templates carry tests for the exact permissions each role gets.

Three runs to a green deploy

H3 is the first real deploy: I start demo-up, approve it, and its smoke test replays six caller scenarios against the running app, including a connection rotation. Before it even started, the nightly teardown job could not log in to AWS, because GitHub now puts numeric owner and repo IDs in its identity tokens and our roles trusted the old format. Then the first smoke test was turned away: the access code in GitHub did not match the one in AWS.

The first real run passed four of six scenarios, and the failures were real model behaviour: once Sonic looked an order up and never spoke the result, and once, after a rotation, it answered from memory. The host now nudges Sonic with a text message when a result stays unspoken, and holds back order details spoken without a lookup. The second run passed five of six, and its trace showed a garbled answer. The agent transcribed the recording of what the caller heard, and it was perfect; the bug was in how the trace matched Sonic's sentence confirmations. The third run was green, and its six traces are now fixtures that CI checks on every push. Rare model behaviour only shows up against the real service, and the audio, not the log, is the ground truth.

Guardrails that held

  • A denied command stops the agent. One agent's first step was a gh api call to read AWS's sample code, and it was denied. It stopped and asked instead of trying another route; the orchestrator fetched the sample and handed it over.
  • The orchestrator is fenced too. When it tried to start an agent with automatic approvals, the permission layer blocked it, because I had not agreed to that.
  • Deploys need me. The app stack deploys only through a workflow I approve in a GitHub Environment, for one to eight hours, and the reaper deletes it at expiry, now that it demonstrably works.
  • Pushing is delegated, with limits. A stream that passes the orchestrator's own verification merges and pushes without asking. Human checkpoints and anything touching infrastructure still wait for me.

What I would change

The loop is not fast. The stream that fixed the misheard codes ran for almost four hours through nine versions, because each change was measured against real Bedrock before the next. It paid off, and a few things would make it cheaper next time:

  • Deploy something real early. A throwaway deploy after the first phase would have surfaced most of the review's findings a day earlier, before they piled up.
  • Get to the human checkpoints sooner. Ten minutes on a real mic found what hours of replays did not.
  • Run CI on the branch before merging. It is the only check that runs somewhere other than my notebook.
  • Size the model to the risk, not the task's shape. Phrase capture looked mechanical but needed a live model, and Haiku faked it.

The app is built. All 23 streams are merged, the first real deploy passed its smoke test on the third run, and its traces are checked by CI on every push. The only checkpoint left is recording the demo video.
