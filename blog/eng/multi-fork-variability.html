Dozens of forks, one codebase: model every variant, then prove nothing changed

The inventory says what each fork does. This part decides how one codebase will do all of it, and how you'll know it does.

TL;DR

The problem. Part 1 produced a concept × fork matrix: every behavior, and where each fork differs. One codebase now has to reproduce every difference a tenant still uses, switchable per tenant at runtime, without any tenant noticing the move.

What you get. A variability model whose variants carry concrete values, intent and usage evidence. Each kind of difference maps to the smallest mechanism that fits it, variants that leave work in flight get an explicit switch strategy, and data-model differences follow a schema-first rule. Then the proof: mirror live reads, replay captured writes offline, filter the noise the way Diffy does, and put guardrails around the AI doing the refactoring.

Why it's worth your time. Mirroring and replay look interchangeable and aren't: a mirrored write executes twice. And an AI that refactors code and edits the tests in the same pull request can "prove" a regression correct.

Status. A design, written before it was run, like the rest of the series.

Part 2 of 3. After the inventory; Part 3 covers cutting tenants over and the governance that stops the forks from growing back.

An inventory is a description. Nobody can deploy a description. Between the matrix from Part 1 and a tenant running on the unified code, three questions need answers: what exactly has to vary, how the code will vary it, and how anyone will know the tenant's behavior survived.

The first two are design. The third is the one that decides whether the program is trusted, and it has to start on day one, because the evidence takes weeks to collect.

From concepts to variants

The inventory's real purpose is to list every distinct behavior the unified code must reproduce. For each concept, the versions across all forks are grouped into variants, and each variant records enough to design its variation point:

FieldWhat it holdsWhy

Two details are easy to miss. A missing concept is a variant too: the feature turned off. And because AI writes part of this record, every record carries the pinned model and the prompt version that produced it. An illustrative record:

concept: reminders.follow-up-cadence          # stable ID from the hierarchy
variation_point: config.value
variants:
  - id: v1                                    # the base's behavior
    value: { days: 7 }
    forks: [base, fork-a, fork-c]
  - id: v2
    value: { days: 15 }
    forks: [fork-b]
    fork_intent: contractual
    usage: { tenants: 3, hits_30d: 18240 }
  - id: v0                                    # concept absent: feature off
    forks: [fork-d]
    usage: { tenants: 1 }
stateful: true
switch_strategy: drain
provenance: { model: pinned-model-id, prompt_version: v3 }

Variants that leave work in flight

Some variants leave work in progress in their own shape: an approval halfway through its steps, a reminder cycle already scheduled, a cache built by the old code, rows in the old data layout. Switching a tenant to another variant mid-flight can break that work. So every variant is marked stateful or stateless, and every stateful variant gets exactly one switch strategy:

Drain
New work goes to the new variant; work already in flight finishes on the old one. Simplest when in-flight work ends on its own.
Migrate
Convert the in-flight state at the switch, with a tested conversion. For work that would never drain, like long-lived schedules.
Version
Each record remembers which variant created it, and both variants stay readable until the old records expire.

The strategy is recorded with the variant, so it's applied the same way at every switch: a per-variant flip, a full cutover or a switch back. Switching back is the case that bites: the old path has to be able to read whatever the new path wrote while it was on.

Reuse this

Record differences as values, not adjectives ("7 vs. 15 days", not "the cadence differs"), and give every stateful variant one named switch strategy: drain, migrate or version. The first makes configuration fall out of the inventory; the second makes switching back a plan instead of a hope.

Pick the smallest mechanism that fits

A small kit of standard mechanisms covers every variant, and each kind of difference maps to one of them. For each difference, use the lowest rung that solves it; each rung up brings more power, more risk and more cost.

RungKind of differenceMechanismTools
1A different valueConfiguration resolved per tenant@ConfigurationProperties, a config service
2Modules a customer boughtEntitlements, kept separate from flagsA small service of your own
3Behavior on or offFeature flag evaluated with the tenant as contextOpenFeature as the API
4Custom fields and validationsMetadataJSON columns plus JSON Schema
5Rules and workflows that varyA rules or workflow engineDMN, Drools, Camunda, Flowable, Temporal
6Alternative logic; a different external systemStrategy interface, or ports and adapters, chosen per tenantSpring Plugin's PluginRegistry
7Extra steps; truly bespoke codeExtension points, domain events a tenant module listens to, pluginsCustomer modules in the build; PF4J
—A different data modelAdditive superset schema, extension tables or JSON attributesApplied before the fork's tenants move (below)

A feature flag is not configuration. Permanent differences go into entitlements, configuration or extension points; flags are short-lived and have an owner.

Runtime, not startup

In a shared deployment, every mechanism must resolve per tenant at runtime. That rules out two Spring favorites: @Profile and @ConditionalOnProperty decide once, at startup, so they can't select variants when one process serves every tenant. What works instead:

  • Resolve the tenant once (JWT, subdomain or header) and propagate it with a ScopedValue or ThreadLocal, including into async work and messaging.
  • Select per request: a PluginRegistry picks the tenant's implementation, falling back to the core behavior.
  • Use domain events so extensions can react without the core knowing they exist.
  • Enforce the boundary in CI: ArchUnit fails the build if the core depends on an extension; japicmp or revapi versions the extension API; every extension has contract tests.

Prove each mechanism end to end on one real variant before applying it widely. Design each concept's variation point when it's first touched, for all the variants the inventory found, even if only some are implemented now.

Anti-patterns

if (tenantId.equals("acme")) scattered through the core. Permanent flags with no owner. A plugin per customer for what configuration solves. A generic do-it-yourself platform. Customer scripts without a sandbox. Each one rebuilds the fork, just inside a single branch.

Keep the number of variation points low

  • Delete variants no tenant uses.
  • Push the business to standardize where variants differ trivially. Some customizations are cheaper to negotiate away than to preserve.
  • Group the remaining variation into a small number of tenant profiles.
  • Test only the configurations that exist (one per fork or tenant group), not every combination of flags.
  • But test the transitions. Switching one variant at a time creates combinations no tenant ever ran. Flag every pair of concepts whose call slices write the same entity fields; a person reviews how they interact, and their transitional combinations get explicit tests.
  • Run every tenant profile inside one booted @SpringBootTest context, resolved at runtime through the tenant context. @ActiveProfiles, mocked beans or per-tenant property overrides each force a new context, so CI time would grow with every profile.
Reuse this

Map each kind of difference to one standard mechanism and climb the ladder only when the lower rung fails. Then make the test suite share a single Spring context across tenant profiles, or the price of every new profile is paid in CI minutes forever.

Data-model variants: conform the schema before routing

Code variants are the easy half. Forks also changed their schemas, and those differences block unification. Find them by building, not reading:

  • Apply each fork's Flyway or Liquibase migrations to an empty database with Testcontainers.
  • Diff the resulting schemas (Atlas schema diff or SchemaCrawler).
  • Diff them against the real production schemas too, read-only. Manual hotfixes often leave production apart from the migrations.

Flag the conflicts: the same table or column with a different type or meaning in different forks. Expect migration version numbers to collide, too; forks almost certainly reused them, so their migration histories can't be merged. Define the unified target schema, write one migration per fork that brings its database there, and re-baseline every database at a new common version.

The order matters. Hibernate builds one entity model at startup, shared by every tenant, so each tenant's database must already satisfy the base's model when its tenants move. The per-fork migration gets there with additive changes only: new columns are nullable or defaulted, so the fork's code can still write during the fallback window. Validating the base's entity model against each tenant's database is a cutover gate. Moving data between databases is a separate, later decision.

Data-model variants themselves use expand/contract: add the new structure beside the old, backfill or dual-write, switch reads per tenant, then remove the old structure. Changes stay additive while any fallback window is open.

Proof, part one: which variants are actually used

Production traffic and logs serve two purposes: showing which variants are really used, and proving behavior was preserved. Start capturing immediately. Usage evidence needs weeks of data, and it's the cheapest way to shrink the program.

  • Entry-point usage comes from access logs, job execution logs and consumer metrics: hit counts per entry point per tenant. That marks each unit and variant used or unused.
  • Variants inside a method (a branch, not an entry point) need line-level evidence. Run a JaCoCo agent on one production instance per fork for a few weeks; its coverage maps straight onto the fingerprinted methods from Part 1.

Proof, part two: mirror reads, replay writes

Two techniques sound the same and aren't. Mirroring sends a copy of live traffic to the new build as it happens. Replay runs captured traffic later, against a snapshot. They aren't interchangeable, because a mirrored write executes a second time.

  • Live mirroring, reads only. The shadow deployment connects with a read-only database role and its outbound calls are stubbed. A "read" that secretly writes fails loudly instead of changing data.
  • Session replay for writes. Capture each tenant's requests and consumed messages in their original order, and replay them against a snapshot taken when capture began. IDs that one response created and the next request sent are rewritten to the IDs the replay created; GoReplay's middleware sees both responses, so it can do that.
  • Scheduled jobs: compare the database state after a run on a copy of the snapshot.
  • Filter the noise: replay against the original fork twice and the new build once. Whatever differs between the two original runs (timestamps, IDs, ordering) is noise and is ignored. This is the method Twitter's Diffy popularized.
  • Remove randomness: inject a fixed Clock and deterministic ID generators in replay mode.
  • Compare outbound calls: stand in for external systems with WireMock recordings and verify the calls. An email that stops being sent is a behavior change. Recording needs an egress proxy or a mesh sidecar on the fork deployments, which is an infrastructure change; budget for TLS interception and for HTTP clients that ignore proxy settings.
  • Compare database effects, not just responses, by replaying against snapshot copies.
  • Protect personal data: mask it before it leaves production. Privacy law (GDPR, LGPD and the like) applies to recorded traffic.

Running both code paths inside production, the Scientist pattern, is limited to side-effect-free logic. Rolling back a transaction doesn't unsend messages or emails, or undo cache writes and consumed sequence values.

Where traffic doesn't reach, characterization tests fill the gap: golden-master snapshots with ApprovalTests, Testcontainers for the database, and recorded stand-ins for external systems. For legacy integrations that are hard to repoint, a proxy-based tool like Hoverfly captures real traffic without changing the hosts the code calls. Many integrations aren't HTTP at all (files, SFTP, database views); those get Testcontainers and golden files instead.

Reuse this

Mirror reads live; replay writes offline against a snapshot. Give the shadow a read-only database role so a mislabeled read fails loudly, and run the original twice so its own nondeterminism defines what "different" means.

Proof, part three: guardrails for the AI doing the refactoring

In this playbook, the base absorbs every variant, and Codex does much of that refactoring: it reads a fork's implementation and reimplements it as a variant in the base, one variant per pull request, in a worktree with write access, with replay as a required CI check and a person reviewing each PR. Nothing is merged from the forks; they become the reference Codex reads and the oracle replay compares against.

The biggest risk isn't bad code. It's an agent that changes the tests along with the code and so "proves" a regression is correct. Five rules, for AGENTS.md and CI:

1
Frozen tests
Characterization and parity tests are read-only for the agent. A PR that changes production code and frozen tests fails, or needs separate approval through CODEOWNERS.
2
Declared scope
Each task declares the paths it may touch. CI fails the PR if the diff goes outside them.
3
Behavior spec first
Before an extraction, record the invariants tests often miss (authorization, idempotency, external contracts, performance budgets), and test each: an authorization matrix, replay and retry tests, a JMH or Gatling baseline.
4
Evidence in every PR
Which suites ran, the behavioral diff (none, or explained), the performance comparison. Reviewers check the evidence, not just the code.
5
Behavior changes in their own PR
If convergence needs a behavior change, such as merging two customers' variants, it gets its own PR with a decision record. Never inside a refactoring.

Three complements make the safety net stronger than it looks:

  • Property-based tests (jqwik in Java) for mapping rules. Golden masters pin the examples you observed; properties check the rule for any input.
  • Mutation testing (Pitest) for every AI-generated test. A large suite of weak tests is false confidence.
  • No automatic test regeneration during the migration. Tools that "maintain" tests after a change record the regression as the new behavior.
!
The trap in generated unit tests

Unit-level test generators such as Diffblue Cover capture what the code does today, which is useful for logic hotspots. But unit tests are tied to code structure, so they break en masse exactly when you extract the extension points this program exists to create.

⇄
The cross-fork trick

Generate tests on the base and run them against each fork. Test failures show behavioral divergence; compile failures show structural divergence. A cheap second opinion on the inventory.

What this part adds up to

By now each difference has a value, an intent, a usage count, a mechanism and, if it's stateful, a switch strategy. Each fork's database is on the path to the base's schema by additive steps. Usage evidence has been accumulating since day one, and a replay harness can compare any tenant's real sessions, on the fork and on the base, down to the emails it sends.

What's left is moving people's production systems. Part 3 covers the cutover: the prerequisites of a shared deployment, the tenant tiers that decide how each tenant moves (including contracts that make every change a separate event), how flags are governed and tracked to zero, and the organizational work that stops new forks from appearing the week after the last one is retired.

A variant isn't done when the code compiles behind a flag. It's done when replay shows the tenant can't tell the difference, and the only tests that could have hidden a regression were ones the agent wasn't allowed to touch.
