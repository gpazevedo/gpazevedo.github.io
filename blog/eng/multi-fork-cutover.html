Dozens of forks, one codebase: move every tenant, then keep the forks from growing back

The last part of the playbook: what a shared deployment needs, how each kind of tenant moves, and the rules that keep one codebase from becoming dozens again.

TL;DR

The problem. After the inventory and the variability model, the base can reproduce every variant a fork's tenants use. Now real customers have to move onto it, some of them under contracts that treat any change as an event, and the organization that produced the forks has to stop producing them.

What you get. The four things a shared deployment needs before the first tenant arrives; three tenant tiers, each with its own cutover path; two kinds of flags kept strictly apart, with an owner, an expiry and an audit trail; the order of work; and the governance, metrics and risks that decide whether any of it lasts.

Why it's worth your time. Moving a tenant swaps all the code under it at once. That's fine for most tenants, and it isn't for the ones whose contracts require each change to be switched separately. There are two ways to make the move a non-event, and which one fits depends on a single question about what the contract controls.

Status. A design, written before it was run, like the rest of the series.

Part 3 of 3. Follows Part 1: the inventory and Part 2: variability and proof.

Parts 1 and 2 were about knowing. This one is about moving: real tenants, real production systems, and a calendar. It's also about the part no tool fixes. The forks exist because, for years, copying the code was the easiest way to say yes to a customer. If that's still true the day the last fork is retired, the first new fork appears the week after.

Build the base one fork at a time

The base absorbs every variant; the fork branches aren't refactored. When the base can reproduce every variant a fork's tenants use, that fork has nothing left to refactor, and its tenants move onto the base's code with the right configuration. Meanwhile the forks become three things:

❄
Frozen

No changes except urgent fixes, and every urgent fix is applied to the base too.

⌕
The reference

Codex reads a fork's implementation and reimplements it as a variant in the base. Nothing is merged from the fork.

⚖
The oracle

Replaying a tenant's traffic against the fork and against the base with that tenant's configuration proves behavior survived.

✕
Not a destination

From day one, all new tenant-specific work goes into the base behind a variation point, never into a fork branch.

Start with the fork closest to the base, since it needs the fewest variants. Add its variants to the base one variant per pull request, with the base's default behavior unchanged and replay as the merge gate, so no tenant's behavior changes yet. Cut its tenants over, learn, and move to the next fork. Each fork needs fewer new variation points than the last, because the shared variants already exist.

Decide the base-side changes before any tenant moves. For every "stale" item from the inventory, choose between keeping the fork's old behavior (it becomes a variant in the base) and adopting the base's version, as you would for bug and security fixes. Adopted changes do alter a tenant's behavior at cutover, so tell the tenant in advance.

What a shared deployment needs first

One deployment serving every tenant needs four things in the base before any fork's tenants can move onto it.

1 · Every code path knows which tenant it's serving

HTTP requests are the easy case. The usual places it breaks: scheduled jobs, message consumers, async executors, outbound calls, and caches. A cache key without the tenant ID leaks data between tenants. A fork that only ever served its own customers may never have needed a tenant context at all, which is why the census records how each fork identifies tenants.

2 · Jobs run once per cluster

Every @Scheduled method fires on every pod of a shared deployment, so jobs need a cluster lock (ShedLock) or a clustered scheduler. Each run then fans out per tenant. A value that differs per tenant, such as reminding after 7 or 15 days, is a per-tenant check inside that one run. Only a difference in when the job runs (cron, time zone) needs a tenant-aware scheduler such as JobRunr, Quartz or db-scheduler.

3 · One set of dependencies

The shared deployment runs only the base's platform. The forks stay on their own Java and Spring Boot versions, since nothing is merged from them; variants are reimplemented in the base. So upgrade the base to the target platform before the first tenant moves. Only forks that must catch up in place (Option B, below) upgrade too.

4 · Isolation, and connections sized by server

A bug in one variant can now reach every tenant. Add a kill switch per variant per tenant, rate limits per tenant, and logs and metrics tagged by tenant and variant.

Connection pools follow the database topology. Size them per database server, never per tenant: with many tenants, a pool each would exhaust the server's connection limit. Schema-per-tenant can share one pool and set the schema at checkout. Database-per-tenant needs bounded pools created on demand and closed when idle, or a multiplexing proxy such as PgBouncer or RDS Proxy. Session-level settings can pin RDS Proxy connections, so test that before relying on it.

Reuse this

Before consolidating single-tenant code into a shared deployment, audit the five places tenant context gets lost (jobs, consumers, async work, outbound calls, cache keys) and put a cluster lock on every scheduled job. Both failures are silent until two tenants share a pod.

Three tenant tiers, three paths

Tenants move one at a time, and each tenant's tier decides how. Whoever owns the contracts places each tenant in a tier.

TierRequirementPath
StandardNothing beyond the SLAA single cutover per tenant
Functional controlEach behavior change switched on separatelyOption A
Code isolationEach code-path change switched on separatelyOption B

The standard cutover

  1. Load the tenant's configuration: every variant set to its fork's behavior.
  2. Apply the additive migrations and validate the base's entity model against the tenant's database.
  3. Compare: mirror the tenant's live reads to the shared deployment, replay its captured writes against a snapshot. Each variant maps to known units, so each divergence points at a specific variant.
  4. Switch routing at the gateway.
  5. Keep the fork deployment as a fallback until things are stable. The fork's code must still run against the tenant's database during that window, which is why the schema changes were additive.

A tenant of any tier can also run on its own dedicated deployment of the base when it needs infrastructure isolation: noisy neighbors, data residency, its own maintenance window. That's a deployment choice, not a tier. The move still swaps all the code at once, so it doesn't satisfy a code-isolation requirement.

Option A: a behavior-neutral move, then per-variant switches

For contracts that govern changes in functional behavior.

  • Before the move, every variant reproduces the fork's behavior exactly, including the old behavior for base-side changes the fork never received. Even bug fixes stay off for this tenant until each is switched on individually.
  • Evidence: session replay plus a longer period of mirrored reads than usual, weeks rather than days. Together they show the move changes nothing.
  • After the move, every behavior change, whether adopting the base's version or standardizing, is a separate per-tenant flag flip, scheduled as the contract requires.
  • Cost: no fork refactoring. These tenants follow the standard path with stricter configuration and a higher bar of evidence.

Option B: per-variant code switches in the fork deployment

For risk profiles that require each code change to be isolated, so a problem can only ever affect one variant.

  1. Catch the fork up with the base, one release at a time, with every base-side behavior change behind a flag that defaults to the old behavior for these tenants. git-imerge pins each conflict to the pair of commits that caused it. Each step is a release tag that must build and pass its tests; a platform jump such as javax to jakarta uses OpenRewrite recipes at the release where the base made it.
  2. Switch variant by variant. For each variant, the unified path sits beside the old one, chosen per tenant by a migration flag (branch by abstraction). For side-effect-free logic, run both paths and log divergences: the Scientist pattern, Scientist4J in Java.
  3. Move with no code change. When the fork's diff from the base reaches zero, its deployment is already running the base's code, and moving to the shared deployment is an infrastructure change only.

Cost: the catch-up touches every tenant on that fork. One strict tenant puts its whole fork on this path, so budget Option B per fork, not per tenant, and start it as soon as the inventory has classified the base-side changes. It's the longest piece of work; run it in parallel.

The question that decides A or B

Do the strict contracts govern changes in functional behavior, or any change to the code that serves the tenant? If it's behavior, Option A covers these tenants and no fork has to be refactored in place. Ask the contract owners early; the answer can remove the program's longest workstream. And whatever the answer, security fixes usually can't wait for per-variant scheduling, so check each contract's terms for emergency changes.

Whatever the path, every flip of a stateful variant applies the switch strategy recorded in Part 2: drain, migrate or version the in-flight work before the flag counts as switched. In a full cutover, in-flight work on the fork either drains there before routing changes or is migrated with the tenant's data. And the old path must be able to read whatever the new one wrote until the fallback window closes.

Flags: two kinds, never mixed

Variant configurationMigration flag
PurposeWhich behavior a tenant getsOld vs. unified path during a switch
LifetimePermanentDays to weeks
RemovedWhen the variant is retiredWhen every tenant on the fork is on the unified path

Give every migration flag an owner and an expiry date, and make CI fail on expired ones. Otherwise the flags become the next layer of debt. One tenant configuration and flag service serves the shared deployment and the caught-up Option B forks alike, so a tenant's settings carry over unchanged when it moves.

For contract-sensitive tenants, each flip is a change record. Log who flipped it and when, which tenant and variant, the approval reference, the replay or mirrored-traffic evidence behind it, and the fallback window. If a contract requires notice before behavior changes, the tenant's list of pending variants is its change calendar. And a kill switch per variant per tenant keeps every reversal a single flag change.

Tracking to zero

Every (variant, fork, tenant) combination moves through the same states:

1
Decided
Drop, adopt the base's behavior, or preserve.
2
In the base
Implemented behind its variation point, default unchanged.
3
Verified
Replay and mirrored reads show the tenant can't tell the difference.
4
Switched on
With its audit record.
5
Old code removed
The only state that actually reduces the codebase.

The concept × fork matrix from Part 1 becomes the burn-down chart: every cell that isn't "same" is work left. A per-tenant view shows how many of each tenant's variants are on the unified path. Rerun the inventory weekly; the cache makes it cheap.

A view the contract owners can read

Contract owners and reviewers need to see what can change for each tenant without reading code. A view generated from the inventory adapts the runtime adaptability viewpoint of Tekinerdogan and Sözer, which records what can adapt independently of the mechanism. It needs one extension: the active mode is per tenant, not system-wide.

Three things run in parallel from the start: capturing usage and traffic, because the evidence needs weeks; the Option B catch-ups, as soon as the inventory has classified the base-side changes; and the no-new-divergence rule, from day one.

If a cloud move is also on the roadmap, make convergence its precondition: move the unified base once, rather than lifting and shifting dozens of forks. Design one artifact that can run pooled (multi-tenant) or siloed (one tenant per deployment), keep tenant configuration in a config service and secrets in a secrets manager, and tag observability by tenant from the start.

The half no tool fixes

Convergence only holds with a sponsor who will stop new forks, and with protected capacity for the team doing it. The questions worth asking in week one:

  • Intent. Grow the product, maintain it, or migrate its customers elsewhere? (Part 1's first table.)
  • Authority. Can new forks be stopped? Who approves customer-specific requests from now on?
  • Capacity. How much of the team goes to convergence versus maintenance? Something like 70/30 at first is realistic; zero means it doesn't happen.
  • Success. What does success look like at 6 and 12 months, and how will it be measured?
  • Contracts. Does any agreement promise specific behavior or a dedicated version?
  • People. Is anyone from the original team still here? They're the most valuable asset and the biggest key-person risk.

Governance against new forks

  • A "no new forks" policy, agreed with product and commercial leadership.
  • Every customer request goes through one intake.
  • A small architecture forum, with product and customer success, places each request on the variation ladder from Part 2: configuration, flag, extension point, or no.
  • A review gate in CI (an AI reviewer plus ArchUnit) enforces the rule automatically.

Organize a dedicated convergence squad beside a maintenance team, rotating people between them to spread knowledge, and let the team that designs the extension points own them. Bring customer success in early: some customizations are cheaper to negotiate away than to preserve.

The questions that change the plan

A design written before reading the code should end with what it doesn't know. Each of these changes the plan depending on the answer:

  • What do the strict contracts govern: functional behavior, or any code change? The answer decides between Option A and Option B.
  • What's the database topology (per fork, per tenant, shared), the engine, and the number of tenants per fork? Together they set connection pooling. The census answers it.
  • How wide is the Java and Spring Boot version spread? The census answers it too.
  • Is the commit history meaningful (clear messages, ticket IDs), or was it squashed? That affects provenance quality, not which concepts are found.
  • Can the forks' outbound traffic be recorded (egress proxy or mesh, TLS interception)? If not, outbound behavior is verified by characterization tests alone.
Across three parts the pattern is the same. Measure before deciding, decide before moving, and move one variant and one tenant at a time, with evidence the change can't fake. The technique gets the forks back into one codebase. Only the governance keeps them there.
