Not a Testing Problem:
how a multi-agent system evaluates itself in production

Evaluating an autonomous procurement system isn't a testing problem — it's an architecture problem. Here's how three evaluator types, a 25-point quality composite, and five automated remediations got built into a multi-agent system's production fabric from day one — and what's still just scaffolding.

Procurement is a domain of consequences. An agent that misclassifies an item sends it down the wrong negotiation strategy. An agent that produces a vague bid rationale creates legal exposure. An agent that breaks confidentiality by revealing a competitor's price can unravel supplier relationships in hours.

When you automate 80% of an organization's purchasing volume at machine speed, the cost of silent quality drift is not academic. Buyer Team — a multi-agent system that autonomously negotiates purchase orders from requisition to award — forced us to confront this early: traditional testing is necessary but not sufficient for agentic systems.

"The right mental model isn't 'how do we test this agent?' It's 'how do we continuously know the state of our agent's quality, in production, at all times?'"

This post walks through the evaluation architecture we built, the decisions behind it, and the trade-offs we consciously accepted. Observability tells you what happened. Evaluation tells you how well. This post is about the second half.

The core problem: why agents are different to evaluate

Before designing anything, we mapped the failure modes that make agentic systems hard to evaluate. There are four.

Non-determinism. The same input doesn't produce the same output. A traditional function is easy to regression-test; an LLM agent requires statistical evaluation over distributions. Binary pass/fail harnesses generate false negatives constantly unless they're written to tolerate variance — which defeats the purpose of a tight gate.

Multi-hop opacity. A Bid Evaluation agent might rank Supplier A over Supplier B correctly, but for the wrong reasons. The answer passes; the reasoning is brittle. You won't catch this until the third similar scenario where the reasoning pattern breaks.

Cost opacity. Every agent invocation burns tokens. A single buggy retry loop can silently multiply the cost per negotiation before anyone notices. Token usage isn't a test concern — it's an operational reality that needs the same continuous monitoring as error rates.

Silent quality drift. The model doesn't know it's getting worse. Evaluation scores degrade gradually, and a slow slide in a quality score doesn't trigger any infrastructure alarm on its own — only a purpose-built quality alarm does.

Three evaluator types, zero guessing

The most important early decision was to stop thinking of evaluation as a single thing and decompose it into three types, each optimized for a different class of question.

Type A
LLM-as-Judge
qualitative
Used for Communication Tone, the Negotiation Quality Composite, and Rationale Defensibility — the last of these twice: once as an equally-weighted slice of the composite, and again through a dedicated three-axis rubric that gates auto-award on its own. Every judge call, from PR checks through production, runs on the same model — one calibration surface to maintain, not two.
Type B
Ground Truth
deterministic
Kraljic classification is graded at three tiers of the same metric: a 1.0 rule-floor on synthetic fixtures (offline, every PR), a 0.80 floor on a live name-only agent call (every PR), and a 0.90 floor on a live full-axes run (daily, feeding the production alarm). Bid ranking is graded by mean Spearman rho ≥ 0.90 across a golden dataset, plus zero top-1 mismatches on close calls.
Type C
Code-based (Lambda)
structural
Bid Format Compliance and Governance Policy Compliance run as deterministic Lambda checks before any LLM judge sees the output. Scores are binary: 1.0 or 0.0. Either one firing triggers the same halt-negotiations remediation — there's no partial credit and no separate code path to keep in sync.

LLM-as-Judge: outsourcing qualitative judgment

Some questions cannot be answered deterministically. "Is this supplier communication appropriately professional and relationship-preserving?" has no regex. "Is this bid rationale logically sound and evidence-based?" has no lookup table. For these, we use a judge model — a separate LLM invocation that scores the output against a rubric.

The variance issue deserves emphasis. An LLM judge is itself a probabilistic system — calibrating it is as important as calibrating the agent it evaluates. That's why judge consistency and judge-vs-human calibration are checked on a recurring cadence rather than assumed once and forgotten, and why every eval surface, from the PR gate to production, is pinned to the same model. Two models to keep in sync would mean two calibration problems.

Ground truth: the anchor for objective accuracy

Where objective labels exist, we use them. The domain provides two natural ground truth datasets: a Kraljic Strategy Dataset with labeled item classifications, and a golden bid-ranking dataset with known rankings from historical negotiations.

Kraljic accuracy isn't gated by a single number — it's gated at three tiers, each cheaper and looser the earlier it runs. A synthetic-fixture rule baseline must hit 1.0 offline on every PR — no network call, no excuse. A live name-only classification call must clear 0.80 on every PR — a floor set just under the measured baseline, so it catches regressions without being a coin-flip gate. A live full-axes run must clear 0.90 daily, and that number is the one that feeds the production alarm. Getting the quadrant wrong is a category-level error — it decides which negotiation strategy runs at all, not just how one negotiation is scored — which is why it gets the tightest, most frequently re-checked floor of any ground-truth metric in the system.

Code-based evaluators: the zeroth gate

Before any LLM judge touches an output, Lambda-based deterministic checks run against it. Bid Format Compliance validates JSON schema, required fields, and format constraints. Governance Policy Compliance checks budget ceiling, approved supplier list, ESG minimum score, and confidentiality rules. Both are binary: 1.0 or halt. There is no partial credit for governance violations, and no partial credit for malformed bids. These are the fastest, cheapest, most reliable layer — which is why they run first, and why the same remediation Lambda listens for either one.

The communication tone sampling problem

Communication Tone is the most expensive evaluator to run at scale — it fires per supplier message, not per negotiation. Running an LLM judge on every message in a busy multi-supplier auction adds up quickly.

The solution is a tiered sampling strategy driven by risk, not randomness — scoped specifically to award and rejection notifications, the two message types where a wrong tone or a leaked price carries the most consequence.

100%
Always: Award notifications. Legally binding — no threshold applies, no sampling.
100%
Value threshold: Rejection notifications where the awarded price meets or exceeds a configurable USD threshold (default $50,000). High-value negotiations warrant full scrutiny on the rejection side too.
10%
Sampled: Rejection notifications below the value threshold. Sampling is deterministic — a SHA-256 hash of the communication id decides inclusion, not random() — so a retried Step Functions execution samples the same message the same way every time. Both the threshold and the rate are per-tenant DynamoDB overrides, resolved through the same governance-config lookup as every other threshold in the system.

Trade-off accepted: below-threshold rejection notifications go tone-scored only 10% of the time. That's mitigated by a separate, unconditional mechanism: a WinnerDisclosureGuard hook inspects every rejection message for winner-price leakage, regardless of whether that message happened to be sampled for tone scoring. Confidentiality enforcement doesn't depend on the sampling rate at all — only the softer, qualitative tone score does.

The quality composite: a 25-point rubric

The most important evaluation metric is the Negotiation Quality Composite — six components, each scored 0.0–1.0 by the judge, weighted equally, then averaged and scaled to a 25-point maximum. This is the single number that determines whether an automated model rollback fires.

Component Weight Max points (of 25)
Ranking Accuracy16.7%4.17
Rationale Defensibility16.7%4.17
Risk Detection Accuracy16.7%4.17
Scoring Consistency16.7%4.17
Completeness16.7%4.17
Savings Calculation16.7%4.17

There's no individually-gated sub-threshold per component today — only the blended average is enforced. The production alarm reads the score normalized back to a 0–1 scale (composite ÷ 25) and compares it against 0.60 — equivalent to a 15-out-of-25 floor — which automatically rolls the deployed model tier back to its previous configuration. Equal weighting is the simpler default to build and reason about; it doesn't yet reflect that a wrong ranking should probably cost more than an incomplete field (more on that in "What we'd do differently").

Rationale Defensibility carries more real weight than its equal composite share suggests, because it's also scored independently — a dedicated three-axis rubric (logical soundness, evidence grounding, defensibility under challenge) — and that standalone score, not the composite slice, is what a separate production alarm at 0.70 watches to block auto-award. The composite catches slow drift across a whole negotiation; the standalone gate catches one indefensible rationale before it reaches a supplier. Two evaluators looking at the same concern from different angles, not duplicated effort.

Evaluation thresholds as configuration, not constants

Hardcoding evaluation thresholds into agent code was one of the architectural decisions we explicitly rejected. A threshold appropriate for a $500 tail-spend item is not the same threshold appropriate for a $5M strategic contract. And a threshold appropriate in month one may not be right in month six when the agents have demonstrated reliability.

Every governance and evaluation threshold resolves through a two-stage DynamoDB lookup, run fresh on every node invocation — no cache, no TTL, no propagation delay to reason about:

# Two-stage resolution, re-run on every Step Functions node invocation
cfg = load_config("governance", "default")                   # 1. platform profile
override = load_config("governance", f"tenant#{tenant_id}")  # 2. tenant override
if override:
    cfg = {**cfg, **override}   # shallow merge: override replaces matching top-level keys

# Table: {env}-system-config, keys (config_group, config_key)
# Payload is a JSON blob run through config_schema.migrate() on read

Because the merge is shallow, a tenant override of a block like approval_thresholds replaces that whole block rather than deep-merging individual keys inside it — a deliberate simplicity trade-off that keeps override semantics easy to audit, at the cost of requiring a full block on write. And because there's no cache layer, a tenant override takes effect on the very next node execution, not on any polling interval.

One flag breaks this pattern on purpose: auto_award_blocked, the kill-switch a Rationale Defensibility alarm flips, is cached for 30 seconds rather than read fresh every time. It sits on the hottest path in the system — every approval-gate invocation checks it — so a small, deliberate staleness window trades a sliver of responsiveness for meaningfully less DynamoDB read load. Everywhere else, staleness is worse than an extra read.

Alarms that actually do something

Most observability implementations stop at "alert the on-call." We went further: several alarms trigger automated remediation Lambdas without human intervention.

Alarm Threshold Automated action
Negotiation Quality Drop score < 0.60 roll model tier back
Communication Tone Drop tone < 0.80 disable auto-send
Rationale Defensibility Drop score < 0.70 block auto-award
Bid Format Non-compliance score < 1.0 halt negotiations
Governance Policy Non-compliance score < 1.0 halt negotiations
Kraljic Accuracy Drop accuracy < 0.90 invalidate cache + alert
Governance Violation (any type) count ≥ 1 compliance SNS
Confidentiality Violation count ≥ 1 critical SNS

The automated actions are tiered by severity, and by how much we trust the signal to be a true positive. The two score-based compliance checks — Bid Format and Governance Policy, both binary, both structural — are trusted enough to halt new negotiations automatically the moment either one fires. The count-based violation alarms, which aggregate across looser violation categories, route to compliance and critical SNS topics for human escalation instead of an automatic halt: a broader net is more useful for alerting a person than for deciding, unattended, to stop the system. Quality-drop alarms sit in between — they disable a specific capability (auto-send, auto-award, or the deployed model tier) rather than halting outright, so the agent keeps working while a human reviews the affected surface.

Disabling auto-send when Communication Tone drops is the clearest example of graceful degradation over hard failure. Supplier communications route to a human review queue; the negotiation continues; the messages wait for approval before transmission. Five separate remediation Lambdas exist for these actions, each subscribed to the same evaluation-alerts SNS topic and self-filtering on the alarm name it cares about — this is only possible because the evaluation layer is tightly integrated with the agent's execution path, not bolted on after the fact.

Decision: one model everywhere, not two

Every judge call — PR smoke test, weekly staging suite, production trace — runs on the same lightweight model. We considered a cheaper model for the PR gate and a stronger one for staging certification, but rejected it: two models means two consistency checks and two calibration curves to keep in sync, for a signal that's only used directionally at the PR stage anyway. One model, checked periodically for judge-vs-human agreement, is a smaller surface to trust.

Trade-off: promotion to production is still a human call

There is no automated staging-to-production promotion gate today. A failed or suspended weekly staging run is a manual go/no-go signal for whoever dispatches that promotion — not a block enforced by the pipeline itself. That's a real gap relative to the fully automated PR and production layers, and it's an honest one: judge calibration against the human panel isn't yet confident enough, at a wide enough sample, to hand that decision to a script. In the meantime, the production alarms in the table above are the real backstop — they respond to a bad promotion within minutes of it going live, whether or not a human caught it in staging first.

Degrading under memory failure

AgentCore Memory is designed to provide cross-negotiation context — supplier performance history, previous award patterns, category expertise. The intended failure mode is a circuit breaker around every call to it (and to the underlying Mem0 store): a call that trips the breaker or fails with a storage-related error should mark the negotiation memory_degraded = true and let execution continue rather than failing the negotiation outright, clearing the flag automatically once a subsequent call succeeds.

That mechanism exists as a correctly-implemented module — but it has no callers anywhere in the codebase today. The memory path actually running in production is a simpler DynamoDB-backed supplier-memory substitute, and it degrades silently: on a lookup or write failure it falls through without ever touching memory_degraded. So the honest gap isn't "the flag is set but nothing downstream reads it" — no negotiation is ever marked degraded in the first place. The circuit breaker is unwired scaffolding for a fail-open pattern, not a fail-open pattern quietly running in production. We consider that an open gap, not a finished feature, and it's first on our list below.

Architectural trade-offs: the summary

⊕
Three evaluator types, not one

LLM-as-Judge, Ground Truth, and Code-based serve different classes of question. Added complexity, but each type is optimized for its domain — no single evaluator could cover qualitative tone and binary governance compliance equally well.

⊕
Risk-tiered evaluation sampling

Cuts Communication Tone evaluation cost on routine rejection traffic. Accepted risk: below-threshold rejections go tone-scored only 10% of the time. Mitigated by unconditional confidentiality checking (WinnerDisclosureGuard) that never samples — it runs on every rejection regardless of the tone-scoring rate.

⊕
Thresholds as always-fresh configuration

A two-stage, uncached DynamoDB lookup means tenant overrides take effect on the very next invocation. The risk is override misuse — a tenant can currently set any threshold, including governance ones, below the platform's intended minimum, because the merge has no server-side floor. Still open (see below).

⊕
Automated remediation where the signal is trustworthy

Binary, structural alarms (format, governance-policy compliance) halt automatically; count-based violation alarms escalate to humans instead; quality-drop alarms disable one capability rather than the whole system. Calibrating which alarms deserve which tier of trust is itself an ongoing design decision, not a one-time choice.

What we'd do differently

Start with the golden datasets earlier. The Kraljic ground truth dataset and the bid-ranking golden set were constructed alongside the agents. Ground truth should exist before the first agent line is written — it defines what "correct" means before you have anything to evaluate.

Move the composite from equal weighting to priority weighting. All six Negotiation Quality Composite components currently count the same. A wrong ranking or an indefensible rationale should probably move the score more than an incomplete field does — that's a judgment call we haven't encoded yet, and the equal-weight default is a placeholder more than a decision.

Wire up memory degradation before instrumenting it. The circuit breaker and memory_degraded field exist as isolated, correctly-built code with zero callers — the DynamoDB-backed memory substitute that actually runs in production degrades silently and never sets the flag. A metric or a post-completion review queue is the second step; the first is connecting the breaker to the real memory call path so a degraded negotiation gets marked at all.

Add a governance floor on per-tenant threshold overrides. The two-stage config merge is a plain shallow overlay with no server-side ceiling or floor. A tenant who sets negotiation_quality_composite_minimum — or any other governance threshold — below the platform's intended minimum can currently do so unopposed. Clamping the resolved value against a non-overridable platform floor, in the same resolution path, would close this without adding a second system to keep in sync.

The broader lesson

The investment in evaluation is proportional to the autonomy of the system. A traditional CRUD application fails loudly and recovers quickly — you can afford to evaluate it lightly. An autonomous negotiation agent that makes decisions on behalf of an organization, communicates directly with external suppliers, and recommends contract awards needs to be evaluated at every layer, continuously, and capable of constraining itself before a human notices the problem.

Evaluation in agentic systems is not a QA activity. It is an architectural layer — with its own data infrastructure, its own alarm topology, and its own automated response behaviors. Building it that way from the beginning is what makes it safe to trust the autonomy — and being honest about which parts of that layer are still manual is part of the same discipline.
