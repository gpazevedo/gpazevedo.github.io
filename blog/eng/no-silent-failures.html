Five tools, no silent failures: where Buyer Team handles failure

Buyer Team doesn't scatter failure handling across six LLM agents, thirteen Lambdas, three MCP servers, and a Step Functions orchestrator. It's centralized in five shared tools — one per boundary — so that every failure is detected, categorized, made observable, and recovered or escalated. Each tool exists because a failure once went silent. This is the mechanism tour: what each of the five catches, and the incident that proved it necessary.

Somewhere in Buyer Team, every failure is supposed to be caught: a throttled agent call, a Lambda that dies on its own schedule, an MCP server returning a raw exception to an LLM caller, a checkpoint that was never written. When we swept the codebase for where that detection and handling actually lives, the answer was satisfying in a way code audits rarely are. It is not spread thinly across the six agents and thirteen Lambdas and three MCP servers. It lives in five shared tools — two shared Python packages, one shared Layer, one resilience module, and one alarm surface in Terraform.

That concentration is the point. Buyer Team's resilience history is a series of silent failures — failures that happened, kept happening, and were indistinguishable from health. A Lambda failed 44 of 44 scheduled invocations for 30 days while its business alarms read OK. Another ran 12 days with an AccessDenied on every call. A missing module in a deploy zip took the terminal node of the whole purchase chain down for three days while the rest of the system returned plausible fallback results. None of these were survivable without an observability story, and all of them were fixed the same way: by concentrating the handling in one place where it could not be skipped, and by standing an alarm behind it so even the handling layer can fail loudly.

The five tools, from the innermost boundary to the outermost:

fail-closed guardrails steering guards admission control one AWS client EMF metrics
Tool 2 lambda-core packages/lambda_core · all 13 Lambdas
guarded / http_error_response failure metrics cached clients shared Layer + DLQ
Tool 3 mcp-core mcp_servers/shared · the 3 MCP servers
safe_tool require_tenant traced_tool /ping + build_mcp_app
Tool 4 Orchestrator-resilience orchestrator/resilience · the SFN node executors

Tool 5 AWS metrics & alarms infra/ · CloudWatch, SNS, DLQ, dashboards

Each section below is mechanism-first: what the tool is, what it catches, how. The incidents that forced the tool into existence appear as evidence callouts — they are not the argument, they are the proof. The last section walks one failure through all five tools to show how they compose.

Tool 1 — The Agent MicroKernel

packages/buyer_agent_core one shared package under all six LLM agents

Buyer Team's six LLM agents — Kraljic classifier, spot bidding, leverage auction, bottleneck negotiation, strategic partnership, award comms — each run in their own AgentCore runtime microVM. Each agent.py is a thin declaration: a prompt builder, a request/response schema, a list of tools, a steering guard. Everything that is not the agent's specific business logic lives in one shared package, buyer_agent_core, which we call the microkernel. It owns the serving loop, the safety layer, and the admission boundary — the three places an agent can hurt the system without meaning to.

Fail-closed guardrails

Every deployed agent runtime sets GUARDRAIL_REQUIRED=true. When that flag is set and GUARDRAIL_ID/GUARDRAIL_VERSION are unset, the guardrail wiring raises GuardrailRequiredError instead of returning an empty config. Because each agent constructs its model at module import time, that raise crashes the process before it binds a port. A deploy that loses its Guardrail doesn't serve a single unprotected request — it just doesn't come up. An unprotected state is also alarmable on its own: unconfigured wiring emits a guardrail.unconfigured metric, so the condition is visible even before it crashes anything.

The microkernel also draws the line between a real guardrail block and a masking-only intervention. Buyer Team's Guardrail anonymizes EMAIL/NAME/PHONE/ADDRESS by design — the agents pass supplier contact details into the model, which echoes them back and trips output PII masking. A masking-only intervention leaves the content usable; a genuine BLOCKED action (content filter incl. PROMPT_ATTACK, topic DENY, blocked PII/regex) must stop the run. is_masking_only_intervention() makes that distinction, and a genuine block raises GuardrailBlocked — which is deliberately not retried. Proven live: retrying a blocked prompt can come back clean, because the PROMPT_ATTACK filter is confidence-scored rather than deterministic, and running step 2's structured-output coercion on top of a blocked step 1 makes the model fabricate a plausible-looking response from nothing. The block gets silently discarded. Blocking is terminal, and a security.guardrail.triggered metric fires on the way out.

Steering guards fail closed

Every agent's tools are gated by steering hooks — governance checks that can refuse a tool call (a TCO guard that demands every candidate be priced, a rank-only integrity guard on auction bids). A GuardHandler base class wraps all of them. Any exception escaping a hook's check() cancels the tool call and emits a governance.hook_error metric — deliberately distinct from the metric fired when a hook works and blocks something, so an alarm can tell "the guard broke" from "the guard is doing its job." A guard that hangs fails closed the same way a raise does: check() runs under asyncio.wait_for (10s default).

The fail-closed guarantee is enforced by tests, not convention. A static test asserts every GuardHandler subclass overrides only check() — never steer_before_tool directly, which is the sibling escape route — and that none subclass Strands' SteeringHandler directly. Every one of the eight real guard instances across the agents has a test that drives a genuine failure through its own check(), and every agent's spec has a test asserting the guard is actually registered. The guarantee covers a guard that's wired in; the tests confirm each one is.

Inbound admission control

An LLM agent's unit of work is a multi-second two-step run, so the resource to bound is in-flight count, not requests per second. Each agent runs ASGI middleware (AdmissionControl) that caps concurrent task POSTs — globally and per tenant — and fast-rejects with HTTP 503 plus a Retry-After: 1 hint when saturated, instead of letting requests queue under a burst. Health probes and GETs always pass through, so a saturated agent never looks unhealthy to the platform. The body is bounded at 1 MiB, checked as chunks arrive so an oversized body is never fully buffered before rejection. Per-tenant bucketing means one tenant's burst can't starve another's admission slots on a shared warm replica — fairness among tenants that are already trusted equally, not a new authorization boundary.

Shedding early beats queueing: a rejected request gets rescheduled against a less-loaded replica immediately by the caller's retry, rather than piling onto one that's already struggling.

One AWS client, one metric path

Every agent's tools.py used to build its own DynamoDB resource, botocore Config, and region lookup — six copies of one retry policy, so a timeout change had to be made six times and could drift silently. The microkernel's aws.py is now the single construction site: Config(connect_timeout=10, read_timeout=30, retries={"max_attempts": 3, "mode": "adaptive"}), region read lazily on first use, every client/table cached for the life of the warm container. A static boundary test enforces per-agent that no agent imports boto3 directly.

Metrics go out through an EMF implementation — a structured JSON line to stdout that CloudWatch Logs extracts into a datapoint, with no CloudWatch API call on the instrumented path. The previous implementation was a synchronous put_metric_data sitting in the per-step usage-logging hot path with a 5s connect + 5s read timeout, retried once: in the failure case, up to ~20s of blocking network I/O per LLM step. EMF removes the remote call entirely, so the metric can't fail independently of the code it instruments.

Model ladder and readiness

The model each agent uses is resolved from a tier at initialization, not hardcoded. A config-read failure is distinguishable from a legitimate fresh-environment fallback by a tier_fallback metric and a /ping tier_source field — a genuinely broken config and a benign default look different to an operator. The /ping health check is a real readiness gate: unhealthy until startup — including model and prompt configuration loading — genuinely completes, healthy after; a replica never takes traffic before it's ready, and it flips unhealthy the moment shutdown begins so in-flight work drains within a bounded window.

Evidence — a week of masked crashloops

Every one of the six agent Dockerfiles once omitted response_builder.py from its explicit COPY list. Every deployed runtime crash-looped on container startup with ModuleNotFoundError, and invoke_agent_runtime returned 424 on every real call — for a week — before anyone noticed. It stayed invisible because the orchestrator's node executors degrade gracefully to fallback-stub pricing on any agent failure, so what was actually a total outage looked like ordinary fallback traffic. The fix was one line in six Dockerfiles; the lesson was that graceful degradation without an error-rate alarm is a silent-failure engine. That is why the microkernel's metric path and the alarm layer (Tool 5) are not optional extras — they are the only thing that makes degradation legible.

The other founding incident: an adversarial replay of 60 attacks scored 0/60 blocked because no agent's Bedrock call carried guardrailConfig at all — the Guardrail resource was provisioned in Terraform but never attached to any model call. The microkernel's guardrail wiring exists because provisioning a Guardrail has no effect until the code actually passes it.

Tool 2 — lambda-core

packages/lambda_core a shared Layer under all 12 Lambdas

One layer below the agents, the same drift the microkernel fixed for the agent fleet was unfixed for the Lambdas: six-plus independent boto3.client(...) sites with no shared retry config, seven copy-pasted logger blocks, five-plus hand-rolled put_metric_data sites — and, worst, two handlers with no exception handling at all. lambda_core is the same cure for the Lambda layer: one package, shipped as a real aws_lambda_layer_version, that every handler imports.

Two failure primitives for two trigger shapes

Every Lambda trigger needs the same two things when its body raises: log the exception with enough context to find it, and emit a CloudWatch metric so it's alarmable. What differs per trigger shape is what happens after that. lambda-core splits the difference with two primitives:

  • guarded(logger, source) — a context manager that logs, emits a <source>.failure metric, and re-raises. This is for SNS/EventBridge-shaped handlers, where re-raising lets Lambda's async-invoke retry — and, once configured, the DLQ — still fire. It only adds observability; it never changes control flow.
  • http_error_response(...) — a decorator for API-Gateway-shaped handlers (e.g. token_exchange_broker): catch, log, emit the failure metric, and return a structured {statusCode, body} JSON error instead of letting the exception surface as a raw Lambda 502.

The failure metric is dimensioned by exception class, so an alarm can tell what failed apart from how often. Emission is EMF — best-effort by construction, so a broken metrics call can never mask the real exception it was reporting.

Shared clients, shared logging

aws.py is the one place a handler's boto3.client(...) gets built, with the same retry/timeout policy the agent fleet uses (10s connect / 30s read / adaptive retries) and caching per warm environment. logging_setup.py gives every handler one consistent logger at LOG_LEVEL (default INFO, overridable per environment). Both replaced N copies of the same thing, so a tuning change is now one edit and one deploy instead of a silent per-handler drift.

The infra half: a DLQ where there was none

Observability primitives don't fix a missing DLQ — that's infrastructure. Before this work, no Lambda in the repo had a dead-letter queue or on-failure destination: an unhandled exception silently vanished after Lambda's default two async-invoke retries. lambda-core ships with the infra half as well: a shared SQS DLQ, plus event-invoke config and the IAM grant on all eight async-invoke Lambdas that had no prior handling.

The IAM detail here is the kind that silently breaks: the invoked Lambda's own execution role — not the SNS/EventBridge principal — needs sqs:SendMessage on the destination, or DLQ delivery fails silently. The precedent comment calls it out explicitly, because it is the second-silentest failure mode in the file.

Evidence — failures that simply vanished

Two of the automated remediation Lambdas had zero exception handling and no DLQ or on-failure destination anywhere in Terraform. An unhandled DynamoDB throttle during a live governance alarm would raise, exhaust Lambda's two default async retries, and then disappear. Nothing logged, nothing emitted, nothing escalated.

One security-metric Lambda's failure handling was worse than nothing: a bare except: pass that swallowed the exception. A GuardDuty finding that failed to publish simply vanished — a security signal eaten by the very Lambda that exists to surface it. That swallow was deliberately changed to a re-raise when lambda-core landed: a finding is never silently lost, even if publishing fails loudly.

Tool 3 — mcp-core

mcp_servers/shared a shared base for the three AgentCore-hosted MCP servers

The three MCP servers that expose tools to the agent fleet over MCP each hand-rolled (or skipped) their own tenant check, error handling, tracing, and health check before this package existed. mcp-core is the same cure the microkernel and lambda-core each provide, applied to the server layer: one shared base every MCP server imports, so a server's resilience stops being a per-server judgment call.

safe_tool: a tool never leaks a raw exception

@safe_tool(logger) is the MCP analogue of lambda-core's guarded. It lets ToolError and PermissionError through — those are already-shaped, expected failures — but catches anything else and rewraps it as an opaque ToolError carrying a logged error_id. The calling agent gets a tool-shaped error instead of a raw stack trace leaking across the tool boundary; the error_id lets an operator correlate the opaque failure back to the real log line. Same shape as lambda-core's http_error_response: the boundary controls what the outside sees, and the inside is preserved for the operator.

require_tenant: fail fast on a missing boundary

@require_tenant() rejects a tool call with no tenant_id before the handler runs. Its default resolver trusts the tenant_id from the call — because no verified identity reaches these servers today: they're invoked directly, not through an AgentCore Gateway, so a JWT claim never reaches this path. The point isn't to verify identity that can't be verified; it's to make the boundary explicit and consistent instead of ad hoc per server — and to fail fast, loudly, the moment a tool is called without the one field everything downstream keys on.

traced_tool, /ping, and one-line wiring

@traced_tool(name, ...) tags the current span with tool.name and tenant_id, so a failed tool call is attributable to the tenant and the tool that failed. build_mcp_app(server) replaces the three-line app-plus-middleware-plus-/ping wiring with a single call — a health check that, like the microkernel's, only reports healthy once the app is genuinely serving. Decorator order matters and is documented: require_tenant (outermost, fail fast) → safe_tool (catches everything below it) → traced_tool (wraps the actual call).

Evidence — three servers, three ways to get it wrong

Three servers, three ad hoc (or absent) failure modes. One server checked no tenant at all. Another compared tenant_id against a second argument nothing in the codebase ever populated — a check that was theoretically strict and actually a no-op. None of the three had a /ping route or wrapped exceptions before they reached the caller: a raw exception from an MCP tool surfaces to the calling agent as an opaque failure, and a broken server gave no signal about whether it was up. mcp-core exists because three hand-rolled implementations are three different ways to get the same thing wrong.

Tool 4 — orchestrator-resilience

orchestrator/resilience the Step Functions orchestrator's recovery machinery

Tools 1–3 make each layer's failure handling consistent and observable. Tool 4 is where the machinery actually lives: six orchestrator node Lambdas (ingest/validate, Kraljic classify, strategy execute, bid evaluation, approval gate, award comms) run a procurement negotiation through a Step Functions state machine, and the resilience package is where the real retry-and-recover work happens — retries, circuit breakers, idempotency, a dead-letter queue, fallback classification, saga compensation, and state recovery.

A safety net below the code: ASL retry and catch

Before any of that application code runs, the state machine itself has a retry layer — declared once in Terraform and attached to every node's Task state. Each one carries a Retry block (the standard Lambda service-fault and timeout error types — 3 attempts, 2s interval, 2x backoff) and a Catch on States.ALL routing to a Failed state. This catches a different class of failure than tenacity does: a node Lambda that never started, a transient AWS Lambda service fault, an invocation that hangs past its own hard timeout — failures at the invocation boundary, outside the node's own code, before the resilience package ever gets a chance to run.

One node carries a deliberate exception to the shared block. The human-in-the-loop approval step excludes timeouts from its retry set, because retrying it means re-invoking the step — which resets its start timestamp and installs a fresh task token, silently re-arming the 96-hour approval clock on every retry. Instead, a timeout on that state routes straight to a dedicated timed-out outcome — a valid outcome, not a failure — and the scheduled sweep performs the REQUIRES_ATTENTION routing on its next 30-minute tick. Same principle as everywhere else in this post: the generic retry policy is the default, and an exception to it is scoped narrowly and left as a comment explaining exactly which incident it prevents, not silently special-cased.

A chokepoint you can't opt out of

invoke_agent_runtime is the single function every agent call in the orchestrator goes through. It composes the retry decorator, the per-agent circuit breaker, and an explicit timeout in one place — and it's also the instrumentation point: token ceilings (200K/100K), a hook-rejection-loop guard (five consecutive rejections and it stops), and the cost/health metrics (cost.usd, cost.unpriced_model_invocation, agentcore.invocation_success 0-or-1, and agentcore.session_seconds in a finally). One chokepoint means no agent call can skip the resilience stack by forgetting to wire it in.

Retry, circuit breakers, and timeouts — all config-driven

Retry uses tenacity's exponential backoff with jitter, built from a config block in system-config — tunable without a redeploy. Each attempt emits an OTEL span event; on exhaustion the failure is published to the DLQ. Circuit breakers are one per external-dependency type (supplier MCP, Bedrock per failure-correlation scope, A2A agents, memory), with fail_max/reset_timeout from the same config source, and every state transition emits a resilience metric. Every external call carries an explicit timeout from config — and boto3 retries are deliberately disabled on those clients, so the resilience layer owns retry and the underlying call owns exactly one timeout, instead of the two fighting each other.

Idempotency and the transactional outbox

Side-effecting operations derive a deterministic key from (negotiation_id, supplier_id, action, round_number), check a DynamoDB table, and return the cached result on a hit — stored with a 14-day TTL, deliberately longer than the 7-day negotiation ceiling so a redrive never expires its own records mid-flight. System-level fallback decisions use a reserved supplier id and get the same treatment. Escalations and DLQ sends go through a transactional outbox: the event is written in the same DynamoDB transaction as the status it accompanies, and a poller delivers it — so a crash between the status write and the SQS send no longer drops the escalation.

The DLQ: a 12-field message, two destinations

When retries exhaust on a non-idempotent operation, the failure context — all 12 fields: negotiation, tenant, failed node and agent, error type and message, last checkpoint, trace ID, attempt count, breaker state, timestamp, graph-state snapshot — is recorded as an outbox event. It's delivered to the shared SQS DLQ and tee'd to an S3 archive with Object Lock GOVERNANCE and a 7-year retention: immutable retention well past the 14-day DLQ window, so an auditable record survives even after the queue's messages expire.

Fallback that knows it's a fallback

When the Kraljic Classifier agent is unavailable or returns a schema-invalid response after all retries, the orchestrator classifies deterministically from the same profit-impact/supply-risk axes and thresholds — and then applies rejection criteria: a rejected fallback must escalate to REQUIRES_ATTENTION rather than auto-award. The fallback carries a per-quadrant confidence (0.75–0.90) and an explicit "agent unavailable" reason, so a downstream consumer always knows a classification is a fallback and never mistakes it for the real thing.

Sagas, checkpoints, and recovery locks

Forward recovery resumes a negotiation from its last checkpoint. Each node checkpoints after completing, to a table keyed (tenant#negotiation, checkpoint#version) with a 30-day TTL and optimistic concurrency (write only if no prior row or a strictly-greater version). On restart, recovery enumerates non-terminal negotiations via a GSI, acquires a per-negotiation lock whose deterministic expires_at (600s) is checked in the ConditionExpression — so a crashed holder is reliably taken over — enforces the 168h total timeout, and resumes from the checkpoint. Backward recovery is the saga complement: each side-effecting step records an undo entry to a saga log, and on terminal failure those entries replay newest-first to idempotent compensation handlers. Recording is best-effort (a missing entry degrades to no-undo, never a failed PO issuance), and every handler is idempotent, so the whole flow is safe to retry.

Evidence — recovery code that silently no-op'd

save_checkpoint() had zero callers anywhere in the repo. Every recovery and DLQ-redrive path read a checkpoint that was never written: recovery never resumed a negotiation, and DLQ redrive escalated every message straight to REQUIRES_ATTENTION with a no_checkpoint marker. A fully-built resilience mechanism was dead code — not broken, not deleted, just never wired in. The fix wired checkpointing into all six node handlers through one shared helper, and exposed a Decimal-JSON-serialization crash along the way (a Decimal budget value in the graph state crashed a bare json.dumps). That is the class of failure this whole post is about: machinery that exists but was never connected produces exactly the silent no-op that a "tool" is supposed to prevent.

The other failure was a dependency that wasn't there: the orchestrator's Lambda build script never copied a supplier-communications module into the build dir, though the award-comms and delivery handlers imported it. Every deploy since that import landed shipped a zip that failed to import at cold start on both handlers — blocking every negotiation from reaching AWARDED — for three days before the missing copy step was found. And the delivery handler was missing its X-Ray IAM grant, so every invocation that did start hung the full 30s retrying the span export and timed out. Two deployment-time gaps that no amount of in-process resilience could catch — the kind the alarm layer (Tool 5) exists to make visible.

Tool 5 — AWS metrics & alarms

infra/*.tf the layer that turns silence into a page

Tools 1–4 make failure handling consistent and recoverable, but they can't make a failure loud. That's the alarm layer's job: the CloudWatch alarms in infra/ that watch the Lambdas, the state machine, and the agent runtimes, and page on the metrics every other tool emits. This is the tool that closes the loop — the one that would have caught every incident in this post if it had existed at the time.

The alarm catalog

The set of error alarms, by what they watch:

  • Six node-Lambda error alarms — one per orchestrator node, AWS/Lambda Errors ≥ 1 over 5 minutes.
  • Nine scheduled-Lambda error alarms — for every EventBridge-scheduled Lambda: outbox poller, DLQ redrive, runtime warmer, heartbeat, adversarial-robustness, supplier-skew, approval-sweep, plus the KPI rollup and FinOps cost poller.
  • Three state-machine alarms — executions failed, executions timed out, and execution time approaching 80% of the 7-day workflow ceiling.
  • One Metrics Insights alarm — a fallback-quality alarm summing fallback-rejection count over a 1-hour window, aggregating across dimension values in a single series.
  • Fourteen agent-runtime alarms — Errors and Latency for each of the seven runtimes (six agents + one skill runtime), dimensioned on the full {Name, Operation, Resource} set with the endpoint-qualified runtime name.

Error alarms on the Lambda, not business alarms on its output

The design rule behind the scheduled-Lambda set is the subtle one: an error alarm watches the Lambda's AWS/Lambda Errors metric, not the business metrics it publishes. A Lambda that dies on its own schedule has no other error signal — nothing calls it, so nothing fails at it — and the business alarms reading its output metrics all sit at OK under treat_missing_data = "notBreaching" the moment publication stops. The KPI rollup Lambda proved this: it failed 44 of 44 scheduled invocations for 30 days while all four of its business alarms read fine. The lesson is that missing data looks like health, so the thing you alarm on must be the thing that exists when the system is alive — the invocation itself.

An alarm that matches nothing looks healthy

CloudWatch matches an alarm's dimension set exactly, so an alarm keyed on a dimension subset matches zero series. With treat_missing_data = notBreaching, it then sits at OK forever and looks like healthy coverage. That's what happened to all 14 agent-runtime alarms: they were keyed on {Resource, Operation}, but every live series carries {Name, Operation, Resource} where Name is the endpoint-qualified runtime name. Seven runtimes had no error or latency coverage since the alarms were added, and the console showed green the whole time. The fix re-keyed on the full set — and the lesson is tombstoned in the file: re-verify the full dimension set, not just the values, whenever these are re-pointed.

Cost discipline is part of the design

Alarms bill $0.10 per alarm-month prorated hourly, regardless of state — so disabling alarm actions saves exactly $0, and only deleting alarms reduces the bill. CloudWatch alarms were 87% of the CloudWatch bill ($4.16 of $4.77 over 30 days), and $1.40/month of that bought nothing. The cleanup followed from that one fact: ten alarms that billed for zero coverage were deleted (four evaluation alarms on an unsubscribed topic, six per-node duration alarms whose signal already surfaces through the error and executions-failed alarms), and four KPI alarms were deliberately kept — they were the ones that matched nothing during the KPI-rollup outage, and their metrics are live again. Cost trimming is treated as a resilience decision, not a budget one: an alarm is kept when it's the only thing that would notice a silent failure.

Evidence — two outages the alarm layer now covers

The approval-sweep Lambda failed every 30-minute scheduled invocation for 12 days with an access-denied error on its GSI query — silently, because no Lambda-error alarm existed for it. It's a compliance function (timeout/cancel escalations); its job is to enforce governance, and it was down for twelve days without anyone noticing. Its alarm was added as a one-off, then generalized to every scheduled Lambda.

The KPI rollup Lambda failed 44 of 44 scheduled invocations over 30 days while its four business alarms — reading the very KPIs it publishes — sat OK under missing-data-as-health. The Lambda dying was invisible because the only alarms that existed watched its output, and no output looks exactly like healthy output.

A failure's journey through the five tools

The five tools aren't five answers to five different questions — they're five layers of the same answer, and a single failure passes through all of them. Here's one concrete path: an A2A call from the orchestrator to an agent that's throttling.

  1. The microkernel admits it. Inbound admission control sheds load with a 503 + Retry-After before the runtime ever reaches the model, so the throttled dependency isn't hit by more than it can take. The agent's steering guards and guardrail are fail-closed: a misconfigured guardrail means no call, not an unguarded one.
  2. The chokepoint retries it. invoke_agent_runtime applies tenacity retry with backoff and jitter, counts the attempt against the per-agent circuit breaker, and enforces the call timeout — while emitting agentcore.invocation_success and cost.usd regardless of the outcome.
  3. mcp-core and lambda-core shape the failure. If the agent's own MCP tool fails, safe_tool rewraps it as an opaque, traceable ToolError instead of a raw exception leaking back. If the node Lambda's body raises, guarded logs it, emits a <source>.failure metric dimensioned by exception class, and re-raises for the built-in async retry.
  4. The orchestrator recovers or escalates. If the call is a side effect, the idempotency key dedupes a retried attempt. If retries exhaust, the 12-field DLQ message goes through the outbox to both the queue and the immutable archive. If it's a classification step, the rule-based fallback runs — and rejects itself upward if it can't be trusted. If a negotiation is truly abandoned, saga compensation undoes what already committed.
  5. The alarm layer makes it loud. The node's AWS/Lambda Errors alarm fires on the topic, the fallback rejection count trips the quality alarm if fallbacks are happening too often, and the agent runtime's own error alarm catches the throttle at the source — because the metric that exists only when the system is alive is the thing being watched.

The throughline across all five layers is the same principle, applied at five different scopes: a failure must not be silent. Each tool exists because a failure once went silent at that scope — a crashlooping agent masked as fallback traffic, a handler with no exception handling at all, an MCP server whose check was a no-op, recovery machinery that was never wired in, a Lambda dying on its own schedule with no one watching. The tools are the mechanism; the incidents are the proof of what happens without them.

What we've learned

  • Resilience is a shared library, not a team culture. Every one of these tools replaced N hand-rolled, drifting, or missing implementations with one package. Culture tells people to handle failures; a shared tool makes it the default they can't accidentally skip.
  • Graceful degradation without an alarm is a silent-failure engine. The microkernel's model ladder and the orchestrator's fallback are good — but the week of masked crashloops proved that when degradation looks like normal traffic, only an error-rate alarm tells the truth.
  • An alarm that matches nothing looks healthy. The dimension-subset bug and the KPI Lambda's business alarms both sat at OK while covering nothing. The thing you watch must be the signal that exists when the system is alive — the invocation, not its output.
  • Missing data is not health. treat_missing_data = notBreaching is a footgun: the moment publication stops, every business alarm reads fine. That's why the scheduled-Lambda alarms watch the Lambda's own errors.
  • Machinery that isn't wired in is the same as machinery that doesn't exist. A zero-caller checkpoint function, a tenant check nobody populated, a zip that never bundled the module it imported — the failure modes that hurt most are the ones where the defense was built but never connected.

None of this makes failures disappear. What it makes them is visible, categorized, and recoverable — so that when one happens, it's an incident we can see and act on, not a silent divergence that compounds.
