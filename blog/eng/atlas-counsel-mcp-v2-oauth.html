ATLAS Counsel MCP v2: an OAuth resource server, built for broad exposure

Version 2 of our MCP server is an OAuth 2.1 resource server that cannot boot without a credential, cannot be told which tenant to act as, and cannot answer from a corpus the tenant never ingested. Each of those is now a property of the code rather than of a deployment's configuration — which is the difference between running a pilot and opening the door. None of it cost compatibility: the same endpoint still serves clients on both sides of the 2026-07-28 protocol change, so nothing in the field had to move.

When we wrote up ATLAS Counsel — the citation-first RAG agent that answers policy and contract questions — the authentication section described a rule we still consider load-bearing: tools never take a tenant_id argument, and identity is derived from a verified credential. That has survived intact into v2, and everything below is built on it.

What has changed is the deployment posture around it. v1 served pilot and demo deployments, where the credential was configured, verified, and known to the handful of people operating it. That is a perfectly reasonable place for a system to be while it is being proven, and it is not where this one is going. Broad exposure means many customers, many deploys, and callers who bring their own machine-to-machine credentials rather than a JWT someone minted by hand and sent over email.

At that scale, a security property that holds because an environment variable is set correctly is a security property with a failure mode. v2's work was moving every one of them into the structure of the service, and adding OAuth 2.1 with per-tenant Cognito credentials so that onboarding a customer is an API call rather than a key exchange.

The posture, up front

Five guarantees. What makes them worth stating is not that the service does these things, but that there is no configuration under which it does otherwise — each one is enforced by a construct that has no way to express the unsafe case.

auth
Authentication is mandatory. create_app raises unless a credential is configured, and no flag can relax it — the one that could has been deleted rather than defaulted.
tenant
Tenant identity is derived, never asserted. No surface — REST, WebSocket or MCP — accepts a tenant_id. Request models set extra="forbid", so a client that sends one gets a 422 naming the field rather than being served as whatever its credential maps to.
path
One resolution path. Every authenticated surface goes through _resolve_tenant — the HTTP middleware and the WebSocket handshake alike — so a new endpoint cannot grow a weaker rule of its own.
limit
Rate limits are per tenant. Auth-gated paths key on the authenticated tenant rather than the client address, so one customer cannot exhaust another's budget — including customers sharing an egress IP.
corpus
A tenant is answered from its own corpus or not at all. The retriever holds exactly one tenant's store and has nothing to fall back to. An empty corpus and an unreachable one are distinct, observable events.

The rest of this post is how each of those is built, and what it cost.

From pilot deployment to public surface

ATLAS Counsel's deployments have been authenticated throughout. Production set MCP_REQUIRE_AUTH=true, so every gated path required a credential, and the pilot corpora behind those paths belonged to tenants who had been onboarded by hand. The posture was sound for what it was serving.

It was, however, sound by configuration. The guarantee was a property of a particular deployment's environment rather than of the service, and that distinction is invisible right up until it matters. What changes at broad exposure is not whether the endpoint is protected — it was — but how many deploys, environments, and hands that protection now has to survive. A property held by one correctly-set variable does not scale to a fleet; a property held by the constructor does.

So v2 removes the choice. create_app raises if none of MCP_API_KEY, MCP_JWT_SECRET or MCP_OAUTH_ISSUER is configured, and _resolve_tenant denies unconditionally when nothing resolves. MCP_REQUIRE_AUTH is no longer read at all: once authentication is unconditional, a flag that could turn it off is not a feature, it is a way to get it wrong. A deployment now either has a credential or does not start.

Second-order effect

Making boot depend on deployment configuration broke import atlas_counsel.service.api — the module built the app at import time, so importing the package now required an auth setup. app became a PEP 562 module __getattr__, which constructs lazily on attribute access. uvicorn atlas_counsel.service.api:app is unchanged; import no longer implies a deployment.

We considered keeping a dev-mode escape hatch behind a new ATLAS_ALLOW_ANONYMOUS variable, on the grounds that local runs should stay frictionless. We rejected it as the same flag with a better name — the requirement was that no unauthenticated access exists, and an exception that exists for developers exists. Tests configure a credential instead, which turned out to be a two-line fixture change.

Three credentials, one choke point

OAuth is additive. The HS256 and API-key paths are unchanged and still accepted, because existing callers exist and a security upgrade that breaks them is a security upgrade that gets rolled back.

Credential 1 HS256 JWT Authorization: Bearer
tenant_id claim exp required optional aud multi-tenant
Credential 2 API key x-api-key
compare_digest → DEFAULT_TENANT single-tenant fallback
Credential 3 OAuth 2.1 — Cognito M2M Authorization: Bearer
RS256 via JWKS client_credentials client_id → tenant map RFC 9728 discovery

All three resolve through one function. That's the rule we care about most: a new endpoint cannot quietly grow a weaker rule of its own, which is exactly how /ask once ended up trusting a caller-supplied tenant_id. The HTTP middleware and the WebSocket handshake both call _resolve_tenant; nothing else may authenticate.

Two credentials share the Bearer scheme, so the order matters: HS256 is tried first, and if it doesn't verify and OAuth is configured, the same token is tried as an OAuth access token. Adding OAuth therefore disturbs no existing caller.

One detail there is worth more than it looks. Bearer credentials are matched on the scheme, not on a literal "Bearer " prefix:

scheme, _, credential = auth_header.partition(" ")
if (mcp_jwt_secret or oauth_verifier is not None) and scheme == "Bearer":
    if not credential:
        return None, "missing bearer token"

A prefix check on "Bearer " — with the trailing space — misses a header that is exactly Authorization: Bearer: no space, no token. Matching on the scheme catches it and returns an explicit missing bearer token. The empty-token case is the one worth handling deliberately, and it is precisely the one a prefix check drops through.

"Before you expose a multi-tenant endpoint broadly, every safety property it has should be one you could not switch off if you tried."

Cognito's M2M tokens don't have the claims you want

Here is where the protocol stopped helping. The textbook OAuth resource-server design is: verify the signature, check the audience, read the tenant out of a claim. Cognito's client_credentials access tokens support none of that shape.

What you'd want What Cognito M2M gives you Consequence
aud claim naming this resource No aud at all — it's an ID-token claim; access tokens carry client_id Pass no audience to jwt.decode
A per-tenant custom claim Not achievable — the pre-token-generation trigger does not fire for client_credentials Tenant comes from a map the app holds
Scopes that mean something per tenant One resource server, one invoke scope, shared by every client Scopes gate the surface, not the data

The first row has a sharp edge. Because we pass no audience, a token that carries an aud claim at all is rejected. Cognito M2M tokens don't have one — but Auth0 and Okta tokens do. Pointing MCP_OAUTH_ISSUER at either of those rejects every token, cleanly and confusingly. That's a real limitation, and we chose it deliberately rather than loosening the check: the verifier is Cognito-specific by design, and it says so in its own docstring so that the next person to read it doesn't discover it from a support ticket.

The second row is the one that shaped the architecture. Tenant identity cannot come from the token, so it comes from a client_id → tenant_id map the application resolves itself. An unmapped client is rejected even with a perfectly valid signature.

We considered simply using the client_id as the tenant id — fully dynamic, no map, no table. It fails on three counts: Cognito client ids are mixed-case opaque strings that don't pass our tenant-id validation, tenant ids would stop being names anyone chose, and rotating a client would orphan that tenant's stores.

The verifier never raises

claims = jwt.decode(
    token, key=key, algorithms=["RS256"], issuer=self._issuer,
    options={"require": ["exp", "iss", "client_id"]},
)
if claims.get("token_use") != "access":
    return None
tenant = await self._client_tenants.resolve(claims["client_id"])

Any decode failure, unknown key id, JWKS fetch error, or unmapped client is a None return, not an exception. That keeps the call site simple, and it creates the one operational problem you'd predict: a bare None is impossible to diagnose in a deployment. So every rejection logs its reason at DEBUG — which sounds trivial and was, in fact, one of the fixes that came out of reviewing the implementation against its own plan.

Where the map lives, and why that moved the validation

The first version of the map was a JSON blob in an environment variable. It worked, and it made onboarding a tenant into a deploy: edit the ECS task definition, mint a new revision, restart the service. For a product whose pitch includes "start using it today," that's a bad shape.

So there are now two implementations behind one ClientTenantSource protocol:

StaticClientTenantsDynamoDBClientTenants
SourceMCP_OAUTH_CLIENT_TENANTS JSONMCP_OAUTH_CLIENT_TENANTS_TABLE
OnboardingEdit task definition, redeployWrite a row
ValidationOnce, in create_appOn every resolve
Good forSingle-tenant, air-gappedMulti-tenant production

That third row is the part I'd point at if you only read one paragraph of this post. When the map was an environment variable it was operator configuration — checked once at boot, because that's when it enters and it cannot change afterwards. As table rows it is runtime data that can change underneath a running process, so validate_tenant_id runs on every resolve.

The rule didn't change. The value moved, and the validation followed it. This matters downstream in a way that isn't abstract: a tenant id is interpolated into a CREATE SCHEMA DDL string and used as a filesystem path component. Validating operator config at boot also has a specific payoff — a typo authenticates fine and surfaces as a tool-level error on a customer's first call, with the deploy showing green.

Caching a lookup that an attacker chooses the key for

The table is read per request behind a ~30 second TTL cache, through asyncio.to_thread because boto3 is blocking and shares the event loop with every other request in the process.

Both hits and misses are cached. The miss is the important one: the caller picks the client_id in its own token, so caching only hits would let anyone drive one DynamoDB read per request by inventing client ids. Yes, the signature is verified before the lookup — but a valid signature from a client that maps to nothing is exactly the case we're describing.

On a DynamoDB failure, a still-cached entry is served even if expired. An outage should not sign out tenants that were already resolving. A client with nothing cached is denied — so the failure mode is open for the already-known, closed for anything new, which is the direction we want.

Why we didn't use the SDK's auth wiring

MCP's Python SDK ships a TokenVerifier / auth= mechanism. It is the obvious thing to adopt, and we extended our own middleware in place instead. The reason is specific and, I think, generalisable.

The SDK resolves identity inside the mounted sub-app. Our rate-limit middleware runs outside it. Starlette inserts middleware at position 0, so the last-registered middleware is outermost — our auth middleware is registered last, runs first, and has already set the tenant context by the time the rate limiter executes. That ordering is exactly what lets the limiter key by authenticated tenant.

Adopting the SDK's wiring would have moved identity resolution to after the rate limiter, which would have silently dropped /mcp back to per-IP rate limiting for every OAuth caller. Silently: no error, no log, just a security property quietly relaxed — the same bug as the first card above, but permanent and by design.

Architecture note

Keeping one choke point has a second payoff. /health/deep and /mcp stay on a single auth path, so an OAuth-only deployment has a credential that reaches the deep health check. Under the SDK's model, auth would live inside the MCP sub-app and /health/deep would need its own — a second implementation of the rule we spent this whole redesign consolidating.

The general form: a framework's auth integration point is only correct if it sits at the same layer as everything else that depends on identity. Ours doesn't, so we didn't use it.

Discovery, so a client can find its way in

A resource server that requires OAuth but can't tell you where to get a token is a resource server you configure by email. RFC 9728 fixes that, and MCP's auth spec builds on it.

One exemption is worth naming: CORS preflight. Browsers never attach Authorization to an OPTIONS preflight, so gating it would make /ask unreachable from exactly the browsers our CORS configuration exists to serve. The preflight reaches no handler and reads no tenant data.

And one that looks like an exemption but isn't: /ws/ask authenticates inside the handler rather than through the HTTP middleware. Starlette short-circuits HTTP middleware on any non-http scope, so listing the WebSocket path as gated would look exactly like protection and provide none. It calls the same _resolve_tenant and closes with 1008 on failure — the WebSocket analogue of a 401.

MCP SDK 2.0, and serving two protocol eras at one endpoint

The same change moved us to mcp>=2.0. FastMCP is gone; build_mcp_server() now returns an MCPServer, and host and path moved onto streamable_http_app() and run().

Two version numbers move independently here, and they are worth separating before they collide. mcp>=2.0 is the SDK the server is built on; the protocol revision is what a client negotiates on the wire. Upgrading the first dropped nothing from the second — both eras are served at the same /mcp/ endpoint: the classic stateful initialize handshake, and the 2026-07-28 stateless per-request envelope selected by the mcp-protocol-version header. A client on either one is served as it is, and neither is a migration anyone has to schedule.

The recency is the point. The 2026-07-28 revision went final on 28 July 2026, replacing 2025-11-25 — the largest change to the protocol since authorization was added, and the one that made it stateless at the transport layer. Ten days is not long enough for an installed base to move, and the spec's own deprecation policy holds features functional for at least twelve months after they are marked, so the stateful handshake is not a legacy path being tolerated. It is what most clients still open with.

Three mounting details are load-bearing enough to be worth stating plainly, because each one cost us a debugging session:

  • The mount uses streamable_http_path="/". The SDK's own default is /mcp, so mounting it at /mcp puts the endpoint at /mcp/mcp.
  • /mcp/ with the trailing slash is canonical. Starlette 307-redirects a bare /mcp, and not every client follows a redirect on POST.
  • host is passed through because the SDK validates the request's Host header against it as DNS-rebinding protection. Its default of 127.0.0.1 rejects everything behind API Gateway with a 421.

And the session manager is started from the app's lifespan, because Starlette's Mount does not forward lifespan events into a mounted sub-app. Without it, every MCP request fails with "Task group is not initialized."

That compatibility is asserted rather than assumed. The transport tests drive both eras against the same endpoint — the handshake and the stateless envelope alike — so an SDK bump that quietly stopped serving one of them fails in CI rather than in a customer's client. One endpoint, two protocol eras, both covered, which is what you want when clients in the wild are on both.

Authentication was only half the problem

A tenant that authenticates perfectly and then reads someone else's documents is not a tenant you have isolated. Two changes landed alongside OAuth, and the post would be dishonest without them.

Corpus or nothing. A FallbackRetriever sat in front of the per-tenant stores and degraded to an in-memory index of the shipped demo corpus whenever the real store raised. A tenant whose index was missing — or whose store was briefly unreachable — got confident, cited answers assembled from documents it had never ingested. The latch was per-process and sticky, so it stayed that way. It is replaced by a retriever that holds exactly one tenant's store and has nothing to fall back to, and the two failure modes are now deliberately distinct: never ingested raises CorpusNotProvisioned and the agent refuses for lack of grounding; unreachable propagates, because an outage must not be indistinguishable from an empty corpus.

Ingestion over the authenticated surface. Loading a tenant's corpus used to be an operator task. It is now a counsel_ingest tool call on the same endpoint the tenant queries, which means it inherits the entire auth stack above — the credential set, the tenant binding, the per-tenant rate-limit bucket — with no separate path to keep correct. The tenant is current_tenant; there is no argument to name another one with.

That tool replaces rather than merges. Re-ingesting a document under the same doc_id deletes every previously indexed span of that id first:

ingest(acme-msa, 5 spans)   -> 5 chunks
ingest(acme-msa, 3 spans)   -> the 2 dropped spans are GONE from the index

Upserting by chunk id would leave those two spans retrievable and citable, so an answer could quote a clause the tenant had deleted, with nothing in the response revealing it. Replacement also makes a half-applied batch converge: there's no transaction across documents, so a mid-batch failure names what was applied and what failed — and re-sending the whole batch rewrites the applied documents to the same state.

Onboarding a tenant is now three steps, none of which require a restart: create the Cognito app client, write the client_id → tenant_id row, ingest that tenant's corpus. Live within the ~30 second cache TTL.

Trade-offs we accepted

Each of these is a decision with a cost attached, taken deliberately and with a mitigation we can point at. They are listed because a security posture you can only describe in the positive is one nobody has stress-tested.

DecisionCost, and what absorbs it
A stateful AWS resource on the auth path. DynamoDB being unreachable now affects OAuth callers. The TTL cache serves stale entries through an outage, so tenants that were already resolving keep working. A client with nothing cached is denied — the correct direction, and still an outage.
Onboarding without a redeploy means access control is no longer wholly in version control — a row written out-of-band is invisible to terraform plan. Accepted knowingly: being able to write the table between applies is the capability. Terraform still seeds and reviews the tenants this stack provisions, and the table's point-in-time recovery and audit trail become load-bearing rather than incidental.
Corpus-or-nothing means an un-ingested tenant authenticates successfully and then refuses every question. The honest failure, and preferable to the alternative it replaced — answering from someone else's documents. The cost is that a skipped onboarding step looks like a broken product rather than an error; the runbook calls it out, and nothing yet enforces it.
Two client-tenant sources behind one protocol. A second path to keep correct. Kept because the static map is genuinely the right choice for a single-tenant or air-gapped deployment, not because it is legacy.
One invoke scope, so any credential that can call counsel_ask can also call counsel_ingest. A known gap, named here rather than discovered later. The resource server is already the right place to split read from write, and that is the next increment on this path.
Removing MCP_REQUIRE_AUTH is breaking for anything that set it, and for local runs that relied on no credential at all. The variable is documented as ignored — deliberately kept in the reference so its absence reads as a decision rather than an oversight. Infra drops it in the same change.
Net position
The service cannot boot without a credential, cannot be told which tenant to act as, and cannot answer from a corpus a tenant did not ingest. Those hold by construction now, not by configuration, which is the bar an endpoint has to clear before it is opened to customers who bring their own credentials. The price is a DynamoDB dependency on the auth path and an access-control surface that no longer lives entirely in Git — both taken with open eyes. What it did not cost is reach: clients on either side of the 2026-07-28 protocol change are still served at that one endpoint.

What generalises

Four things here would apply to any MCP server growing real authentication.

Validate where the value enters, and re-check when it moves. The same map validated at boot as config and per-resolve as data. The rule is stable; where it applies is not, and moving a value between layers silently moves its validation requirement with it.

A framework's auth hook is only correct at the right layer. The SDK's TokenVerifier is well-designed and wrong for us, because identity had to be resolved outside a middleware that depends on it. Check what else in your stack reads identity before adopting one.

Caches whose keys an attacker chooses need miss caching and refresh limits. Both the JWKS cache and the client-tenant cache had this shape, and both were amplification vectors until they didn't. The signature check doesn't save you when the expensive lookup happens first.

Make the safe posture the only posture. Any control that a flag can disable is really two controls: the mechanism, and the discipline that keeps the flag set across every environment and every future deploy. The mechanism is the part you can test. Before broad exposure, it is worth going through each safety property and asking which of the two is actually holding it up — and moving anything in the second column into the first.
