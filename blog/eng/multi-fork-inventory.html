Dozens of forks, one codebase: find out what each fork does

A playbook for consolidating a multi-fork SaaS, starting with the step everyone wants to skip: an inventory you can trust.

TL;DR

The problem. A Java and Spring Boot SaaS has dozens of customer forks. They're branches of one repository, they all compile, and every one serves tenants who depend on how it behaves today. The goal is one codebase, with every tenant keeping its current behavior and each change switched on one variant and one tenant at a time.

What you get. The first stage of the playbook, the inventory. A deterministic pipeline measures every fork, fingerprints what it does, and classifies each difference against both the point where the fork split off and the base as it is today. AI then names each difference as a behavior, under a judge that decides what is new.

Why it's worth your time. A plain fork-vs-base diff makes every stale fork look heavily customized. A three-way comparison separates the mechanical catch-up work from the real divergence that needs a decision, and that's what keeps the program small enough to finish.

Status. This is a design, written before I read a line of the code it targets. The pilot gates at the end are what it has to prove before it scales.

Part 1 of 3. Part 2 turns the inventory into a variability model and proves behavior is preserved with production traffic. Part 3 covers cutting tenants over, including the ones whose contracts make every change a separate event.

The situation is common after an acquisition. The product was built by a small company that sold customization. Each large customer asked for something slightly different, there was no extension seam in the core, so someone created a branch. Years later there are dozens of branches, each deployed for its own customers, and the team that inherited them can't say what makes one different from another.

Every fix now has to be applied dozens of times. Every platform upgrade is dozens of upgrades. The obvious move is to merge the forks back, and the obvious move fails, because nobody knows what any of them actually does.

Copying code to vary behavior is the root cause of the multi-fork problem. Any plan that doesn't stop new copies just schedules the next consolidation.

Before the technique: four causes and one question

Forks are a symptom. They usually have four causes, and only the first is technical:

  • Technical. The core has no seams, so customizing means editing it, and editing it means a branch.
  • Commercial. Customization was sold as a feature. Contracts may promise specific behavior.
  • Knowledge. The original team took the why of each difference with them. The current team has the code without the mental model.
  • Governance. If sales or account management can still promise bespoke behavior, a new fork appears after every convergence.

So the first question isn't technical either. What does the owner intend to do with the product? The answer picks the approach:

IntentApproach
Invest and growFull convergence: one core with extension points
Keep it running for a few yearsStabilize only: automate patch propagation across forks, no plugin platform
Move customers to another productDon't converge. Catalogue each customization as a migration requirement

The rest of this series assumes the first row. The inventory is useful in all three, though: you can't migrate, stabilize or converge what you haven't catalogued.

The target, the constraints and the principles

The target is a single codebase. In the end-state this playbook was designed for, it runs as one shared multi-tenant deployment. Every tenant keeps its current behavior, and changes are switched on one variant and one tenant at a time.

The constraints that shape everything below:

  • The forks are branches of one repository with shared history, and they all compile. If yours are separate repositories, add them as remotes first; the rest still holds.
  • "Base" means the version new customers get today, not the forks' common ancestor. The base kept evolving after each fork split off, and that one fact drives most of the design.
  • Production traffic and logs can be captured per fork.
  • Some contracts or risk profiles require each variant to be switched on separately in production (Part 3).
  • The AI tool is OpenAI Codex. The ideas carry over to any agent that can run headless against a working copy and return structured output.

And six principles, which the stages below keep coming back to:

◇
What, not how

Concepts describe what the system does. The same concept can have different names and code in different forks.

◎
Snapshot first, commits second

Compare what each fork does today. Use history only to trace where a change came from.

⑂
Git decides who; AI decides what

Who changed something is a deterministic Git question. What the change means is the only question AI gets.

#
Never analyze the same code twice

Cache every result by a fingerprint of the content. A variant shared by twelve forks is analyzed once.

✓
Preservation is proven

Behavior preservation is shown with production traffic and tests, never assumed from a clean diff.

↺
Small and reversible

Every production change is small, and a single switch rolls it back.

Stage 1 · The census comes before any AI

Measure first. The census is cheap, deterministic, and it decides the order and the budget of everything after it.

Give every fork its own working copy with git worktree add. All worktrees share one object store, so dozens of checkouts cost little more than one. Then record, for each fork:

git merge-base base forkX               # split point, and that commit's date
git rev-list --count base..forkX        # commits ahead of the base
git rev-list --count forkX..base        # commits behind the base
git diff --name-only $(git merge-base base forkX) forkX | wc -l   # files the fork changed

Three more things come out of the census:

  • The fork tree. Forks often descend from each other. Two forks that share commits the base doesn't have are parent and child, and parents are processed before children. Don't detect this from split points alone: a child fork usually has the same split point from the base as its parent, so that rule misses exactly the cases you're looking for. Forks with a recent split point are the ones that merge the base regularly.
  • The platform spread. Java, Spring Boot and key library versions per fork, resolved from the build, not just declared. Only the base moves to the target platform. The spread sets the normalization rules for fingerprints in Stage 2 and the cost of any fork that has to catch up in place.
  • The tenancy model. How each fork identifies tenants, which tenant-level configuration tables it already has, the database engine and topology, and how many tenants each fork serves.
Reuse this

Measure every branch with worktrees, merge-base and ahead/behind counts before spending a cent on AI. Size and staleness per fork give you a processing order (closest first) and a budget, and they're a few lines of shell.

Stage 2 · An inventory with no AI in it

A small Java CLI splits each fork into functional units and fingerprints them. It's built on JavaParser, with the symbol resolver pointed at each fork's compiled classpath from Maven or Gradle. Each fork is delomboked first, and its generated sources (MapStruct mappers, other annotation processors) are included, so the parser sees the code that actually runs.

The units it extracts:

Unit 1 Entry points where behavior starts
controller methods @Scheduled jobs @KafkaListener · @RabbitListener · @JmsListener @EventListener Spring Batch jobs ApplicationRunner Feign · WebClient clients
Unit 2 Domain units data and switches
JPA entities Flyway · Liquibase migrations @ConfigurationProperties @ConditionalOnProperty
Unit 3 Call slices what each entry point reaches
application packages only interface calls → every implementation
Unit 4 Behavior outside method bodies the part diffs of Java code miss
application*.yml per profile @Query · derived queries templates · message bundles security config filters · interceptors · aspects

The fourth layer matters more than it looks. A fork that changed only a property value, a derived query method name or an interceptor changes behavior without changing a single method body. Spring Data's derived queries don't even have a body.

Three fingerprints per method

FingerprintCoversCatches
StrictThe body, without comments or formattingAny real code change
LooseThe body with local variable names normalizedTells a rename-only change from a real one
DeclarationSignature plus method and class annotations with their valuesA changed @PreAuthorize, @Transactional, @Query or @Cacheable on an identical body

Package moves such as javax.* to jakarta.* are normalized before fingerprinting. Otherwise the base's platform upgrade would look like a change in every fork.

Not every point in history needs the full treatment. The base and each fork's head get the compiled inventory. Each fork's split point only needs method fingerprints, and fingerprints need parsing, not compiling, so the files are read straight out of Git with git show <split>:<path>. That matters, because years-old commits often won't build with today's toolchain.

Static analysis can't see Spring's wiring, so ask Spring

Conditional beans, aspects, interceptors and the links between an event publisher and its listeners are decided at runtime. Each fork's application context is therefore also booted in a test harness, with a Testcontainers database and stubbed outbound calls, and the harness dumps its beans, condition report, request mappings and advisors. That's the same data Actuator exposes at /beans, /conditions and /mappings, captured without touching a single production deployment.

The dump adds the framework-invoked edges to the call slices. Its request mappings also become the ground truth for coverage: if the parser found fewer entry points than Spring registered, the inventory has a hole, and the pilot will catch it.

If call resolution turns out slow or imprecise, SootUp over the compiled bytecode is the fallback for the call graph.

Reuse this

Fingerprint declarations separately from bodies, and inventory what lives outside method bodies. Then boot each variant's Spring context in a test harness and use its request mappings as the ground truth your static inventory has to match.

Stage 3 · Compare every fork three ways, not two

This is the idea the rest of the playbook stands on.

The base kept changing after each fork split off. Diff a fork against today's base and every change the base made since the split shows up as a difference, as if the fork had made it. A fork that is merely five years stale looks like the most customized one in the portfolio.

So each unit is compared at three points:

The comparison runs per method, on fingerprints, and rolls up into functional units. Every combination has a meaning and a set of commits to record:

MBFStatus for the forkHashes recorded
xxxsamenone
xyxstale the base changed it after the splitbase commits (M..base)
xxycustomized the fork changed itfork commits (base..fork)
xyyconverged same result on both sidesboth, linked by patch-id
xyzdivergent both changed it, differentlyboth

presentpresent—removed by the forkthe fork commit that removed it
present—presentlegacy the base removed it, the fork kept itthe base commit that removed it

Rows with a blue tag are catch-up gaps: the fork simply never received the base's changes. That's mechanical work. Shaded rows are real divergence: the fork genuinely differs, and someone has to decide what happens to that behavior. A two-way diff can't tell these apart, and in forks that are years old the first group can easily be the larger one.

Two traps

  • Shared helpers. A change in a common service changes the fingerprint of every entry point that calls it. Group methods that changed together (by class and by commit) and analyze each group once, with the affected entry points as context, instead of once per entry point.
  • Moved methods. A method moved to another class looks like a removal plus an addition. RefactoringMiner flags moves and renames so they're read as what they are.

Results are deduplicated across all forks by content hash. A variant shared by twelve forks is analyzed once.

Reuse this

Whenever two branches have both moved on, classify against the merge-base as well as both heads. Stale and customized are different kinds of work with different owners, and only the three-way view separates them.

Stage 4 · Provenance: a SHA says where, a patch-id says what

Every piece of evidence carries two hashes. The commit SHA says where the change came from. The patch-id says what the change is. After a cherry-pick, rebase or squash, the same change has a different SHA in every fork it reached, so SHAs alone would report differences that aren't there.

git blame M..base  -- <file>              # base-side changes, on the changed lines
git blame base..forkX -- <file>           # fork-side changes; older lines show as boundaries
git show <sha> | git patch-id --stable    # what the change is, independent of its SHA
git log --cherry-mark --left-right base...forkX   # commits equivalent on both sides

On the fork side, lines unchanged since the split show up as boundary lines, so older history drops out by itself.

First appearance comes from Git, not from processing order. Among commits with the same patch-id, take the earliest author date: cherry-picks keep the author date and change the committer date. Then pick the fork closest to the root of the fork tree that contains it (git branch --contains). That also catches features that were born in a fork and later carried into the base.

Provenance runs before any concept extraction. It's deterministic Git work, and its output, the commit messages and ticket IDs behind each change, tells the AI in the next stage why a fork changed something.

Reuse this

Key change identity on git patch-id --stable, not the SHA, and date it by author date. It's the only way to recognize the same fix after it has been cherry-picked into a dozen branches.

Stage 5 · AI proposes, a judge decides

Start with the base

The base is processed first, from its current head, so the concept hierarchy uses the vocabulary of the version new customers get.

  • For each functional unit, Codex extracts leaf concepts: a few-word name and one sentence that explains it.
  • Embedding-based clustering groups leaves into features, and an LLM names each group. A second pass groups features into capabilities.
  • People review the top two levels in full. Every fork's results are hung on this tree, so this is where review pays off most.

Every concept follows three rules. It has a stable ID and a list of aliases; IDs are never deleted, and merged concepts become redirects. It sits at one level of a fixed rubric (capability, feature or rule), and the rubric with a few examples goes into every prompt. And it describes behavior, never implementation.

Then the forks, but only what differs

Only code that differs from the base reaches the AI, and the extractor never creates concepts directly. There are two kinds of analysis, both cached:

  • Base-side changes (stale, not received, legacy): what the base added or changed since the split. The cache key is the pair (old version, current version), so forks that split at the same point share one analysis.
  • Fork-side changes (customized, fork-only, removed): Codex sees M → F, with B as context. Divergent units get all three versions, like a merge conflict.

Extraction runs as codex exec in the fork's worktree, read-only, with --output-schema so the answer is strict JSON. Its input is the method group's versions, the concepts already linked to it in the base, and the commit messages and ticket IDs from Stage 4. Its output is one of three things: the same concept, a variant (with the behavioral difference and concrete values), or new concepts. Before proposing anything, Codex can search the concept store through an MCP server (search_concepts, propose_concept, attach_evidence), which stops most duplicates at the source.

Then the judge:

embed
Embed the proposal
Name, description and aliases of each proposed concept.
search
Find the nearest existing concepts
Postgres with pgvector.
judge
Decide: same, variant, narrower, broader or new
With a confidence score. A plain structured-output API call; the judge needs no repository access, so it's far cheaper than an agent run.
✓ confident → recorded with its evidence
✗ low confidence → human review queue

A few operating rules keep this honest:

  • One run per method group or unit, never "read the whole fork".
  • Stable rules go in AGENTS.md: what versus how, the level rubric, naming style. The extraction procedure goes in a skill.
  • Pin the model and record the prompt version on every result, so you know which rubric produced which concept.
  • Keep a test set: about 50 units across two forks, hand-labeled with their correct concept. Rerun it after every prompt or rubric change and track match accuracy.
Why split proposing from deciding

An extractor that can create concepts will create a new one whenever it phrases a familiar behavior differently, and the hierarchy drifts into duplicates. Making creation a judged decision, with a confidence threshold and a human queue, turns that drift into a measurable rate you can tune.

Stage 6 · Reconcile, then read the matrix

Processing the base first means its vocabulary shapes the tree. A later fork can reveal a missing parent, or show that two existing concepts are really one. So the hierarchy is reconciled every five forks or so:

  • Embedding similarity within each level flags near-duplicates.
  • The judge proposes merges, splits or moves.
  • People approve them as a pull request against the hierarchy's YAML export, versioned in Git.

The output is a concept × fork matrix: one row per concept, one column per fork, each cell holding its Stage 3 status. Read it two ways. By cell type, it splits the work into catch-up gaps (stale, not received) that are mechanical, and real divergence (customized, fork-only, removed, divergent, legacy) that needs decisions. By row, it sorts concepts into universal, majority and fork-specific, and shows how alike the forks really are.

It's also the program's burn-down chart. Every cell that isn't "same" is work left, and because every analysis is cached by content, rerunning the whole inventory weekly costs little more than analyzing the week's new commits.

What the pilot has to prove

None of the above should run on dozens of forks first. An inventory pilot runs it on the base plus two forks, the closest and the most distant by the census, and checks four things before adding more:

CheckAgainst
Inventory coverageEntry points found vs. request mappings and listeners in each fork's context dump
Match accuracyThe ~50 hand-labeled units
CostAI calls and spend per fork
The rubricFixed before any fork is added, so later results stay comparable

If coverage is low, the parser is missing a kind of entry point; fix that before trusting any count. If match accuracy is low, fix the rubric and the prompt against the labeled set, not against the forks.

What the inventory is for

The matrix isn't the goal. The goal is a list of every distinct behavior the unified code has to reproduce, with enough detail to design how it varies: not "the reminder cadence differs" but "7 days here, 15 days there", which is already the future configuration of each fork.

That's where Part 2 picks up: turning concepts into variants with concrete values, handling variants that leave work in flight, choosing the smallest variation mechanism that fits each difference, and proving with production traffic that a tenant's behavior survived the move. Part 3 covers the cutover itself, including tenants whose contracts require every change to be switched on separately, and the governance that stops the forks from growing back.

The inventory is the unglamorous part, and it's the part that decides whether the rest is engineering or guesswork. Git decides who changed what; AI only decides what a change means; and every claim either one makes is checked against something it can't fake: a booted Spring context, a hand-labeled set, or production traffic.
