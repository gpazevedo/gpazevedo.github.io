What Fails Next

Building an ingest client for 50 million records, one failure at a time.

TL;DR

The problem. Read fifty million records out of a cursor-paginated HTTP API and land every one of them — over hours, at high throughput, against a server that rate-limits, stalls, serves malformed rows, and changes while you are reading it.

What you get. A working consumer, built in eleven stages, each one added because the previous version broke against something specific at scale: streaming pagination that never buffers, a retry policy rather than a retry loop, validation split in two, checkpoints that survive SIGKILL, a worker pool whose watermark cannot skip a page, proactive rate limiting, sharding across parallel walkers, and detection for a dataset that mutates mid-walk.

Why it is worth your time. The failure modes here return exit code 0. Every stage carries the live numbers that prove it, reconciled against a server that counts independently — so no claim in this post is the client grading its own homework.

Part 1 of 2 — this half is about getting the data out. Part 2 is about saving it.

The brief is ordinary: read every record from a cursor-paginated API and land it somewhere. Fifty million rows. Write it.

Almost every version of this ever written works on the first ten thousand records and is wrong about the rest.

Not wrong in a way that raises — wrong in a way that returns exit code 0 and a number nobody checks.

The code in consumer/ was not designed and then written. It was built eleven times, and each version exists because the previous one broke against something specific. The git history is that sequence, one merge per stage, each carrying the tests that pass and the numbers a live run produced against an adversarial mock server that is trying to make the client look good.

Anyone can write a client that reports success. consumer/server/server.py keeps its own counters — rows served, malformed rows injected, retries by status, duplicate pages, distinct shards seen — and every claim the client makes has a counterpart there that it cannot fake.

Part I — The walk itself

Stage 1 · Peak memory is one page, and that is a promise

The first version returns a list. It is also the last version that fits in memory.

iter_pages is an async generator, and that is an interface commitment, not an optimisation. The moment it accumulates and returns, the job is capped at RAM, and no cleverness downstream recovers it. A test pulls exactly one page from a three-page walk and asserts that exactly one request was issued. If the generator ever buffers, that test reads 3.

Four commitments are made here. Each one is a line or two of code, and each one is collected on later.

Invariant 1 Stream, never buffer iter_pages — async generator
peak memory = one page test asserts 1 request, not 3
Invariant 2 Unpack before the emptiness check only the cursor states the contract
empty page + live cursor full page + null cursor
Invariant 3 Yield the cursor that follows collected at stage 4
persist progress after durability
Invariant 4 The cursor is opaque collected at stage 11
never decoded never incremented handed back verbatim

The unpack happens before the emptiness check. A last page can be empty with a non-null cursor, or full with a null one. Only the cursor states the contract — terminating on the payload is a guess about it.

Each page is yielded with the cursor that follows it. Three stages later, that is what lets progress be persisted after a page is durable rather than before.

And a rule that looks like pedantry for ten stages: the cursor is opaque. Never decoded, never incremented, only checked for truthiness or handed back verbatim. It costs nothing. We will collect on it at the very end.

Reuse this

Make the pager an async generator and treat the cursor as opaque — never decoded, never incremented. Peak memory stays at one page whatever the dataset size, and a later server-side switch to keyset pagination costs you one URL.

Stage 2 · A hostile network is the normal case

At fifty million rows, a 503 is not an exception. It is a Tuesday.

The retry loop goes in one place — ApiClient.get_json — so iter_pages never learns that retries exist. A page that 500s once is retried underneath it and yielded as though it had succeeded on the first try.

The interesting part is what is not retried.

StatusReadingPolicyWhy
429 rate limit retry The server is asking. Back off and come back.
500 · 502 · 503 transient retry The condition that caused it may not survive the wait.
501 terminal, despite 5xx stop Not Implemented is a permanent statement about an endpoint.
401 · 403 terminal stop Six attempts against a 401 burns quota on a bug retries cannot fix.

That is the difference between a retry policy and a retry loop.

Backoff is full jitter — random.uniform(0, ceiling), not a fixed exponential. The exponential bounds the worst case; the randomisation is what stops every concurrent retry waking on the same tick and re-triggering the limit that caused them.

delay = random.uniform(0, min(cap, base * 2 ** attempt))
log.warning("retrying in %.2fs", delay)   # the number logged ...
await asyncio.sleep(delay)                # ... is the number slept

Two small properties are held structurally, because both are easy to break in ways that produce a plausible-looking log.

◷
The delay logged is the delay slept

One number, logged and slept by the same call. Sampling the distribution a second time to build the message produces a retry log that is fiction.

↑
Giving up raises the underlying fault

The caller sees httpx's own exception, not a wrapper. When it eventually fails at 3am, the traceback names the thing that actually happened.

Reuse this

Put retries in one funnel underneath the iterator, and make retryable-versus-terminal a policy rather than a status-code range. Full jitter, honour Retry-After, and log the delay you actually slept.

Stage 3 · Bad data is not an error

Somewhere in fifty million rows is a record with no attributes. If that stops the run, the run never finishes.

But if everything is tolerated, a client pointed at the wrong endpoint cheerfully reports "50,000,000 rejected" and exits 0.

So there are two levels, and keeping them apart is the stage.

⊗
Protocol violation — stop

payload["data"] missing or not a list. The API changed or the URL is wrong. There is nothing to walk.

⊕
Data quality event — keep walking

One row missing attributes. Log it with the row and the reason, and carry on to the next one.

Conflate them and one bad row looks like a broken API, while a broken API looks like one bad row.

Falsifiability

Every reject carries the row and the reason, because a count alone is not falsifiable. "9,957 rejected" reads equally plausible whether the validator works or whether it looks up rec["atributes"] and quietly rejects the entire dataset. Letting Python name the fault is what makes the number checkable — the typo reads back as KeyError: 'atributes' beside a record that plainly has its attributes.

Reuse this

Split validation in two: a bad envelope stops the run, a bad row is logged and skipped. Every reject carries the row and the reason — a bare count is not falsifiable.

Part II — Surviving the environment

Stage 4 · The checkpoint that lies

A job that runs for hours in an environment where things die every few minutes may never finish. So: persist the cursor, resume from it.

⚠
A half-written checkpoint

Resumes from a cursor that was never valid, which is worse than having no checkpoint. So the write is atomic.

⚠
A checkpoint left behind

Resumes the next run from the end and ingests nothing, successfully. So it is discarded only on a clean finish.

But the real content of this stage is an ordering:

Rejects durable, then the cursor advances.

Resume is what makes an offset unrevisitable. Once a cursor past page N is on disk, a crash can never revisit page N — the next run starts after those records. A reject still in RAM at that moment is gone for good. A test spies on every checkpoint write and asserts that the page's rejects were already on disk.

That rule gets broken twice more, in two different disguises, and it is the same rule every time: the checkpoint must never advance past durability.

Reuse this

Write the checkpoint atomically (temp file plus os.replace), discard it only on a clean finish, and never let it advance before the rejects it covers are on disk.

Stage 5 · Stopping on purpose

A hard crash is rare. A SIGTERM from a deploy is Tuesday again.

The handler cancels the walk, the exit flush runs in a finally, and the process exits non-zero — because an orchestrator that reads exit 0 as "the dataset is ingested" moves on without it.

The cancellation is absorbed and returned as a boolean rather than re-raised. "We were told to stop" and "we broke" both exit non-zero, but only one of them is a bug, and an exception cannot tell them apart.

0
The dataset is ingested. The only honest use of this code — and the one every silent failure mode in this post counterfeits.
143
The OS killed us. Nothing was flushed on the way out.
1
We left deliberately. Heard the signal, flushed 11 pages, wrote the cursor. The next run resumed from it and finished the other 19,000 records, with duplicate_pages=0.
The exit flush is wrapped in asyncio.shield, and the honest note in the source says it is correct but not yet exercised — the flush is synchronous, so there is no await inside for a second cancellation to land on. It starts mattering two stages later. Writing that down was cheaper than pretending.
Reuse this

Catch the signal, cancel the walk, flush in a finally, and exit non-zero. Exit 0 tells an orchestrator the dataset is complete, and it will move on without it.

Part III — Widening the pipe

Stage 6 · Measure first, and mean it

This stage adds no capability. It exists because the next three are unfalsifiable without it.

Every counter has a counterpart the server keeps independently. Neither tally is derived from the other, so a disagreement is a bug rather than a difference of opinion.

Throughput
records
records_served
What the client parsed, against what the server put on the wire.
Data quality
rejects
malformed_served
What the client refused, against what the server deliberately corrupted.
Resilience
retries
by_status
What the client re-issued, against what the server saw arrive, per status code.

Then the numbers say something nobody planned. Against a rate-limited server the client reached page 17 of 30 and died on the seventh 429 — and its own retry count read six where the server counted seven.

Six or seven

Not a bug: the seventh 429 exhausted the retries and raised, and the attempt that gives up is not a retry. A design decision, confirmed against an independent tally, in production conditions.

That death is also the stage-9 motivation, measured rather than asserted.

Reuse this

Add counters before you tune anything, and give every one a counterpart the other side keeps independently. A disagreement is then a bug rather than a matter of opinion.

Stage 7 · The sink is slow, and now the checkpoint lies again

Fifty million single-row inserts outlast your patience regardless of fetch speed. So rows buffer and flush on size or age.

And immediately, processed stops meaning durable.

If the checkpoint advances when rows enter the buffer, it certifies records that are sitting in RAM. Crash, resume, and they are gone — the checkpoint is lying, which is worse than not having one. So marking progress moves into the flush path, and the flush becomes one ordered breath.

first
Rejects to disk
The reject log for the batch lands before anything else is considered done.
✓ a crash here loses nothing that was counted
then
Rows to the sink
The buffered batch is written and acknowledged.
✓ processed now means durable
last
The cursor advances
Only now is the checkpoint allowed to move past this batch.
✓ resume can never skip a record the checkpoint certified
✗ reverse any two of these lines and a test fails

Same invariant as before, broken a second way.

Two live runs make the cost concrete. Killed with an exception, the client unwinds through its finally, lands the partial batch, and resumes with duplicate_pages=0 — nothing lost, nothing replayed. Killed with SIGKILL, which has no finally: the server had served 60 pages, the checkpoint covered 42, and the resume replayed exactly 18. That is the at-least-once trade, priced.

60
pages the server had served
42
pages the checkpoint covered
18
pages replayed on resume — the price

The reject log across that pair: 1,586 lines, 1,585 distinct ids. Which is why the reconciliation key is distinct id and never line count.

Reuse this

Once rows buffer, processed stops meaning durable. Move progress into the flush path and keep it one ordered breath: rejects, then rows, then the cursor. Flush on size or age, so a trickling feed still records progress.

Stage 8 · The fetch is slow, and pages stop arriving in order

One producer, a bounded queue, a pool of workers. The producer is alone because fetching is inherently serial — page N+1's cursor does not exist until page N answers. That is the API's contract, not an implementation detail, and no amount of client concurrency removes it.

What the pool breaks is the checkpoint, for the third time. Workers finish out of order. Page 7 lands before page 5, and persisting "the newest cursor I have seen" resumes past the gap — losing page 5 silently and permanently.

So the checkpointer becomes a watermark: record each page's cursor at enqueue time, while fetch order is still real, and advance the persisted cursor only through the longest contiguous prefix of completed pages.

The mutation: store the newest completed cursor instead of the contiguous prefix. All 114 tests still passed.

Here is the part worth the whole section. I wrote a deliberate bug — store the newest completed cursor instead of the contiguous prefix — and all 114 tests still passed.

Because a completion that does not advance the watermark never writes to disk. The corrupted cursor only reaches the file through the unconditional exit flush — which is precisely the path a crash takes. Every in-order test was green; only a crash with a hole open would have lost the page. The test that closes it completes page 2 with a hole at page 1 and then calls flush() directly. The mutation now fails.

A test suite that cannot fail is a suite that is measuring nothing.

This one had a real hole, and finding it took trying to break the code on purpose.

The other honest result from this stage: the pool made no difference to throughput.

27,816
records/sec — serial
29,109
records/sec — worker pool
0
difference that survives the noise

The roadmap warns you about this: give the workers real work or the layer is inert. The sink here is a stand-in whose write awaits nothing. So the pool was left in as correctness machinery, and the number was written down rather than massaged.

Reuse this

When workers complete out of order, persist the longest contiguous prefix, never the newest cursor you have seen. Bound the queue — its maxsize is your backpressure — and match the sentinel count to the worker count.

Stage 9 · Being a good citizen

Concurrency turns one rate-limit breach into N simultaneous 429s, and stage 2's backoff is reactive — it handles the 429 you already caused.

A semaphore bounds in-flight requests; a token bucket throttles proactively. Bucket before semaphore, so a request waiting for a token does not also hold a concurrency slot hostage. And the semaphore wraps only the HTTP call: a request that keeps its slot while it backs off re-serialises the entire pool, silently, under load.

async with bucket:                  # 1. wait for a token — holds nothing
    async with semaphore:           # 2. only now take a concurrency slot
        return await self._get(url) # 3. slot released before any backoff

Mutating that nesting does not merely fail the test — it deadlocks it, which is a fair picture of the production symptom.

Then the payoff, against the exact server that killed the stage-6 client:

ClientServer limitClient budgetReachedOutcome
Stage 6 10 rps none page 17 of 30 died on 429s
Stage 9 10 rps 20 rps page 29 of 30 died on 429s
Stage 9 above budget 20 rps 30 of 30 zero 429s

Both died. A client-side bucket is a promise about your rate; it cannot keep you under a limit lower than the one you set yourself. The 429s went from unavoidable to merely misconfigured, and saying so is more useful than a green checkmark.

With the server's limit above the client's budget: 30 of 30 pages, zero 429s. Not "large, but recovered". Zero.

Reuse this

Throttle proactively with a token bucket before the semaphore, and hold the concurrency slot only across the HTTP call — never across a backoff. Draw both per attempt, retries included.

Part IV — The question underneath

Stage 10 · One walker has a ceiling

Past the point where the measurements say one walker is saturated, there is nothing left to tune. The only way to go faster is more walkers over disjoint slices — and that is a distributed-systems move, not a bigger thread pool.

K walkers means K checkpoints, K reject logs, K watermarks, and a new class of mistake in what those files are called.

Naming is a correctness concern

shard_count goes into the filename, because "shard 0 of 2" and "shard 0 of 5" cover incompatible partitions, and sharing a name lets a resumed run load a cursor that was only ever valid under the old boundary.

The ApiClient is shared across every shard. Stage 9's budget is a promise to the server; one client per shard would multiply it by K and silently undo the previous stage.

Four walkers finished in 1.0s what one did in 2.1s. Not 4× — 2.1× — because the shared limiter is doing its job. shard_records_served came back {0: 7500, 1: 7500, 2: 7500, 3: 7500}: contiguous, no gaps, no overlaps, union equals the unsharded walk. And 32 pages against 30, because each shard has its own trailing partial page. The cost of sharding, visible in the request count.

Killed mid-run, it left four independent watermarks — each an offset inside its own key range. The resume finished all four.

Reuse this

Put the shard count into every state filename, not just the index — "shard 0 of 2" and "shard 0 of 5" are incompatible partitions. Share one API client across all shards, or you multiply your rate budget by K.

Stage 11 · The dataset changes while you read it

A walk that takes hours runs against a table people are writing to.

An insert landing ahead of the cursor pulls it backward, and the server re-serves rows already read. That has two symptoms — a duplicate id, and a seq that fails to increase — and both are detectable.

A delete ahead of the cursor is the mirror image, and it leaves no trace. The cursor is pushed past rows that are never served. seq keeps climbing, no id repeats, nothing in the response looks wrong.

One direction is loud, the other leaves no evidence in the protocol. That asymmetry is the whole stage.

That asymmetry is the whole stage, and here is what it looks like measured. Three walks over the same mutating 5,000-row table:

WalkWhat the client reportedWhat the server counted
Offset, detector on Stops on page 2: duplicate id 'rec-000000935' Silent corruption converted into a loud failure.
Offset, detector removed Completes. 5 pages, 4,921 rows, zero errors 260 duplicates served, and 339 of 5,000 records never sent at all
Keyset keyset_duplicate_records = 0 210 rows deleted before the cursor reached them.

The middle row is the one to sit with. A client walked a table to completion, logged nothing, reported success, and dropped 339 real records. Nothing in the protocol reported it. The only reason we know is that the server was counting what it never sent.

339
records never sent, while the client reported success
260
duplicates served and never noticed
0
keyset duplicates — structural, not probabilistic

Detection does not fix that. The fix is server-side — and this is where the opacity rule from stage 1 pays.

iter_pages_keyset is iter_pages's body, unchanged, pointed at a different URL. Eleven stages of accumulated machinery, and switching the server to keyset pagination costs the client one string. That is the whole return on never having decoded the cursor.

Over keyset: keyset_duplicate_records = 0. Exactly zero, not "low" — a served seq can never satisfy seq > cursor again, so it is structural rather than probabilistic. And the loss is finally named: 210 rows deleted before the cursor reached them. An explained absence instead of an unexplained shortfall.

What no pagination scheme fixes without snapshot isolation or CDC: a row deleted before the cursor arrives is never served. That is arriving one page late to a live table. It is not corruption, and pretending it is would be its own kind of lie.

Reuse this

Run the mutation detector in the producer, where fetch order is still real, and watch for both a duplicate id and a seq that fails to increase. Then write down that the mirror image — a silent skip — leaves no trace at all.

Part V — What the arc adds up to

Three ideas survive all eleven stages.

Idea 1 The checkpoint must never advance past durability stages 4, 7, 8
rejects before cursor the sink's buffer is not the sink contiguous prefix, not newest
Idea 2 A library replaces the mechanism, never the guarantee aiolimiter in, tenacity out
less code AND fewer concepts the guard stays, by hand
Idea 3 Say what you cannot do in the source, not a follow-up ticket
five limitations, written down

The first appears at stage 4 as "rejects before cursor", at stage 7 as "the sink's buffer is not the sink", and at stage 8 as "a contiguous prefix, not the newest thing you have seen". Three different mechanisms, one invariant, and every violation of it produces a success message.

✓
aiolimiter — adopted

It deleted a token-bucket class outright. It also silently accepts max_rate=-1 and then blocks forever, where the hand-rolled version raised. So the guard stayed, by hand, in the constructor.

✗
tenacity — declined

The bar is that a library reduce both the code and the number of concepts a reader must hold. It deleted a loop and added a carrier exception, three callbacks and a translation layer.

Credit where it is owed

Under tenacity, holding the semaphore across a backoff would be structurally impossible. That guarantee was traded for a test that fails loudly.

And the third idea, which is the one that costs something to keep. All five of these are written into the source, next to the code that has the limitation, rather than left in a follow-up ticket.

What it cannot doWhy it is written down instead of fixed
Detect silent deletes Nothing in the protocol reports them. Only the server's own counters can name the shortfall.
Show a speedup from the worker pool The sink is a stand-in whose write awaits nothing. The layer is correctness machinery, not throughput.
Guarantee exactly-once Not purchasable across an HTTP API and a file. The trade is at-least-once, priced in replayed pages.
Detect cross-shard duplicates Each shard's detector only ever sees its own slice.
Hold every id in memory A 50M-id set is several gigabytes.

The client is about eleven hundred lines. Most of them are prose explaining why the thirty lines around them are the way they are — because the failure modes here are the kind that return exit code 0, and the only defence against those is writing down what you checked and how you would know if you were wrong.

The second row of that table is the one that bothered me. A sink that cannot fail cannot test the claims made about it — so the next post makes the destination real and follows whatever breaks: The Sink Was a Lie.
