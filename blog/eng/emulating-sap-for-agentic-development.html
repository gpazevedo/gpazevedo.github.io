Emulating SAP for agentic development

You cannot point an agent at S/4HANA forty times an hour while you iterate on a prompt. The fix isn't emulating SAP — it's emulating the OData contract your MCP server actually sees, built one increment at a time.

TL;DR

You cannot build an agentic SAP integration against a shared sandbox you get to touch twice a week. You need an emulator, and the useful one is not a fake SAP — it is a fake of the OData contract your tool layer actually sees.

Cut the seam below the MCP server so the server stays production code. Then build it one increment at a time, and let each increment buy one capability the previous one put in reach. That is the part worth copying: not the final shape of the emulator, but the order the capabilities arrive in.

You have an agent that needs to read purchase orders out of S/4HANA. Maybe it also needs to create them. You have an MCP server that exposes SAP's OData surface as tools. What you do not have is an SAP system you can point it at forty times an hour while you iterate on a prompt.

This is the practical bottleneck in most agentic SAP projects. Sandboxes are shared, provisioning takes weeks, someone else's test data changes under you, and nobody is going to let an unproven agent run odata_create against anything until you can show it behaves. Meanwhile the agent loop you are building needs a tight feedback cycle to develop at all.

The answer is to emulate SAP. Not all of it, not the parts you would expect, and — this is the part most write-ups skip — not all at once.

You are not emulating SAP

The single most useful reframe: you are emulating the OData surface that your agent's tool layer sees. Nothing else.

This is what the clean-core pattern buys you. If your architecture touches SAP only through standard API surface, then the seam between "your system" and "SAP" is a well-defined HTTP contract, and a well-defined HTTP contract is something you can serve from a laptop. You are not reimplementing ABAP, pricing procedures, availability checks, or the enqueue server. You are serving XML metadata and JSON entity sets over HTTPS.

If you find yourself trying to reproduce SAP-computed business logic in your fake, stop. That is a signal that the path you are testing genuinely needs a real system, and you should be honest about it rather than building an elaborate lie.

Reuse this Emulate the contract, not the system. Find the narrowest interface your integration actually touches and serve that — the narrower the seam, the cheaper the fake and the higher its fidelity.

Pick the right seam

There are three places you can cut, and they test very different things.

Seam 1, stubbing the tools. You hand the agent a fake odata_read that returns canned JSON. This is fast and it is worth having for prompt iteration, but understand what it does not test: catalog discovery, metadata parsing, OData query construction, auth, the read and write enablement flags, error handling, pagination. All the places integrations actually break. Use it for the inner loop of prompt work and nothing else.

Seam 2, faking the OData endpoint. You point MCP_SERVER_SAP_BASE_URL at a server you control. The real MCP server container runs. It does real catalog discovery, builds real $filter expressions, handles real responses. Everything between your agent and the network boundary is production code. This is where you should spend your effort.

Seam 3, the real thing. Highest fidelity, and you still need it, just not on every commit.

Reuse this Cut below the component you most want to exercise, not above it. A seam chosen for convenience tests your test harness; a seam chosen for coverage tests your system.

The rest of this post is about seam 2. Concretely, it means swapping one branch under an otherwise untouched stack:

The path, and what each increment buys

What follows is the actual order the emulator was built in, over about three days. I am giving it as a path rather than a design because the order is the useful part: each increment buys one capability, and having that capability is what puts the next one in reach. The later ones were not on the roadmap — the emulator earned them by getting good enough to push further.

1–3. A domain model, and a loop fast enough to be worth having

The starting point is a small CAP application: Suppliers, Materials, Purchase Requisitions and Purchase Orders with their line items, backed by an in-memory SQLite database seeded from CSV on every restart. Nothing persists between runs, which locally is a feature — every test starts from the same known state.

Above it sits a thin MCP server over stdio that wraps the OData API as tools, so an agent can ask for purchase orders without hand-building query strings. Restart takes a second. That is increment 1, and for a while it is all you need.

Two things went in immediately after, and both are worth stealing.

Carry the signal your agent actually reasons about. The fixtures grew a MaterialGroups entity holding the two Kraljic axes — profit impact and supply risk — so a sourcing agent can classify a line as leverage, strategic, non-critical or bottleneck without recomputing it. A fixture set that is structurally correct and semantically empty produces an agent that looks like it works and reasons about nothing.

Build the write path early. create_purchase_order does a deep insert: a header with nested line items, one request. This is the tool nobody will let you run against a real system, which is exactly why it has to be the one you exercise most against the fake.

Fixtures are scenarios, not rows

Before going further, the thing that determines whether any of this is worth running: what is actually in the database.

The instinct is to generate a thousand plausible purchase orders. That is close to useless. An agent that works on a thousand well-formed records tells you nothing. What you want is a small set of records that each encode a situation the agent must handle correctly:

  • A PO fully delivered, and one partially delivered
  • A requisition still open, and one already converted to an order and linked to it
  • One record in a currency that is not the company code currency
  • One with a null in a field your prompt assumes is populated
  • One belonging to a different purchasing group than the calling user
  • One with a supplier name containing an apostrophe, because $filter string literals escape by doubling and something in your stack will get this wrong

That last one is not a hypothetical — increment 5 below is what that fixture caught.

Name the fixtures after the scenario, not the record. po-partially-delivered.json beats po-4500012347.json. When a test fails you want to know which situation broke, not which number.

Then add the volume case: one entity set large enough that an unguarded read blows out the context window. This is how you verify that the count-before-read discipline actually holds under a model in a hurry, rather than merely being written down in your system prompt.

Note what this argues against: a large synthetic dataset. Two material groups, three suppliers, three materials, two purchase orders and two requisitions — seeded from plain semicolon-separated CSV and reloaded fresh on every restart — cover more real agent behaviour than a thousand generated rows would, and stay legible enough that you can read the fixture file and know exactly what state you are asserting against.

Reuse this Name fixtures after the situation, not the record. The fixture directory should read as a list of the things that can go wrong.

4. Point the real client at it

This is the increment that changes what the emulator is for.

Up to here the only consumer was a hand-written MCP server, which means the fake and its client were built by the same person from the same assumptions — the failure mode where a mock and its caller agree with each other and both disagree with reality. The fix is to make the consumer something you did not write: AWS's AWS for SAP MCP Server, the real GA container, unmodified, pointed at this backend the same way it would point at a real SAP gateway.

That server speaks OData V2, so the emulator had to grow one.

Two mechanical details from that increment cost real time and are worth writing down.

The V2 surface is generated, not hand-typed. A V2 adapter — @cap-js-community/odata-v2-adapter — produces a genuine V2 surface from the same CDS model that serves V4: the d.results envelope, __metadata, guid'…' keys, V2 EDMX, all from real protocol code rather than a hand-written imitation. It is a plugin CAP's own discovery has to find, which means it must be a declared dependency. Installing it without letting your package manager write the entry is enough to leave it silently unmounted, serving nothing, with no error.

The CSRF handshake is not in the box. Classic V2 clients do a token dance before any write: GET with X-CSRF-Token: Fetch, read the token from the response header, send it back on the write. Neither CAP core nor the V2 adapter implements that for a service's own endpoints — both source trees only carry client-side helpers for calling out to protected services. So it is hand-built: the adapter's self-registration is switched off in config, and the CSRF middleware is mounted manually, ahead of it, so tokens are issued and checked before anything proxies to V4.

Reuse this If the real integration component can run against your emulator unmodified, you have not built a mock of the integration — you have built a test environment for it. Aim for that whenever the real component is available to you at all.

5. What an independent client exercises

Within a day the independent client had pushed into two paths no amount of designing would have found, and each one turned into a permanent property of the stack.

Filter literals that hold under a hostile value. status, poNumber and prNumber were being interpolated raw into $filter. Passing status = "OPEN' or status ne '" broke out of the string literal and rewrote the filter's boolean logic — every row came back. OData escapes a single quote by doubling it; a one-function fix, applied at four call sites, verified against the emulator by watching the same crafted value return every row before and zero rows after. That is the apostrophe fixture from the list above, earning its keep as a security finding rather than a formatting nicety.

A handshake shaped like the one real clients expect. The first CSRF implementation set X-CSRF-Token only on responses to requests that carried the Fetch sentinel, which is what the protocol description implies. AWS's odata_update failed against it with "CSRF token not found in response headers" — its update flow reads the target entity by key first, with no sentinel, and expects that response to already carry a usable token. Real clients pick up tokens opportunistically from whichever response they saw last. The fix is to echo the current token on every response.

A third behaviour sits underneath that one, and it is the more interesting one: after the header fix, writes still failed intermittently. Debug logging proved the server's own token had changed between two calls nine seconds apart with no fetch in between. The cause was the Lambda cold-starting and re-running the module's randomBytes — capping concurrency does not keep an execution environment warm. Nothing in the token logic was wrong. The live test retries the whole call, and the emulator stayed amnesiac on purpose.

6. A probe and a reset, so the container can say where it is

Locally, "nothing persists between runs" is a gift. Deployed as a container-image Lambda, keeping it a gift takes two small endpoints: the in-memory database and the CSRF token both reset on every cold start, and a test should be able to see that happen rather than guess at it.

Provisioned concurrency would suppress the resets and charge for the privilege. Making them visible and repeatable is cheaper and worth more:

  • GET /health — no auth, so it doubles as a Lambda health probe. Returns build SHA, boot timestamp, and the current row count per entity. A live test polling it can tell a genuine cold start (a new bootedAt) from a warm container, and the build SHA is what a drift check compares against when the deployed image and the tag it claims disagree.
  • POST /admin/reseed — authenticated with the same credential as the OData service. Drops every row and reloads from the CSV fixtures in foreign-key-safe order, returning the new counts. A test that calls it in setup cannot have its assertions muddied by a cold start.

Both are mounted ahead of the CSRF and V2 middleware, because neither is part of the OData surface and neither should inherit its handshake.

Reuse this When your fake is deliberately stateless, give callers a probe and a reset instead of paying to make it stateful. Cheaper, and it turns an invisible source of flaky tests into an assertion.

7. CI that keeps two invariants true

Building the image locally to verify the health endpoint is what made the case for CI: the Dockerfile still carried a COPY of a directory the repository never had. Minutes to fix once something ran the build, an afternoon to find on a deploy.

So increment 7 is a CI workflow, and it is deliberately small: install, npm test, then docker build with the git SHA as a build argument. No push, no AWS credentials, no deploy. It proves exactly two things — the tests still pass and the image still builds — which are the two invariants every later increment leans on.

Reuse this An artifact nothing builds on a schedule is an artifact that is already broken. A CI job that only builds and throws the result away is worth more than it looks.

8. Real S/4 names, and what they unlock

This is the increment that makes the emulator's vocabulary real, and it returns more per line changed than anything else on the path.

The original model used names that were convenient: poNumber, materialNumber, status. Real S/4 uses A_PurchaseOrder.PurchaseOrder, A_PurchaseOrderItem.Material, ProcessingStatus, and it makes org fields mandatory that the mock had no concept of at all — CompanyCode, Plant, PurchasingOrganization, PurchasingGroup, PurchaseRequisitionType, AccountAssignmentCategory. An agent developed against invented names is an agent trained on a vocabulary that does not exist.

The move is a second service projecting the same tables under real S/4 entity and field names, mounted alongside the original. Both stay live until every caller has moved; deleting the old one is a later step, not this one. Adding a surface is cheap and reversible, and it lets callers migrate one at a time.

Doing it produced the single best finding of the whole exercise. Reads expose the business key by flattening an association path — material.materialNumber as Material — so a response carries MAT-1001 rather than an internal UUID. CAP cannot reverse that on write. Posting {"Material": "MAT-1001"} does not error: it silently drops the field, and you get a line item with no material at all.

The resolution — look the business key up, set the foreign key, reject with a 400 if it does not exist — is precisely the work a real S/4 OData service's own ABAP handler does server-side. Nobody had planned to write it. It surfaced because the fake was faithful enough to reach the same wall the real service does, which is the whole return on building it faithfully.

Two more things landed with it:

  • Optimistic concurrency. Real S/4 rejects a PATCH without a matching If-Match. An ETag annotation on the managed modifiedAt of orders and requisitions turns that on, and a test asserts that a stale token gets a 412 and a fresh one succeeds. Without this, a write path can carry a lost-update bug all the way to production and never see a 412 in development.
  • Deliberate failure. POST /admin/fault arms the next N OData calls to fail with a chosen status — 400, 412, 429 or 503 — and DELETE disarms it. It is armed as server state rather than a request header on purpose: the calls that need to fail are ones the caller's own SDK makes internally, which a test has no way to attach a header to.

That last one opens a path the earlier increments could not reach. A caller's retry classification, backoff and dead-letter handling only run when something fails, so the emulator has to be able to fail on cue.

Reuse this Add the faithful surface next to the convenient one rather than replacing it, and give the fake a switch that makes it fail on demand. Retry logic that has never seen a failure is not logic, it is decoration.

What actually has to be right

Stepping out of the path: here is the checklist those increments converged on. A JSON server that returns {"purchaseOrders": [...]} will make your agent work perfectly in dev and fail on day one in staging.

ThingWhat SAP actually does
Response envelopeOData V2 wraps collections as {"d": {"results": [...]}} and single entities as {"d": {...}}. Not V4's {"value": [...]}.
Entity metadataEvery entity carries a __metadata object with uri, type, and often etag. Some clients follow the uri for subsequent reads.
Field namesStandard APIs use A_-prefixed entities and SAP field names, and make org fields mandatory. Convenient names train the agent on a vocabulary that does not exist.
Business keysReads expose the business key; writes may need it resolved back to an internal key. Check that your stack does not silently drop the field instead of erroring.
DatesEdm.DateTime serializes as /Date(1767225600000)/. Filters use the literal form datetime'2026-01-01T00:00:00'. Times come back as ISO 8601 durations like PT08H30M00S.
DecimalsEdm.Decimal serializes as a string, not a number. An agent doing arithmetic on "1250.00" without parsing will silently concatenate.
KeysDocument numbers are zero-padded fixed-width strings. Purchase order 4500012345 is a 10-character string; material numbers are 18 characters padded. An integer key teaches the agent the wrong lookup format.
Counting/EntitySet/$count returns a bare integer as text/plain. $inlinecount=allpages puts a __count string in the body.
CSRFModifying requests need a token: GET with X-CSRF-Token: Fetch, read it from the response header, send it back on the POST with the session cookie. Echo it on every response, not only on the fetch.
ConcurrencyA PATCH without a matching If-Match is rejected with 412. Skip this and a lost-update bug never surfaces before production.
ClientThe sap-client parameter selects the logical client. Getting it wrong in production means querying an empty client and receiving a valid, empty, wrong answer.
Errors{"error": {"code": "...", "message": {"lang": "en", "value": "..."}}} with gateway-style exception codes. Agents reason about error text, so give them realistic error text.

The envelope is the one that bites hardest. A team that builds its emulator against V4 conventions writes an agent, prompts, and an eval set that all quietly assume value. Every one of those artifacts has to be revisited when the first real response arrives shaped as d.results. This is the strongest argument for generating the V2 surface from a real adapter rather than typing it out.

Two further behaviours are worth reproducing on purpose, because they are exactly the failures your guardrails are meant to catch.

Annotation-driven restrictions. SAP's metadata carries sap:filterable, sap:sortable, sap:creatable, sap:updatable, and sap:required-in-filter. A service with sap:required-in-filter="true" on a field will reject a read that does not filter on it. A field marked sap:filterable="false" errors if you filter it. A permissive mock accepts all of this happily. Make at least one entity set enforce its own annotations and you will learn in dev whether your agent reads metadata or guesses.

Pagination that is not $skip. Some services require $skiptoken for stable paging. Build one entity set that way. It is also the canonical example of what a service hints file is for, so it doubles as a live test of whether your hints are actually reaching the model.

Reuse this Reproduce the vendor's restrictions, not only its happy path. A permissive mock is a mock that lies, and it lies in the direction that feels like progress.

Start from real metadata where you can

The increments above generated the emulator's schema from a CDS model, which is the right move when you are also the one deciding the domain. Where you are integrating with a standard SAP API, the stronger move is to take the vendor's own contract.

The $metadata document is the contract. Your agent's model reads it to learn entity set names, property names, types, key fields, and navigation properties. Invent it and you are training your agent against field names that do not exist — which is exactly the debt increment 8 was paying off.

Getting the real one is a single GET against a service you already know the name of, and you can usually obtain it without full sandbox access. SAP publishes EDMX for standard services through its API documentation. Somebody on the customer side can export it from their gateway in thirty seconds. A trial or developer edition system will hand you the standard catalog.

Then commit that file. Treat it as a versioned contract artifact, not a fixture. Everything else in your emulator is generated from it or validated against it. The payoff compounds: once the metadata is real you can generate fixture skeletons from it, validate every fixture against the declared types, and catch the class of bug where your test data carries a field the real service does not expose.

Reuse this Never hand-write a schema you can obtain. Pull the vendor's own schema document, commit it, and generate your fixtures from it rather than alongside it.

The write path is why any of this exists

Every one of the late increments — the CSRF handshake, the business-key resolution, the ETag rejection, the injected 429 — is on the write path. That is not a coincidence. The read path is the one a shared sandbox will grudgingly give you; the write path is the one you will only ever exercise properly against something you own.

Emulate authorization, not just authentication

This is the recommendation people skip and the one that causes the most expensive late-stage rework. It is also the next increment on this path rather than one already taken: today the emulator runs one mcp account with Basic auth, and every caller sees every row.

That is fine while the emulator's job is protocol fidelity. It stops being fine the moment agent behaviour depends on visibility. If your fixtures return every record to every caller, the agent never learns it might see a partial view, your prompts never handle "the user cannot see that PO", and your evaluation set has no coverage of the case.

Then you ship with on-behalf-of token exchange, SAP's authorization objects start filtering per user, and the agent's behaviour changes in ways nobody tested.

The increment to take is small: read a header identifying the caller and filter fixtures by purchasing group, company code, or plant. The org fields that increment 8 added are exactly the ones you would filter on, which is the usual pattern — a fidelity increment makes the next one cheap. It costs an afternoon, and it turns "user asks about a PO they cannot see" into a scenario with a fixture rather than an incident.

Keep the transport auth simple in the fast loop. Emulate the consequences of the identity model, not its handshake.

Reuse this When you stub an auth boundary, stub what it filters, not just what it permits. The expensive surprises come from visibility, not from 401s.

An environment ladder

Different questions deserve different fidelity. Four rungs, in descending frequency of use.

Put a recording proxy in front of a real system for one supervised session, capture the request and response pairs, and replay them deterministically. You get genuine SAP response bodies with genuine quirks, without needing the system again.

Custom function imports deserve a specific warning. They are the tool most likely to have behaviour you cannot infer from metadata, and the one your emulator will get wrong. Test those against something real.

Reuse this Give each question the cheapest environment that can answer it honestly, and record the real system once so the middle rungs are not guesswork.

Keeping the fake honest

Emulators drift. The mitigation is to make drift loud rather than to prevent it, and the mechanism is per-lane contract tests rather than manual poking.

In practice that is four things, all of which run on every pull request alongside the image build:

  • A shell script that pins the V4 response shape — that an over-length key is rejected with the right error code, that a deep insert returns child IDs, that decimals come back as JSON strings, that a partial insert accepts a null. Every fact it checks is something the calling bridge assumes and its offline fakes replay.
  • A unit test for the CSRF middleware: a token on a plain GET, a 403 with the Required sentinel when a write carries none, a 403 on a stale one, success on a fresh one.
  • A test for the S/4 surface: flat S/4-named fields without a deep expand, a business key resolved server-side on deep insert, an unknown key rejected with 400, a stale If-Match rejected with 412.
  • Tests for the operational endpoints: health reporting seeded counts without auth, reseed rejecting bad credentials and restoring the seed, faults arming and disarming.

On top of that, if you are integrating with a real SAP API: re-pull $metadata from the real system on a schedule and diff it against the committed copy. Fail the build on any change. A new field is a fixture you should add; a removed field is a prompt about to break. Either way you want to hear it from CI rather than from production.

And keep a conformance suite: a fixed set of requests fired at both the emulator and a real system, comparing response shape rather than values. Status codes, envelope structure, header presence, type serialization. Not data. Values differ legitimately; shapes should not.

Reuse this Make drift loud. Pin each lane with its own contract test, diff the vendor contract on a schedule, and fail the build on change rather than trusting anyone to notice a field went away.

What not to bother with

Do not emulate business logic. Pricing, availability, credit checks, workflow determination. If your agent's correctness depends on values SAP computes, that path belongs on rung 4.

Do not emulate SAP's real multi-service catalog. One mock service standing in for four real ones, mounted at a plain path, is enough — as long as the entity and field names inside it are honest. Number ranges, document-type addressing and supplier master-data matching are all things you can key on a technical ID instead, provided you write down that you did.

Do not emulate event delivery through the OData layer. Event-driven ingestion is a separate architecture with its own emulation story, and conflating the two produces a fake that tests neither well.

Do not emulate performance precisely, but do inject latency. Real OData responses take hundreds of milliseconds to seconds. An emulator that answers instantly hides timeout handling, hides the cost of a chatty agent, and makes your latency budget look fine right up until it is not. A fixed few hundred milliseconds is enough to keep you honest — and pairs with the fault switch: slow is a different failure mode from broken, and your caller should survive both.

The short version

The emulator is not a stand-in for SAP. It is a fast, deterministic, safely writable implementation of the contract between your agent and SAP — and it gets good by being driven, early and often, by a client you did not write.

Build it at the OData boundary. Take the metadata from a real system and never hand-write it. Reproduce the quirks deliberately, including the annoying ones. Point the real integration component at it as early as you can stand, and let what it exercises decide the next increment. Give it a way to fail on demand. Model authorization, not just authentication. And keep one rung of the ladder pointed at something real, so you find out early when the contract moves.
