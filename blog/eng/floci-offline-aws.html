Adopting Floci: the tests that used to cost a NAT Gateway

Our SAP integration is a chain of event-driven hops — a poller emits, EventBridge routes, a Lambda ingests, Step Functions negotiates, SQS drains. Every hop was untestable without real AWS, because the one thing moto cannot do is invoke a Lambda container off a rule. So we ran a spike against a local emulator and measured what it actually does.

Buyer Team's dev account runs with its paid networking released most of the time. A NAT Gateway and three interface VPC endpoints sit behind a release_vpc.sh / restore_vpc.sh pair, and they stay released because the alternative is paying hourly for a lab that is idle most days. That is a good trade until a test needs them.

And the SAP loop's tests needed them constantly. Not because the handler logic is hard — that is ordinary unit-test material — but because the parts worth testing are the joints. Does the rule's source pattern actually filter? Does maxReceiveCount really redrive to the DLQ on the third receive, or only on the fourth? Does a Step Functions Task state genuinely invoke its target, or did we misspell an ARN in a place Terraform validates but never exercises? None of those are answerable in-process.

Why moto was not enough

moto is excellent and we use it heavily, and the limitation is narrower than "it's a fake." moto can genuinely run a Lambda in Docker — its backend shells out to docker_client.containers.run for a direct invoke. What it does not implement is Lambda as an EventBridge rule target. Put an event on a bus whose rule targets a function, and moto 5.2.2 does this:

File "moto/events/models.py", line 202, in send_to_targets
    raise NotImplementedError(f"Expr not defined for {type(self)}")
NotImplementedError: Expr not defined for <class 'moto.events.models.Rule'>

Reading send_to_targets explains why: it dispatches on the target ARN's service and handles CloudWatch Logs, SQS, an events archive, a cross-account event bus, and API destinations. Lambda is not in the chain, so it falls through to the else. The gap is not container execution — it is cross-service delivery. moto models each service well and is deliberately conservative about wiring them to each other, which is exactly the thing our chain is made of.

So the event-driven half of the chain fell through to tests/integration/, which hits real us-east-1. Which means credentials, and it means restore_vpc.sh: a targeted Terraform apply that provisions a fresh NAT Gateway and Elastic IP, resumes the schedules, and re-arms every dev alarm. It works fine. It is just an absurd amount of ceremony to answer "does the rule fire".

There is a second, less obvious cost. The restore cycle hands the NAT a new public egress IP each time, and the release/restore round trip resets alarm state — a rare-signal alarm comes back INSUFFICIENT_DATA and has to re-earn its datapoints. Running the VPC up and down to test a routing rule quietly degrades the observability we built for actual incidents.

"The tests we most wanted to run were the ones with the highest fixed cost to run at all."

The bill was two months old

It would be tidy to say the SAP integration created this problem. It did not. It made an existing one impossible to keep deferring, and the distinction matters for what we ended up building.

The joints Floci covers are not SAP-shaped. Saga compensation, the circuit breaker, the outbox poller, the A2A dead-letter opt-in — those are Step Functions Task states and SQS redrive policies, exactly the constructs this suite exercises, and every one of them was live-only long before SAP was a work item. Dated by when each live test file first landed:

Window New live-only test files SAP?
13 Jun – 2 Jul 17 — incl. saga compensation, circuit breaker, outbox poller, A2A DLQ None
2 Jul – 1 Sep 0 —
2–3 Sep 7 in three days All of them

Seventeen live-only files accumulated across three weeks in June, each paying the NAT tax on every run. Then the ledger sat still for two months. The SAP work did not introduce the first untestable joint — it added seven more in three days, and Floci went in on 2 September, the same day the first of them landed. The economics had justified this since June; what changed in September was the rate, and a cost you have been quietly absorbing becomes a decision the moment it starts compounding.

The debt that is left

Being precise about this changes what you build. "We need a local emulator for SAP" would have justified something SAP-shaped. What we actually needed had been justified since June — so the rig is generic (the compose file, the client fixtures, the in-memory deploy_lambda that takes any handler source), even though the only suite written on top of it so far is the SAP one. The June chains still run live. Porting the redrive and Task-state half of them is now a small job rather than a project, and it is the obvious next withdrawal from this account.

Not all seventeen, though. The agent-driven ones — anything that reaches Bedrock or the AgentCore data plane — can never move here, for the reasons in the table above. That boundary does not shift just because the rig got easier to use.

The spike: measure, don't read the README

Floci (floci/floci, MIT-licensed, listening on port 4566) is a local AWS emulator in the LocalStack lineage. The interesting claim is that it runs Lambda as real containers rather than in-process handlers. That is exactly the ceiling we had hit, so it was worth a day.

We did not evaluate it from the documentation. We stood it up and drove Buyer Team's own patterns through it — the specific conditional writes, redrive policies and rules our code depends on — and wrote down what happened. The results below are measured, not claimed.

Surface Result What we actually drove through it
DynamoDB Works attribute_not_exists and optimistic-lock conditions raise a real ConditionalCheckFailedException; begins_with queries; nested-map SET; Decimal typing

That split is the whole adoption decision in one table. The stubbed column is not a gap to work around — it is the boundary of what this tool is allowed to claim, and we drew the suite's scope to match it exactly.

The part that surprised us: no source changes

The usual tax on a local emulator is an endpoint seam — every client constructor grows an endpoint_url parameter that is None in production, and you carry that fork forever. We had budgeted for it in lambda_core.client().

It was not needed. Floci injects AWS_ENDPOINT_URL into the Lambda containers it launches, and botocore honours that environment variable natively. Handler code that builds clients the ordinary way is already pointed at the emulator, with no knowledge that it is one.

Why this matters more than convenience

A test-only code path in production code is a place where the tested thing and the shipped thing diverge. Zero source changes means the handler running under Floci is byte-identical to the handler running in us-east-1. The emulator is a property of the environment, not of the code.

What we built

The suite lives in tests/floci/ and covers precisely the joints moto cannot reach: bus and source-filtered rule into a Lambda, a rate(1 minute) schedule firing, SQS redrive to DLQ after maxReceiveCount, and a Step Functions Task really running its target.

docker compose -f tests/floci/docker-compose.yml up -d
RUN_FLOCI=1 uv run pytest tests/floci -v
docker compose -f tests/floci/docker-compose.yml down

It is opt-in behind RUN_FLOCI=1, mirroring the existing RUN_INTEGRATION gate in the parent conftest.py. Default collection is unchanged — 55 tests before, 55 after — and the suite skips cleanly with a message telling you the compose command if Floci is not running. Nobody who does not want Docker in their loop has to have it.

Which left one problem: opt-in meant nothing ran it, so it was the only suite in the repo with no way to notice its own rot. It now runs nightly, and the guard is the interesting part — it is skipped while the dev environment is cost-paused by release_vpc.sh. That reads oddly at first, since this suite is the one thing that needs no NAT. But the pause is a statement that the environment is parked, and a nightly grinding through a parked window is the exact waste the release script exists to prevent; the daily FinOps poller is paused there for the same reason despite having no VPC dependency either.

The guard reads live state rather than a flag someone has to remember to set — the warm-floor rule that release_vpc.sh already toggles — so restore_vpc.sh re-arms the nightly with no extra step. A hand-maintained list of things that must not be forgotten is what produced our last heartbeat trap. It fails open in both directions: if the pause probe cannot reach AWS at all, the suite runs anyway, because being unable to reach AWS must never be what silently disables the one suite that does not need it.

Building the rig, one increment at a time

The suite did not arrive whole, and it is more useful to read the path than the destination. Each step was small enough to validate on its own before the next one started, and each was shaped by something the emulator requires rather than something that went wrong. Taken in order, they are most of what you need to build one of these yourself.

⊕
1 · Name every run

Constraint: Floci keeps state for the life of its container, so a long-lived emulator carries the previous run's resources into the next one — including a live rate() rule still firing into a table that has moved on. Increment: a session-scoped run_id suffixing every resource name. Isolation has to come from naming, because the backend offers none.

⊕
2 · Share the emulator's network

Constraint: the Lambda containers Floci launches join Floci's network, so a host port mapping is invisible from inside one. Increment: put the CAP mock on that same network behind an optional compose profile, listening on the port the Lambda actually dials rather than the one the image bakes in. This is what let a Lambda read the mock's OData surface with no ALB, certificate or VPC anywhere in the picture.

⊕
3 · Tear down the pool, not the container

Constraint: a graceful docker compose down lets Floci reap the warm-pool Lambda containers it started; killing it outright with docker rm -f floci does not, and they accumulate. Increment: teardown reaps the pool by name — docker ps -aq --filter name=floci- | xargs -r docker rm -f. The pipe rather than a $(…) substitution is deliberate: the ID list must word-split, which shellcheck flags as SC2046, and xargs -r makes the empty case a no-op for free.

Where we let real code in

The handlers in this suite are written inline, in the test file, rather than importing the orchestrator's real modules. That is deliberate and it is the opposite of the usual advice, so it needs defending: this suite asserts chain wiring. Does the rule fire, does the redrive happen. The handler logic is unit-tested elsewhere, properly, and importing it here would only add a way for these tests to fail for reasons that have nothing to do with wiring.

There is exactly one exception. The SAP CSRF handshake was moved into sap_client.sap_request specifically so that no caller needs to know CSRF exists — and a claim like that deserves a test that exercises the real module, not a test-local reimplementation of the same handshake. So one fixture builds a deployment package containing the actual orchestrator/sap_client.py plus httpx, installed for the Lambda's real runtime target:

uv pip install --target <tmp> \
    --python-platform x86_64-manylinux2014 \
    --python-version 3.14 \
    --only-binary :all: httpx

A Lambda then imports sap_client and drives a write against the CAP mock's OData V2 surface — the same surface AWS's SAP MCP server drives live. When that test goes red, the mock's write path or the client's handshake regressed. When the live run goes red and this one stays green, the problem is AWS's server or the deployed wiring. The two suites answer different questions, and keeping the boundary sharp is what makes either answer useful.

That decision paid off three weeks later, and not in a way we predicted. Migrating the direct-HTTP path to an S/4-shaped surface meant carrying an ETag from a GET onto the following PATCH, so a write would not come back 412 or 428. The offline test surfaced something the documentation does not lead with: the V2 adapter demands If-Match unconditionally for an entity carrying @odata.etag — stricter than V4. Because the test drives the real sap_client rather than a local imitation of it, that constraint showed up as a failing assertion on a laptop instead of a 428 in a live run.

It also forced the test to get more honest. Its write path had been a collection GET; it is now a by-key GET immediately before the PATCH, same path string both times — mirroring po_export_drain._close_requisition's actual idiom, because that is what gives the client's per-path ETag cache something to reuse. A fake that diverges from the caller it stands in for is the failure mode we keep guarding against; here the offline suite was the thing that caught it.

The honest limit

We have been here before. Our legal-research service accumulated a class of bug where a test fake was more permissive than the real backend — every test green, production wrong, and nothing in CI able to tell the difference. An AWS emulator is that same hazard with a much larger surface area.

So the scope rule is written into the compose file and the suite's docstring, not just into someone's head. Bedrock, the AgentCore data plane, and alarms on AWS/* namespaces are explicitly not covered here, because Floci stubs them and a green test over a stub is worse than no test — it is a false negative with a checkmark next to it. tests/integration/ against real AWS remains the source of truth for AWS behaviour.

Adoption verdict
Adopted, with the scope written down. Green on Floci means the wiring is right — it does not mean AWS agrees. That sentence is in the commit message, the compose file and the conftest docstring, because the day it stops being said out loud is the day the suite starts lying.

What we got for a day of spiking: the event-driven half of the SAP loop is now testable on a laptop, on a plane, with no credentials, no NAT Gateway, and no alarm state getting reset to prove that a routing rule routes. The live tests still exist and still run — they just no longer have to run to answer questions that were never really about AWS.
