Designing for Failure in a
Multi-Agent Procurement System

How 6 autonomous agents are built to fail, degrade, and recover without corrupting state or acting silently — the decisions behind that design and the trade-offs they carry.

Agentic systems introduce a class of failure modes that traditional microservices don't prepare you for. When an LLM agent calls a tool that times out, the system can't simply return a 500 — it must decide: retry, approximate, escalate, or halt. And that decision has business consequences. In procurement automation, a wrong move can mean a missed auction round, a corrupted bid evaluation, or a PO that never gets issued.

This post walks through how we designed for that reality on the Buyer Team — a deterministic DAG of 6 autonomous agents plus a deterministic scoring node that handle the full supplier negotiation lifecycle. We'll cover the architectural decisions that shaped how the system handles failure and the trade-offs behind them.

The Pipeline Architecture

The system is structured as a deterministic DAG — not a graph where agents decide their own routing, but a controlled pipeline where each node has a defined contract for what it produces and what happens when it can't. This was a deliberate architectural choice: determinism at the orchestration layer buys us predictability in failure scenarios.

The pipeline processes a procurement request from ingest to award across seven nodes:

Node 1–2 Ingest & Classify Validate → Kraljic Classification
schema validation rule-based fallback 75–90% fallback accuracy by quadrant
Nodes 3–4a/b/c/d Strategy & Negotiation Router → Spot / Leverage / Bottleneck / Strategic
circuit breakers DynamoDB session cache TCO approximation steering hooks
Nodes 5–7 Evaluate, Approve & Award Bid Eval → Approval Gate → Award & Comms
suspicious bid detection 96h approval timeout config-driven defaults transient retry

"A deterministic DAG doesn't mean a rigid system. It means the failure surface is bounded and auditable. Every edge in the graph has an explicit failure contract."

The key architectural trade-off here is expressiveness vs. auditability. A fully dynamic multi-agent graph could potentially route around failures more creatively — but it would make the failure surface unbounded. We chose the predictable graph and invested the saved complexity budget in explicit, layered failure handling at each node.

The Failure Philosophy: No Silent Degradation

Before writing a single line of failure-handling code, the team aligned on a core principle: every failure must be observable and categorized, never swallowed. This sounds obvious, but it has non-trivial implications for how you design agent tools, escalation paths, and recovery mechanisms.

We categorized failures into three behavioral tiers, each with a different response posture:

Retry
Transient failures: tool unavailability, timeouts, network errors. Agents retry with exponential backoff (500ms / 1s / 2s). Idempotency keys prevent duplicate side effects.
Approx
Degraded operation: when retries are exhausted but a result is still required. Agents fall back to rule-based approximations, partial compilations, or cached values — flagged for downstream evaluation.
Escalate
Unrecoverable failures: total tool failure, suspicious data patterns, governance threshold breaches. Agents write a REQUIRES_ATTENTION event and halt cleanly — never corrupt state silently.

The most important decision in this tiering was where to draw the line between "approximate and proceed" and "halt and escalate." Drawing it too conservatively means frequent human interruptions. Drawing it too liberally means proceeding with low-confidence results that can compound downstream. We calibrated each threshold per agent based on the business cost of a wrong answer in that context.

The 20 REQUIRES_ATTENTION Triggers

Rather than treating escalation as an afterthought, we designed it as a first-class architectural concern. Every meaningful failure pathway in the system routes to one of 20 named REQUIRES_ATTENTION triggers — each with a defined category, conditions, and downstream action. The table has grown as we've found new failure modes in production — 9, then 13, then 14, then 18, then 19, and on to today's 20 — which is itself a sign the taxonomy is doing its job: new gaps get a named trigger, not a shrug. The count itself briefly wasn't trustworthy: one trigger (compensation_incomplete, live since mid-July) went undocumented in the canonical table for weeks while a separate decision log tracked it under a number that collided with another trigger already using it — a reminder that a count stated in prose can't catch a collision the way a single numbered table can.

One of the more subtle design decisions here is the DLQ/REQUIRES_ATTENTION decoupling. The DLQ write is fire-and-forget — the authoritative escalation signal is always the DynamoDB write, never the SQS publish. This means a DLQ outage cannot block an escalation from being recorded. Crash Recovery: Designing for Consistency

The most demanding scenario to design for was crash recovery mid-execution. The Bottleneck Negotiation agent — which runs expensive TCO and risk calculations — needed a recovery path where a crash partway through a multi-supplier calculation would never produce duplicate work or corrupted state when a new instance picked up the task.

Here's how that plays out when the agent crashes mid-TCO calculation for Supplier A, after writing the result to cache but before completing the full round:

Architecture Note

The 600s TTL is a deliberate choice, not an arbitrary one. It must exceed worst-case agent execution time while remaining short enough that a crashed instance doesn't block recovery indefinitely. We sized it at roughly 10× the p99 execution time of the slowest tool call in the node. If that p99 shifts, the TTL should be revisited.

What actually triggers this today

The lock-and-resume sequence above is real, but it isn't a continuous background failover — the recovery sweep is invoked deliberately, post-deploy or after an incident, not on a schedule, so "a new instance recovers" means the next time someone runs it, not an automatic same-second takeover. And until August 4, 2026, the checkpoint half of this story didn't run at all: the function that writes a checkpoint had zero callers anywhere in the orchestrator, so the recovery sweep's checkpoint read always came back empty and no negotiation was ever actually resumed this way in practice — a crash mid-round degraded straight to a "no checkpoint" escalation instead of the resume path pictured here. We wired that write into all six node handlers to close the gap; the sequence above is what it does now, not what it always did.

The Infrastructure of Resilience

Underneath the six agents sits a small set of resilience patterns applied uniformly at every outbound call site: retry with jitter, circuit breaker, idempotency, timeout, dead-letter queue, and a shared invocation wrapper that composes the first three for every agent-to-agent call. None of this is agent-specific — it's the substrate that makes consistent recovery possible, and every tunable parameter (retry counts, breaker thresholds, timeouts) is sourced from a central config store, adjustable in production without a redeploy.

Where this code actually lives

This substrate lives in the orchestrator, not inside the six agents. Each agent is its own isolated Docker build context — it can't import a shared runtime package beyond what its base image bakes in, and this resilience layer isn't in that image. The Step Functions node executors are the callers, so they're the only place this code is both importable and exercised. Every outbound call these patterns wrap is the orchestrator calling an agent, Bedrock, a supplier MCP server, or DynamoDB — never an agent calling itself.

That last part mattered enough to make it a design decision in its own right: hardcoding those constants per call site would mean every production tuning fix required a deploy, and the values would drift apart across nodes over time. Routing every call through shared, config-driven wrappers keeps the behavior — and the vocabulary — consistent everywhere it's applied.

Concurrency Caps: A Mechanism We Built, Then Removed

Because each agent session runs in its own microVM, there's no fleet of interchangeable instances to scale horizontally the way a typical microservice would. The original design shipped a bulkhead at every outbound call site — a per-operation-type concurrency cap enforced with a semaphore: spot bid invitations at 200 globally and 20 per auction, A2A agent calls at 10, DynamoDB writes at 50, and supplier MCP calls at 20, all sourced from config.

It never bounded anything. The deployed call shape turned out to be one A2A call per round per node, with no orchestrator-side fan-out for a semaphore to queue against — the bulkhead never once blocked a call in production. Once we confirmed that, we deleted it rather than keep carrying a mechanism that did nothing but add a layer of indirection. The caps themselves (200 global / 20 per-auction on spot-bid invitations) remain documented invariants, sized to the Bedrock InvokeAgentRuntime rate limit and the bid-fan-out SLA — but the job of bounding concurrency now belongs entirely to admission control below, which bounds how many negotiations a tenant can have in flight, not how many calls of a given type are outstanding.

Inbound Admission Control: The Other Half of Backpressure

Bulkheads bound outbound concurrency — how much load the orchestrator sends out. They don't protect the receiving side. Each agent runtime and the MCP server now caps its own in-flight request count and, on saturation, fast-rejects new task requests with an HTTP 503 and a retry hint instead of letting them queue. Without this, a burst that exceeds an agent's throughput was handled only reactively — queue, retry, eventually DLQ. Shedding early means a rejected request gets rescheduled against a less-loaded replica immediately, rather than piling onto one that's already struggling. Health checks are always exempt, so a saturated agent never looks unhealthy to the platform.

Readiness and Draining: Closing the Fail-Open Window at Both Ends

A subtler failure mode showed up at the edges of an agent's lifecycle. The health check each agent exposes was originally a pure liveness probe — it reported healthy the instant the process started, regardless of whether the agent had actually finished loading its model and prompt configuration. A cold or half-initialized replica could take traffic and fail it immediately. We changed the health check into a real readiness gate: unhealthy until startup genuinely completes, healthy after.

The same problem exists in reverse at shutdown. When a replica is told to stop, it keeps draining in-flight work — but if it keeps reporting healthy while doing so, new traffic keeps arriving at a process that's on its way out. Each agent now flips its health status to unhealthy the moment shutdown begins, before it starts draining, so new requests route away first and in-flight ones get to finish cleanly within a bounded window. Readiness and draining are the same fail-open window, just at opposite ends of a replica's life — closing only one of them would have left the other exposed.

Steering Guards: The Fail-Open Window Nobody Saw

Readiness and draining close a fail-open window in the availability layer — the gap between when a process can accept work and when it should. The same pattern existed in the safety layer, and it was open for months before anyone noticed.

Strands' steering framework ships fail-open: if a hook's check() function raises an exception, the framework catches it, logs at debug level, and lets the tool call proceed unguarded. For a hook whose entire job is "block this before it happens," an exception is functionally identical to deleting the guard — and at default log verbosity, nothing tells you it happened. The ADR governing this behavior stated the fail-closed guarantee as settled fact, and it wasn't true.

A GuardHandler base class now inverts that default. All eight steering hooks run through it; any exception escaping check() cancels the tool call with model guidance not to retry, and a dedicated governance.hook_error metric fires — deliberately distinct from the metric that fires when a hook works and blocks something, because one means the guards are doing their job and the other means a guard is broken. A same-day follow-up (AD-024) closed what was still untested: steer_before_tool wraps check() in asyncio.wait_for (10s default) so a guard that hangs fails closed the same way a raise does, and a static test asserts every guard overrides only check(), never steer_before_tool directly — closing the one place the invariant still rested on an author remembering a convention rather than the build enforcing it. Every guard also gained a test that drives its actual check() body through a genuine failure, and every agent's spec gained a test asserting the guard is registered — the fail-closed guarantee only protects a guard that's wired in.

A second fail-open case sat one layer below. If the Bedrock Guardrail's GUARDRAIL_ID or GUARDRAIL_VERSION were unset — a dropped env var, a bad Terraform output — the agent logged a warning, emitted a metric nobody alarmed on, and served requests unfiltered. This wasn't hypothetical: a July adversarial replay scored 0/60 blocked for exactly this reason. Every deployed agent runtime now sets GUARDRAIL_REQUIRED=true; the wiring code raises instead of returning an empty config when required-but-unconfigured, and because each agent constructs its model at import time, the raise crashes the process before it binds its port. A deploy that loses its Guardrail doesn't serve a single unprotected request — it just doesn't come up. A CloudWatch alarm on the underlying metric means it won't fail silently either.

The common shape

Three fail-open windows, same fix: readiness at startup, draining at shutdown, and safety at every tool call. In each case the mechanism that was supposed to protect was itself unprotected — a guard that could silently stop guarding. The fix is the same in all three: crash or reject at the boundary rather than proceed degraded, and emit a distinct metric so the degradation is observable even without the fix.

State Recovery and Idempotency

Three mechanisms underpin recovery specifically:

Mechanism 1 DynamoDB Lock-Based Recovery Optimistic concurrency · 600s TTL
conditional write on (tenant_id, negotiation_id) one holder at a time TTL auto-expiry
Mechanism 2 Session Cache (TCO / Risk / Score) {env}-agent-session-cache table
tco#{supplier_id} risk#{supplier_id}#{category_id} score#{bid_id} + input_hash
Mechanism 3 SUPERSEDED Marking on Cycle-Back REQ-G305 · 3 retries, 500ms/1s/2s backoff
all bids marked before reinvoke re-marking is a no-op all retries exhausted → halt → RA

The session cache deserves particular attention. Each cached result is stored with an input hash — not just the result. This means idempotency is verified at call time: if the inputs change (e.g., a supplier updates their proposal between a crash and recovery), the cache miss forces a fresh computation. This is a subtle but important correctness guarantee for negotiation scenarios where stale results could materially affect the outcome.

Keeping State and Events Consistent

A state mutation and the event it produces — a DLQ escalation, a purchase-order export handoff — used to be two independent writes: one to DynamoDB, one to SQS. A crash between them could leave state and events pointing in different directions. They now commit together, in the same DynamoDB transaction, via an outbox table that a scheduled poller drains to its real destination. DLQ escalations also stopped requiring a human to notice and manually replay them — a scheduled process now resumes each one automatically from its last checkpoint, and only routes to a human queue once a bounded number of automatic attempts has been exhausted.

Undoing What Can't Be Resumed

Checkpointing and locks handle forward recovery — resuming a negotiation that can still complete. They don't handle a negotiation that's been abandoned: the total-timeout ceiling is reached, or an operator cancels it, after money-moving or supplier-notifying side effects have already committed. Resuming forward is the wrong move there; the effects need to be undone instead. Each side-effecting step — sending bid invitations, writing an award, issuing a purchase order — now records a compensating action alongside the effect itself. If a negotiation is abandoned, those compensations replay in reverse order, newest first, each through an idempotent undo handler, until the negotiation reaches a clean terminal state. It's the backward half of the same recovery story the checkpoints tell forward.

Architectural Trade-offs

No failure-handling architecture is free. Here are the explicit trade-offs we made and the reasoning behind them, including a few we're still living with.

⊕
Deterministic DAG vs. Dynamic Agent Graph

Chose: fixed DAG. Trade-off: less routing flexibility. Gain: bounded failure surface, auditable escalation paths, predictable recovery behavior. Dynamic graphs are harder to audit — every edge becomes a potential silent failure.

⊕
DynamoDB-First Escalation vs. SQS-First

Chose: DynamoDB as the authoritative signal. Trade-off: DLQ visibility is delayed if publish fails. Gain: DLQ outages can't mask business failures. The dlq_publish_failed metric surfaces DLQ health independently.

⊘
Approximate & Proceed vs. Halt & Escalate

Chose: approximate for mid-tier failures, halt for governance thresholds. Trade-off: approximated results carry uncertainty. Gain: pipeline continues for routine degradation; only genuine anomalies interrupt human workflows.

⊕
Manual Restart for Auction Partial Failure

Chose: intentional ops pause over automated recovery. Trade-off: human intervention required. Gain: auction fairness is preserved — automated recovery from an asymmetric participant state could introduce bias that's harder to audit than a clean manual restart.

⊕
Input-Hashed Cache vs. Result-Only Cache

Chose: cache stores result + input hash. Trade-off: slightly larger cache entries, hash comparison on every read. Gain: changed inputs after a crash trigger a fresh computation — prevents stale negotiation results from propagating silently.

⊘
Rule-Based Fallback vs. No Fallback for Classifier

Chose: rule-based fallback at 75–90% accuracy depending on quadrant, against an LLM baseline around 95%. Trade-off: misclassifications can route to a suboptimal strategy node — worst case on BOTTLENECK, where the fallback is weakest. Gain: low-risk classifications keep flowing during an outage instead of blocking everything; the riskiest fallback outcomes (empty supplier pool, too few risk signals) are rejected straight to human review rather than auto-proceeding.

⊘
Per-Operation Bulkheads vs. Admission-Only Backpressure

Chose: ship per-operation-type concurrency caps ahead of need, then remove them once the deployed call shape showed they were unreachable. Trade-off: engineering effort spent on a mechanism that never bound a single call in production. Gain: a simpler system once we confirmed the per-tenant admission gate — reserved, max, and weight, enforced at negotiation-admission time — is the boundary that actually does the work.

⊘
Uniform Approval Timeout vs. Tier-Specific Windows

Chose: a single 7-day auto-cancel window across all Kraljic tiers. Trade-off: the highest-stakes tier arguably warrants a shorter window before an unattended approval quietly expires. Gain: one timeout to reason about and tune, at the cost of not yet differentiating by risk tier — an open question rather than a closed one.

⊕
Scheduled Sweep vs. Pipeline-Native Timeout for Approval Escalation

Chose: a separate scheduled sweep (30-minute cadence) to escalate and auto-cancel stale approvals, rather than letting the pipeline's own timeout-and-retry policy carry that job. Trade-off: up to 30 minutes of lag between the 96-hour boundary and the escalation actually being recorded. Gain: correctness — retrying a timed-out approval step turned out to silently re-arm its own clock, since the retry re-ran the same code that starts the wait in the first place. A timeout that resumes the thing it was timing is the wrong shape for a human-approval step; ending the run cleanly and letting an independent sweep own the status transition isn't.

Not every gap we know about is closed. The rule-based Kraljic fallback, for instance, still lacks its own circuit breaker after repeated consecutive fallbacks in a short window — today that shows up as an alarm an operator has to notice, not an automatic escalation. We'd rather be honest about where the design is still catching up to the failure modes we've found than round it up to "handled."

Three Nodes Worth Examining Closely

Bottleneck Negotiation — Most Architecturally Complex

The Bottleneck agent is the most failure-rich node in the pipeline. It runs tool calls for TCO computation, risk scoring, and proposal delivery — all of which can fail independently. Its failure strategy layers tool-level fallbacks (approximated TCO on tool unavailability), hook-level circuit breaking (5 consecutive rejections → DLQ), DynamoDB session cache for crash idempotency, and explicit full-round vs. partial-round proposal delivery failure paths. Designing it this way meant treating every one of those failure modes as a first-class case up front, rather than discovering them in production.

Spot Bidding Agent — Circuit Breaker per Supplier

The Spot Bidding agent introduced a design that's worth highlighting: rather than using a single circuit breaker for all supplier communications, it maintains a circuit breaker per supplier. This means one supplier going offline doesn't halt the entire bidding round — the agent continues polling remaining suppliers and compiles partial results. The zero-bids terminal path (all suppliers fail to respond) is handled as a distinct escalation, not as a degenerate case of partial failure. Deduplication uses a (negotiation_id, supplier_id, type) composite key in DynamoDB to prevent duplicate bids from retries.

Bid Evaluation — Quality-Gated, Deterministically

Bid Evaluation used to be our seventh agent; it's now inline deterministic scoring in the Node 5 executor, and it still treats suspicious-bid detection as a first-class concern rather than a post-hoc check. Every bid is checked against its supplier record and its price/delivery fields before scoring; a bid with no matching supplier or an untrustworthy price or delivery figure is flagged suspicious rather than scored normally. When more than 10% of evaluated bids come back suspicious across a round of five or more (a lower absolute threshold applies to smaller rounds), or when zero bids remain trustworthy regardless of ratio, the node halts and escalates rather than proceeding with a best-effort result. Bids that clear evaluation still carry a separate over-budget flag when their price exceeds the negotiation's budget limit — surfaced for downstream and human reviewers, not auto-rejected.

Takeaways for Agentic System Design

The patterns behind this design aren't specific to procurement — they apply broadly to any system where autonomous agents take consequential actions:

Make the failure surface explicit before you build. Every agent tool call should have a documented answer to: what happens if this fails? Treating failure as an afterthought means you discover the answers in production.

Separate the escalation signal from the notification channel. If your escalation depends on a messaging system that can itself fail, you have a single point of failure in your safety net. Write to an authoritative store first; publish to queues fire-and-forget.

Idempotency is not optional in agentic systems. Agents retry. Infrastructure restarts. The same action will be attempted more than once. Every tool call that produces side effects needs an idempotency key, and every cache needs an input hash, not just a result.

Order your timeouts deliberately, not by default. A fallback that's correct in isolation can still never run if the process hosting it dies first. Every timeout in a call chain needs to sit below the budget of whatever would otherwise kill it.

Some failures deserve manual intervention, not automation. The temptation to automate recovery from every failure mode is real — but some failure states carry enough ambiguity that automated recovery could make things worse. The Leverage auction partial failure is a deliberate example: the right answer is a human decision, not an algorithm.

"The goal isn't to eliminate failures — it's to ensure that every failure is visible, categorized, and responded to with intention."
