Wiring agents into SAP with the AWS for SAP MCP Server

Buyer Team's SAP transport isn't code we wrote. It's AWS's own GA server, running on AgentCore Runtime, reaching an ERP through nothing but its standard OData surface. This is what that choice buys, what it costs, and how a requisition raised in SAP ends up as a negotiated purchase order written back to it — across a contract four operations wide.

Every procurement automation platform eventually runs into the same wall: the ERP. Buyer Team's negotiation chain is entirely ours — six agents, a deterministic Step Functions DAG, our own data model. But a negotiation begins with a purchase requisition somebody raised in SAP, and it ends with a purchase order that has to land back in SAP. Both ends of the system belong to someone else, and they speak OData.

We had already written that client, and it worked. orchestrator/sap_client.py is a perfectly good Python OData client driving an automated requisition-to-order loop. The problem with it isn't quality; it's ownership. A hand-rolled ERP client makes you the maintainer of an integration surface that changes on somebody else's schedule, in a domain where the cost of being subtly wrong is a purchase order that shouldn't exist.

So our integration design names a different transport: the AWS for SAP MCP Server, GA since 1 May 2026 — a container image AWS publishes and you deploy onto Amazon Bedrock AgentCore Runtime. The appeal is straightforward. Your agent never learns SAP. It calls generic tools — odata_read, get_metadata, odata_create — and the server owns catalog discovery, query construction, authentication and response handling. Business logic stays on AWS. SAP is touched only through its standard API surface, which is a clean-core pattern rather than a pile of custom ABAP extensions.

The claim underneath all of that is the integration becomes configuration rather than code. This post is what happened when we tested it.

The loop this is all for

Before any configuration makes sense, it helps to see what the integration carries. A requisition is raised in SAP and sits there OPEN. Buyer Team notices it, prices it against SAP's own materials catalog, negotiates it across six agents, awards it, and writes the resulting purchase order back — at which point the requisition SAP started with reads ORDERED and points at a real order document.

Two properties of that picture matter more than anything else in this post. The first is that SAP is only ever touched through its standard OData surface — no ABAP extension, no custom RFC, nothing installed on the tenant side, so an upgrade to the ERP is not an event in our release calendar. The second is that the loop is genuinely closed: the write-back isn't a report or a notification, it's the same requisition transitioning state. That's the difference between an integration that reads an ERP and one that participates in it.

No SAP tenant? Build the other side of the wire

We don't have an S/4HANA system to point at, and renting one to answer an architecture question is not a good trade. What we do have is a SAP Cloud Application Programming Model app serving a procurement domain over OData — suppliers, materials, requisitions, orders and their line items — implementing the real state machine: a requisition starts OPEN, and once bought it gets linked to an order and flips to ORDERED.

Two things had to change before AWS's server could talk to it. It had to speak OData V2, which is what classic SAP Gateway exposes, and CAP serves V4 — an adapter handles that. And it had to be reachable from AWS, which is where the first architectural decision got made and unmade. The original plan was a container on ECS behind an internal load balancer with certificates and DNS. That plan was structurally unworkable and we caught it before building it: none of our SAP Lambdas run inside a VPC, so they could never have reached an internal endpoint. What replaced it is much smaller — the app packaged as a container-image Lambda behind a public Function URL, with no load balancer, no certificate, no DNS, and no cost at rest.

The mock is deliberately cheap, and the cheapness has a cost we chose knowingly: its database lives in memory, so it forgets everything on a cold start. Health and reseed endpoints make that volatility uninteresting rather than expensive to fix. This is the kind of trade worth making explicit, because a test double that costs real money gets switched off, and a test double that's switched off proves nothing.

The request path

Zoom into any one of those four boundary crossings and this is what it looks like. An agent mints a machine-to-machine token; an AgentCore Gateway validates it, evaluates a policy and pins the request to a tenant; AWS's server authenticates outbound to the ERP with credentials it reads from Secrets Manager. Inbound authorization and outbound authentication are separate trust boundaries, which turns out to be the single most useful thing to understand about this architecture.

A detail worth internalising before you configure anything: there are two AWS SAP MCP servers, and conflating them wastes a day. The AWS for SAP MCP Server gives agents access to SAP business data over OData and runs remotely on AgentCore Runtime — that's this post. The AWS for SAP Management MCP Server manages SAP workloads on AWS (health, backups, Systems Manager for SAP) and runs locally over stdio. Different problems, similar names.

Configuration is the integration

Everything about the server is environment variables, validated at startup — a violated rule prints a descriptive error and the process exits. Most of them are connection strings. A few of them encode a security posture, and those are the ones worth understanding before you deploy anything near a production ERP.

Setting Our value Why
SAP_OAUTH_FLOW BASIC What the mock presents. On a real tenant this is the most consequential line in the file — see below.
USE_SAP_CATALOG false There is no SAP service catalog to query, so a custom catalog in S3 names our one service and the server makes no catalog calls at all.
WRITE_ENABLED true Master switch. On its own it enables nothing.
CREATE_ENABLED / UPDATE_ENABLED true The loop creates an order and updates a requisition. That is the complete set of writes it needs.
DELETE_ENABLED / FUNCTION_IMPORT_ENABLED unset Left at their default of false. Nothing deletes an SAP record or invokes custom backend logic, so those tools don't exist for the agent to reach for.

That write configuration is the part I'd argue is genuinely well designed, and it generalises well beyond SAP. Writes require two independent levels of opt-in — the master switch and the specific operation flag — and the server refuses to start if you set the master switch without enabling any operation. You cannot accidentally give an agent a delete tool against an ERP. That's scope reduction at the server rather than instruction in a prompt, and it's a much stronger guarantee than telling a model what not to do.

The same logic extends to the setting that restricts which services the discovery tool will even surface. We didn't need it against a single-service mock, but on a real tenant it's the control that matters most: an agent scoped to procurement should not be able to discover finance services, let alone read them. Making a capability undiscoverable is a stronger guarantee than making it forbidden.

Scoping a tool surface you don't own

Buyer Team's own MCP servers are multi-tenant, and they're protected by a house pattern: a Gateway interceptor that overwrites the tenant identifier on every call from the caller's token, and a policy engine scoped to specific tool names. Copying that shape onto AWS's server was the obvious first move, and it would have broken every call — because AWS's tools take no tenant parameter. Nothing in the surface is named tenant_id.

So the Gateway went out deliberately bare, which was correct for a single-tenant validation. What it took longer to see is that the tenancy axis exists under a different name. The parameter every one of those tools accepts is service_name — and service_name is precisely what decides which SAP system a call reaches. Pin that from the token and you get the same guarantee the house pattern gives, on a surface the house pattern doesn't fit.

⊕
The interceptor pins service_name

Overwritten from the caller's token claim on every call, failing closed when the claim is absent. No caller passes a tenant, so no caller can pass the wrong one. Tenants get their own catalog entries rather than their own runtimes — one Gateway, one server, entries in a map.

⊗
The policy engine is the outer ring

Cedar sees a coarse action and an opaque request body. It can decide whether a principal may reach the SAP surface at all; it cannot decide which service they get. Knowing where a policy engine's vision ends is what stops you writing policy that can't see what it's deciding about.

⊕
A separately revocable credential

SAP access is its own machine-to-machine client on its own scope, independent of every other skill's client. Revoking an agent's ERP access shouldn't require revoking anything else, and shouldn't require a deploy.

The generalisable lesson is small and portable: every multi-tenant surface has an axis that decides whose data you reach. It just doesn't always share your naming. The question isn't whether your pattern's parameter exists on someone else's tool — it's which of their parameters is doing that parameter's job.

How it got built

Six phases over several weeks, each independently verifiable, and nothing merged on the strength of a passing unit test alone. Every phase names the rig that proved it: an offline Docker Compose stack with real Lambda containers on a local AWS emulator, and a live dev account with the real Gateway, the real runtime and AWS's real container. Prove it offline, confirm it live.

1
Prove the shape
Deploy AWS's actual image — not a stand-in — register it behind a Gateway, and drive a full create-and-update round trip from an authenticated client. Three boundary problems stood between "deployed" and "working": an undocumented IAM permission, a protocol handshake one side assumes and the other never implements, and a runtime lifetime that doesn't mean what its setting is named. None of them are inferable from either party's documentation, and all three cost less than a day once we were looking at real logs instead of reasoning about them.
✓ Answered the architecture question — and moved the product exactly zero distance, which is worth naming out loud
2
Put the loop in the deployed path
The probe proved a transport that exactly one integration test could reach; the deployed functions were still pointed at an empty URL. Closing that meant computing configuration from infrastructure rather than setting it by hand, moving credentials to a secret both sides read so they can't drift apart, and pushing the protocol handshake down into the shared client where no caller needs to know it exists.
✓ First unattended run: a real requisition produced a real event, a real domain row and a real negotiation — no test code invoking any of it
3
Make failure visible
A loop that runs unattended has to say so when it stops. Alarms went on the obvious failures and on the one that isn't: exports that are pending but never draining, where nothing errors and nothing moves. A drift check compares the deployed test double against the version we think is running, which turned out to matter more than expected — it caught a build that was pushing successfully and deploying nothing at all.
✓ Every later phase deployed on the first attempt, verified nightly against a green baseline
4
Make the contract look like S/4
Everything so far had been proven against a domain model of our own invention, and a mock whose field names we chose can't tell you whether the mapping layer survives contact with a real one. So the mock grew a second service under genuine S/4 entity and field names, plus the organisational fields a real document carries — company code, plant, purchasing organisation and group. Added alongside the first rather than replacing it, so callers could migrate one at a time.
✓ The mapping layer stopped being a fiction, and optimistic concurrency became something we'd tested rather than assumed
5
Join the data, promote the transport
Until this point the pipeline carried a requisition to a negotiation that then stopped for want of candidate suppliers — a precise, legible answer from a working system, naming its own next step. Supplier and category data began crossing the same boundary as the requisition, and pricing gained a distinction that matters: the materials catalog price scores the bids, while the requisitioner's own estimate stays the budget ceiling. Conflating those two numbers would move an authorised budget silently.

With both transports finally reading one contract, AWS's server became the default and the hand-written client became the fallback rather than the primary.
✓ A SAP-sourced negotiation reached an award, with candidates and scoring both traceable to SAP data
6
Scope the surface, close the failure paths
Tenancy moved from asserted to enforced, per the section above. The dead-letter queue got a consumer rather than just an alarm, along with a classification model for the ways a message can be undeliverable — writing that list is the design work, and it's what surfaced a message type that had been silently discarded. And suppliers gained the ability to expose their own MCP servers, discovered and registered at runtime, which is the same integration pattern pointed outward instead of at the ERP.
✓ Every message has somewhere to go, and every call is pinned to a tenant before it reaches SAP

"Almost every finding in that sequence is a boundary problem — a permission nobody documents as required, a handshake one side assumes and the other never implements, a setting that doesn't mean what it's named. None of them live in either party's code. They live in the gap, and the only instrument that reads the gap is a deployment."

Verdict
The integration really is configuration rather than code — and getting the configuration right took a deployment. A requisition raised in SAP becomes a negotiated, awarded purchase order written back through AWS's own server, with suppliers and catalog prices sourced from the ERP, every call pinned to a tenant, and no extension of any kind installed on the SAP side. What it is not is a validation of S/4HANA semantics — the thing on the other side of the wire is still an app we wrote, and that distinction does more work than everything above it.

The remaining distance to a real tenant

A mock is not a tenant, and each phase has been explicit about which part of the distance it closed. Field names being right is the cheapest part of being right. Four pieces of the real-tenant path are still ahead, and every one is a design decision rather than a chore — which is the good kind of remaining work:

Transport
SAP BTP API Management
Not built
AWS's recommended pattern routes through BTP rather than pointing the server at the SAP gateway directly, with the Destination Service resolving the backend. Our Function URL stands in for that whole layer.
Identity
Outbound OAuth flow
Consequential
The real choice is a single service account versus on-behalf-of token exchange — and it's an authorization design decision, not a plumbing one.
Grounding
Service hints
Underrated
A hints file maps human concepts to exact SAP property names, with known issues and workarounds. This is the documented mechanism for stopping a model inventing field names against a 400-field entity.
Semantics
S/4 business validation
The real distance
Release strategies, budget availability checks, account assignment, number ranges. Our app accepts an order because the columns line up. A real system accepts one because a controller's configuration says it may.

The identity one deserves more than a card, because it's the decision most likely to be made by accident. A single machine-to-machine service account collapses every user into one identity and moves the entire authorization burden into your agent layer. On-behalf-of token exchange propagates the end user's identity into SAP, so SAP-side authorization objects still apply and a buyer sees only their own purchasing group. In a regulated landscape, keeping that burden in SAP where the authorization model already lives is usually the better trade — and it's worth deciding deliberately at design time rather than discovering after an audit.

And one boundary the server doesn't cross

MCP is a request/response tool-execution protocol. The server does not subscribe to SAP business events. If you want an agent to react the moment a requisition is raised, that's a separate architecture you compose alongside it — SAP Event Mesh to EventBridge to a function that starts an agent session, which then reads back to enrich from whatever identifier the event carried. Our scheduled poller is precisely a stand-in for that missing event source.

Worth being honest about which parts of a design are AWS features and which are your own composition; the two get blurred in a lot of writing about this server, and the parts you composed are the parts you have to operate. Idempotency and poison-message handling are yours either way — at-least-once delivery means the same document arrives twice, and a failing agent session belongs in a queue somebody drains rather than retrying forever against an ERP.

What we'd tell the next team

Deploy the real image early, then keep deploying. Every finding worth having came from the gap between two systems, and gaps are invisible to both sides' test suites. Our offline coverage is good and it could not have caught a single one of them.

Separate "the shape holds" from "this is what runs." The first probe answered the architecture question completely and moved the product zero distance. That distance turned out to be five phases wide, and it is very easy to declare victory at the end of the first one. Naming the two things differently is most of what stops you.

Prefer scope reduction to instruction. The best security property in this whole integration is that the delete tool doesn't exist, because a flag wasn't set. A capability an agent cannot discover is a much stronger guarantee than a capability you've asked it not to use, and that principle transfers to every tool surface you build or adopt.

Find your pattern's analogue rather than forcing your pattern. The house tenancy pattern didn't fit a surface with no tenant parameter, and scoping the Gateway bare was the right first move. The better question, once you know a surface, is which of its parameters is doing your parameter's job.

Make the fallback fail the test. A graceful fallback and a green assertion are indistinguishable from a working primary path. If a new transport is wrapped in a broad exception handler, the only test worth writing is one that makes the old transport explode on contact. That single line is the difference between proving something and hoping about it.

The integration is configuration — and the configuration compounds. A requisition raised in SAP now becomes a negotiated award and a written-back purchase order without anyone watching, scored on the ERP's own catalog prices, routed to the right tenant's service, and recoverable from every failure path we know how to produce. Four operations wide, nothing installed on the SAP side, and each phase small enough to describe in a paragraph. The system is the sequence, not any one of them.
