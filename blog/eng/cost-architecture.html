The cost architecture of an autonomous procurement agent

Our target is a weighted-average negotiation cost under $0.10. What's actually deployed to get there is a 3-tier Amazon Nova model ladder, partial prompt caching, a Kraljic classifier that mostly never runs at all, and a context-compaction hook — four real, shipped mechanisms, each one shaped by live evidence and each built around a specific trade-off: how much of the request to cache versus keep fresh, how much classification to skip versus recompute, how much context to keep versus discard. This post covers how the mechanisms work, the trade-off behind each one, and what a full live negotiation suite actually costs today — plus two newer capabilities that have quietly made the whole thing more self-correcting: an automated tier-rollback safety net and a quality-driven cache invalidation, both from a closed-loop evaluation system.

An earlier version of this post described a broader cost architecture: two model-family scenarios, a five-layer optimization stack including nightly Bedrock Batch inference, and an hourly CUR/Athena pipeline joining AWS's actual bill to per-tenant token counts. A repo audit reconciled that description against what's actually running — a second model family, batch inference, and CUR attribution were never built, and we've deferred them deliberately rather than build them now. That deferral is itself a mitigation, not a gap: building an attribution layer on top of a cost number nobody had verified would have turned an honest absence into a confidently wrong chargeback figure.

This is the corrected version. It covers the four mechanisms that are actually shipped, the trade-off behind each one, and what the metrics they emit — including negotiation.total_cost_usd and the newer, finer-grained cost.usd — actually show today.

What's actually deployed

Buyer Team turns a Purchase Requisition into a negotiated Purchase Order across a seven-node Step Functions DAG. Four mechanisms currently work to keep that cheap:

Mechanism What it does Where
Model tiering 3-tier Amazon Nova ladder (Micro / Lite / Pro), resolved per agent at build time DynamicAgentFactory + model_resolver.py
Prompt caching Bedrock cachePoint on the system prompt only — tool-schema caching exists in code but is dormant on Nova buyer_agent_core/cache.py
Kraljic short-circuiting Manual override → seeded quadrant → semantic cache → live agent → rule-based fallback, in that order — the LLM is the last resort, not the default path orchestrator/node_kraljic_classify.py
Context compaction Truncates oversized tool results (head + tail elision) before they re-enter the conversation on multi-round agents buyer_agent_core/compaction.py

Two things that were part of the original cost story are not on this list because they don't exist: nightly Bedrock Batch inference for supplier KPIs, and a second, Claude-based model-tiering scenario. Neither has a line of code anywhere in the repo. We come back to what is missing, and why we're not building it yet, further down.

Layer one: a Nova ladder that keeps getting pruned toward "don't call a model at all"

Model selection resolves an abstract tier label — SimpleLLM, DefaultLLM, StrategyLLM — to a concrete Bedrock model ID at agent build time via DynamicAgentFactory, reading system-config's model/default.tiers map with an environment-variable override and an in-image seed as fallbacks that never raise. Every tier-resolved agent on the negotiation path runs on Amazon Nova — Claude Haiku 4.5 is also live in the stack now, but deliberately outside this system: it powers the post-award LLM-judge evaluators (rationale defensibility, tone, negotiation quality) via a direct bedrock-runtime.converse() call, not through DynamicAgentFactory. Keeping judges off the tier ladder is itself a design choice — it means judge quality is never coupled to a cost-tiering decision, at the cost of those calls not going through the tier system's caching or accounting (more on that trade-off below).

Tier Model $ per 1K tokens (in / out)
SimpleLLM Nova Micro $0.000035 / $0.00014
DefaultLLM Nova Lite $0.00006 / $0.00024
StrategyLLM Nova Pro $0.0008 / $0.0032

An EvalLLM tier (Llama 3.1 8B) is seeded in the tier map but still unused for that purpose — the LLM-as-judge path that's actually live runs on Claude Haiku 4.5, configured independently rather than through this tier system, for the reason above. Rates for the tier-resolved models are baked into orchestrator/resilience/pricing.py, keyed by the literal resolved model ID rather than the tier label, because the tier→model mapping can drift live via system-config and pricing by what was actually invoked is more accurate than pricing by tier name.

The interesting part isn't the ladder — it's that a tier assignment is treated as a hypothesis to keep checking against eval-harness scores, not a decision made once and left alone. That checking loop has driven every production change to the ladder so far, and it recently closed all the way: a bad tier assignment can now roll itself back without anyone paging in.

⊙
Config-driven promotion, not a redeploy

Because the tier→model mapping lives in system-config rather than in code, moving an agent to a stronger tier when eval scores call for it is a config change, not a build-and-ship cycle. Two agents have been promoted this way so far — Bid Evaluation and the Kraljic Classifier both moved up a tier after eval-harness scores made the case, each a same-day config edit.

◎
The cheapest tier is sometimes no model call

The bid_evaluation_llm runtime was retired outright and replaced with deterministic inline scoring — composite cost/delivery/quality/ESG/history math with no A2A agent, no Strands, no token cost, and none of the ~25–58s AgentCore session overhead an LLM call carries on every award decision. The trade-off: less flexible than a model reading the bid narrative, but a materially faster and cheaper award path for a scoring function that's fully specifiable in code. Spot Bidding and Leverage Auction both price deterministically below a $5K threshold for the same reason, reserving the LLM call for negotiations where the reasoning is worth the cost.

⊙
An automated rollback safety net

Every human tier promotion is now snapshotted to a previous-tier record in system-config before it takes effect. If the live Negotiation Quality eval score later drops under 0.60, a remediation Lambda restores the prior tier map automatically — and every warm agent picks up the change within 30 seconds via a config-epoch watch in DynamicAgentFactory, no container restart required. The tier ladder now tunes itself upward on evidence and reverts itself downward on regression, both without a deploy.

Award & Communications tells the same story from a different angle: it's configured on SimpleLLM and the runtime is deployed and kept warm, but the synchronous PR→PO path never invokes it. Both the winner notification and every rejection notification render from deterministic Python f-string templates — 0 LLM tokens on the notification content itself, and it removes the ~25–32s A2A round-trip from every award. The winner notification uses a standard "refer to your contract for execution" line rather than LLM-generated rationale. The Award node does make a real Bedrock call now, just not on this path: an async, post-award self-invoke feeds the negotiation's reasoning to the Claude Haiku judges described above, entirely off the synchronous award critical path.

Put together, the current agent-to-tier picture is much leaner than a seven-agent fan-out:

Node Tier Tokens on the live path
Kraljic Classifier DefaultLLM Usually 0 — short-circuited by seeded quadrant or semantic cache (see below)
Spot Bidding DefaultLLM 0 below $5K (deterministic pricing); LLM call above it
Leverage Auction StrategyLLM 0 below $5K (deterministic pricing, same bypass as Spot Bidding); LLM call above it
Bottleneck Negotiation / Strategic Partnership StrategyLLM Always an LLM call — no deterministic bypass on either path. Exactly one of these three strategy nodes fires per negotiation; Kraljic quadrant routing is exclusive
Bid Evaluation (none) 0 — deterministic scoring, no LLM agent exists
Award & Communications SimpleLLM (configured, unused) 0 — deterministic templates, runtime never invoked live

That's a materially different shape than "every negotiation fans out across a graph of LLM agents." For a Non-Critical spot bid under $5K with an already-classified category, the live path may not call an LLM at all. The shape didn't come from designing a leaner architecture up front — it came from evidence pushing two agents toward stronger tiers and one toward no model call at all, and from now checking that decision continuously instead of once. Cognitive-demand tiering only holds if you keep checking whether the demand was real.

Layer two: prompt caching, with cross-tenant leakage designed out

Bedrock prompt caching stores the request prefix — normally the system prompt and tool schemas — so a byte-identical prefix on a later call reads at roughly a tenth of standard input cost. Live testing against Bedrock Converse found this splits by cache-point location, not uniformly by model family: the full Nova family (Micro/Lite/Pro) accepts a cachePoint in the system block, but Nova rejects one inside toolConfig.tools outright. Claude accepts both. cache.py gates the two independently as a deliberate trade-off — full tool-schema caching stays Claude-only code, ready but unused, rather than special-casing Nova's narrower support at every call site. On the live negotiation-path fleet, which runs entirely on Nova, only the system-prompt half of the discount is real:

Caching by definition means reusing something written for one call on a later, different call — which is exactly the shape of a cross-tenant data leak if the cached prefix ever contains anything tenant-specific. That's the risk a shared prompt cache carries by construction, and it's mitigated at the build boundary, not at request time: DynamicAgentFactory is the single assembly point, and a test fails the build if any per-invocation value — supplier data, round state, resolved tenant thresholds — lands before the cache checkpoint. That's what makes the cached system prompt identical across every tenant, negotiation, and round sharing an agent's build config, and it's why a cross-tenant cache hit is safe rather than a data leak: the only thing before the checkpoint is public boilerplate, never tenant data.

What we didn't have for a while was visibility into whether the caching was paying off at all. A cache.hit metric closed that gap — 1 or 0 per invocation, emitted whenever Bedrock reports either cache-usage key, so Average over a window is directly the hit rate, live on the FinOps dashboard. Nearly a month of data now says the system-prompt cache is actually working, not just correctly configured: 28 of 29 recorded invocations for the Kraljic Classifier — the one agent generating enough dev traffic to measure — hit the cache, a ~97% rate against the 5-minute TTL. The first fully-green live end-to-end suite confirms the same thing at larger scale, with token counts read straight off OTLP trace spans: 116.1K cache-read tokens against 275.5K uncached input tokens across the run, each cache-read token priced at roughly a tenth of standard input — a real, measured discount, not a theoretical one.

Extending caching from the system prompt to Strands' message-level cache config for Nova was evaluated and deliberately left off. Nova only accepts a cachePoint on a text-only user turn, and Strands always places the cache point on the last user message — which in a multi-round tool loop is a toolResult turn from round two onward, exactly the shape every StrategyLLM agent runs (Leverage Auction, Bottleneck Negotiation, Strategic Partnership). For those agents the feature would cost a request failure, not save anything, so the extended cache config stays Claude-only for both tool- and message-level caching, and the finding is recorded in cache.py's docstring so the trade-off doesn't need re-evaluating. The practice worth keeping: test a caching extension against the model's actual accepted request shape before turning it on, not just against the API's documented surface.

Layer three: the classifier that mostly never runs

The Kraljic Classifier assigns a procurement category to one of four quadrants. orchestrator/node_kraljic_classify.py resolves it in priority order, and the LLM is the fallback of last resort, not step one:

  1. Manual override — operator-pinned quadrant, feature-flagged off by default; highest precedence when enabled.
  2. Seeded short-circuit — the category's row already carries a kraljic_quadrant; return it directly.
  3. Semantic cache — a prior classification for the same category, thresholds, and cache epoch, keyed on tenant, category, and a hash of the thresholds, 24h TTL.
  4. Live agent — invokes the Kraljic Classifier runtime (DefaultLLM/Nova Lite); persists and caches the result.
  5. Rule-based fallback — deterministic axis rule if the agent is unavailable or returns a malformed response.

A cache keyed only on category would carry a staleness trade-off: if profit-impact or supply-risk thresholds change, a cached classification computed under the old thresholds would keep being served as if nothing changed. That's handled by folding the thresholds into the cache key itself — any threshold change produces a new key automatically, no separate invalidation step to remember. The same self-invalidation mechanism also responds to classification quality rather than just threshold changes: if the live Kraljic Accuracy eval score drops under 0.90, a remediation Lambda bumps a governance cache-epoch counter, which folds into every future key and makes the entire cache miss and repopulate on next read — no scan, no delete, existing rows simply age out on their unchanged 24h TTL. Because most live categories are pre-classified and the cache now invalidates itself on both dimensions, step 4 is rare in practice. The dollar saving from a cache hit here is genuinely small — on the order of a fraction of a cent per classification, once you're already avoiding full input-token price via prompt caching — but that's not really the point. The bigger saving is upstream of caching entirely: most categories never reach the agent at all.

Layer four: context compaction

Multi-round agents (Leverage Auction, Bottleneck Negotiation, Strategic Partnership) accumulate tool results across rounds, and an unbounded tool output re-enters every subsequent LLM call in that conversation — the risk being both runaway token cost and, eventually, a context window that can't fit the negotiation's own history. A Strands AfterToolCallEvent hook mitigates it by truncating any tool result whose serialized size exceeds a configured character cap (default 4000). A second, narrower risk sits inside that fix: truncating naively from the head alone would silently drop the thing that usually matters most in a long tool output — a running total, a final status — from the tail. The hook avoids that by keeping both ends, splitting the budget two-thirds to the head and one-third to the tail. This is the one piece of the original cost story that was accurate the whole time; it shipped correctly and hasn't needed correcting.

What we haven't built, and why that's not an oversight

Three things from the earlier version of this post don't exist, and we're not building them next:

✗
Batch inference for supplier KPIs

No Bedrock Batch job, no feature flag, no nightly schedule, no savings metric. Supplier KPIs used by negotiation agents are read as static/seeded data today, not recomputed by any inference job — on-demand or batch.

✗
Per-tenant CUR/Athena cost attribution

A tenant-cost-attribution DynamoDB table is provisioned in Terraform, but nothing populates it — no Lambda, no Athena query, no CUR join. It's orphaned infrastructure, not a partial implementation. (A narrower, aggregate-only sibling now exists — see the FinOps dashboard's AWS-cost-by-service widget below — but it carries no tenant dimension and doesn't touch this table.)

✗
Cost alarms of any kind

Two token-volume spike alarms exist as an untuned first pass — the code's own comment calls them "first-pass guesses only, no real dev volume data exists yet to tune against." No dollar-denominated alarm, no per-tenant anomaly detector, no budget near-breach warning, and no retry-overhead tracking exist anywhere.

The honest reason to leave these alone isn't bandwidth — it's that all three are second-order systems built on top of a first-order signal, negotiation.total_cost_usd. That signal is now verified against the real table and backed by a companion success-rate metric (below), but it's still a low-volume number: dev hasn't run enough live negotiations yet to give an attribution pipeline or a dollar-denominated alarm anything meaningful to key off. An attribution pipeline built ahead of that volume would produce a confidently precise-looking chargeback figure on a thin sample, which is worse than an honestly absent one. The trade-off is deliberate: build the second-order systems once the first-order signal has the volume to support them, not before.

Verifying the number the rest of this depends on

Every mechanism above is only as trustworthy as the number that's supposed to prove it's saving money. That number is negotiation.total_cost_usd, dimensioned by tenant_id, negotiation_id, strategy, and kraljic_quadrant. The mechanism behind it is straightforward and, on its own, well designed:

Step 1
Price each completed agent call
Every A2A call in invoke_agent_runtime() that returns both a resolved model_id and a negotiation_id is priced via pricing.estimate_cost_usd(model_id, usage), against the baked-in per-model rate table — the same one behind the tier prices above.
Step 2
Accumulate atomically per negotiation
The priced delta is added into a DynamoDB negotiations-table item via an atomic increment update expression, since a negotiation's cost is built up one agent call at a time across multiple node Lambdas.
Step 3
Read once, at whichever terminal node ends the negotiation
Three Step Functions terminal nodes — Bid Evaluation's no-qualifying-bids cancellation, Award & Comms' commit, Approval Gate's rejection resume — each independently re-read the accumulator fresh and emit negotiation.total_cost_usd once, degrading to 0 on a read failure so cost tracking can never block an already-committed transition.

Accumulation deliberately sits behind a broad exception handler that logs and moves on — the same graceful-degradation posture this system applies everywhere else (Kraljic's rule-based fallback, memory's degraded-boolean-OR, terminal nodes reading 0 on a DynamoDB failure), on the principle that cost tracking must never be the thing that gates a negotiation. Every value in the update's expression values is Decimal-typed end to end, matching DynamoDB's resource-API contract, and the unit test for the accumulator asserts that type directly rather than just a captured value — the standard for tests touching this write path. The design leans on a second practice alongside the handler itself: verify the accumulator against the real negotiations table directly on anything that touches this pipeline, rather than trusting the dashboard alone — the same habit that keeps every mechanism in this post honest.

Two companion metrics now sit alongside the accumulator itself. An invocation-success metric and an unpriced-model-invocation metric (with its own CloudWatch alarm) give a success-rate signal on the agent calls this pipeline prices and flag any model that's configured but has no entry in the pricing rate table — previously priced at $0 with no trace. And a newer cost.usd metric emits a per-call dollar figure dimensioned by tenant_id, agent_name, and model_id — a finer-grained view underneath the per-negotiation total, useful for spotting which agent or tenant is driving spend without waiting for a negotiation to complete. One boundary worth stating plainly: the Claude Haiku judge calls from Layer one run through a raw bedrock-runtime.converse() call, not invoke_agent_runtime(), so they sit outside all three of these signals by design — they're evaluation-only, off the negotiation critical path, and not billed to a negotiation's total.

We're not going to publish an invented per-negotiation dollar figure. That aggregate figure spans many negotiations across the full strategy space, not one, so it isn't a like-for-like replacement for a per-negotiation p50 or p90 — dev still hasn't accumulated enough live negotiation volume for that distribution. But it's real, dated, and multi-model evidence in a way a single sample can't be: it confirms the caching discount at scale (116.1K cache-read tokens priced at roughly a tenth of the 275.5K uncached-input tokens they'd otherwise cost), it shows the tier ladder holding its shape under load (142 Nova Pro calls against 40 Nova Lite, consistent with strategy agents dominating token spend), and it gives a first real anchor for the Claude judge calls (23, roughly one per award on the async path). The FinOps dashboard — now ten widgets, covering token usage by agent/tier, cache read/write counts, agent-session duration by tenant, cost per negotiation, real AWS-billed cost by service from a daily Cost Explorer poll, cache hit rate, agent invocation success rate, unpriced-model-invocation count, invocation count by tenant, and the per-call cost.usd widget — is wired to the right metrics and ready to plot a real distribution the moment negotiation volume gives it one. The service-level cost widget is real data today; it's just account-wide, not attributable to a tenant or negotiation.

Practices worth carrying into the next mechanism

Assert the contract, not just the current behavior. A test that only checks a captured value can encode an accident as the expected shape, silently, forever. Where a test can check a type invariant instead — a DynamoDB-compatible numeric type, in this case — it should, and that's now the standard for tests touching the cost-write path.

Pair "never block the critical path" handlers with a success-rate signal. Broad exception handling around a non-critical side effect is the right call and should stay — the failure mode it protects against, a dependency outage taking down a negotiation, is real and worth guarding against unconditionally. On its own, though, it can't distinguish occasional failure from total failure, since both look identical from inside a try/except that logs and moves on. The invocation-success and unpriced-model-invocation metrics now give that signal for the agent-invocation and pricing-coverage side of this pipeline; the accumulator write itself is the one piece still relying on table-checks rather than an always-on success metric.

Don't build the attribution layer before the number underneath it has volume. The CUR/Athena pipeline from an earlier draft of this post was never actually built, and holding off was the right call — a per-tenant chargeback built on a thin sample reads as more precise than it is. It stays deferred until negotiation.total_cost_usd has the live volume to be worth attributing.

Treat tier assignments as a hypothesis, not a one-time decision. Every real change to the model ladder — promoting an agent to a stronger tier, eliminating an LLM call from Bid Evaluation entirely — came from live eval evidence, not from re-reading the original cognitive-demand rationale harder. That habit is now partly automated: a tier promotion is snapshotted before it ships, and a quality regression rolls it back without a human in the loop. The cheapest model is sometimes no model at all, and continuous checking is what finds that out.

Keep evaluation off the path it's evaluating. The Claude Haiku judges run async, post-award, through a separate model configuration from the tier ladder they don't participate in. That's a deliberate boundary: judge quality never gets coupled to a cost-tiering decision, and a judge-model change can't accidentally alter what gets cached, priced, or tiered on the negotiation's own critical path.

Summary

What's real and live: a 3-tier Nova model ladder that's been actively pruned toward fewer LLM calls, not more of them, each change driven by eval evidence, config-driven so it ships without a redeploy, and backed by an automated rollback that reverts a bad promotion on its own; a prompt cache that covers the system prompt on the Nova fleet, with cross-tenant isolation designed in at the build boundary rather than patrolled at request time, measured at a ~97% hit rate and now confirmed at scale (116.1K cache-read tokens against 275.5K uncached input across the first full live suite run); a Kraljic classifier that's short-circuited before it's invoked more often than it's actually called, with a cache key that now invalidates itself on both threshold changes and live accuracy regressions; and a context-compaction hook that keeps both ends of a truncated tool result so a running total or final status is never silently dropped. Batch inference, CUR-based per-tenant attribution, and dollar-denominated cost alarms stay deliberately deferred until negotiation.total_cost_usd — now verified against the real table and carrying its own cost.usd per-call breakdown — has the live volume to make building on top of it worthwhile.

The instinct threading through all four mechanisms — verify against the real table or the real trace, not just the dashboard, before building the next layer on top — is what let the tier ladder gain an automated safety net, the Kraljic cache gain quality-driven invalidation, and the cost pipeline gain a per-call metric this month, each addition checked against live data rather than assumed correct. That's the habit worth carrying into whatever gets built on top of this next.
