Specifying and measuring an AI system

A working method for systems that contain a model but are mostly not one.

TL;DR

Most software that "uses AI" is ordinary software with a model call somewhere in the middle. Shrink the nondeterministic surface to one function, specify everything on either side of it, and never let a quality claim into a design document.

Then measure: find ground truth you already hold, blind the judgements that need a human, ablate each layer, and report the number — including where it is bad — before building anything that acts on the output.

The usual conclusion about AI-containing systems is that the ordinary parts can be specified and tested as normal, and the AI part is a black box you just have to live with. That conclusion is wrong on both counts. The ordinary parts are larger and more consequential than they look, and the AI part is measurable — provided you build the instruments for measuring it before you build anything that depends on it.

This is the method I use. It applies to any pipeline that turns source data into model-generated records: extraction, classification, enrichment, graph construction.

1. The line runs through each component, not between them

The common mistake is to sort components into "AI parts" and "normal parts" and conclude that the AI parts can't be specified. That's too coarse.

Count the code in a typical inference component — say, one that extracts concepts from text. The model call is a handful of lines. Everything else is ordinary software: fetching the source record, rendering a versioned prompt template, calling with retry, timeout and backoff, parsing the response, validating it into typed objects, rejecting malformed output, persisting with provenance, and checkpointing so an interrupted run resumes.

That is the large majority of the component. It is fully deterministic, and it is exactly what a specification is good at. The nondeterminism is confined to one function that takes a rendered prompt and returns raw text.

Dex Horthy makes the same observation from the other side in his notes on context engineering for coding agents: a model call is a stateless function, context in and output out, so the context is the only lever you have on quality. He spends his effort on the input. This post spends it on what sits around the function, and the reason is the setting. A coding agent's output is checked for free by a compiler, a test suite and a maintainer. Model-generated records that go straight into a database get none of that, so the checking has to be built.

Reuse this

Shrink the nondeterministic surface to a single function. Everything on either side of it is specifiable, and the boundary is a validation contract rather than a vague seam. If model output can reach your data store without passing through a validator, nondeterminism has leaked into the parts you believed were safe.

2. What belongs in a specification — and what must never enter it

Real requirements are checkable

A requirement for the deterministic scaffolding should describe something that goes wrong in practice and can be tested or gated. I write them in EARS-style constrained syntax ("WHEN trigger THE SYSTEM SHALL response"), though the notation matters less than the property of being checkable. Section 3 gives the six that matter most.

Quality claims are not requirements

Belongs — checkable

WHEN a model response fails schema validation THE SYSTEM SHALL reject it and record the failure.

WHEN an extraction run is interrupted THE SYSTEM SHALL resume without reprocessing completed records.

Never — a hypothesis

THE SYSTEM SHALL extract concepts accurately.

The extractor achieves high alignment against the controlled vocabulary.

The right-hand column is not a set of requirements. These are hypotheses. Written into a design document they acquire the appearance of settled decisions, and they are then quoted back as though they were established. If measuring exactly this is the point of your evaluation, a specification that quietly asserts the answer is the most damaging thing you can put in the repository.

Quality lives in the evaluation as a measured number. It is asserted nowhere else.

Prefer executable invariants to prose

A prose requirement says the system shall. A validator makes it so.

Where a rule is important enough to state, implement it as a constructor-level constraint: a record that cites no source fails to construct; a generated record without a model identifier fails to construct; an answer resting on inference fails to construct without a confidence and a caveat.

Two copies of a rule drift, and the copy that isn't executable is the one that goes stale. Where an invariant exists in code, the specification should point at it rather than restate it.

Guard against spec rot

Prompts change many times. A design document that describes the extraction method in prose describes version one forever while the code moves on.

Have the specification reference the prompt file rather than paraphrase its contents. The scaffolding around the prompt stays accurately described, and the method itself lives in exactly one place.

3. Six instruments that make the AI part tractable

These are deterministic components whose whole purpose is to make the nondeterministic component measurable. They are the highest-value things to specify carefully, because every claim you later make depends on them.

01 · Versioned prompts

Versioned prompts. Prompts are code. They live in files, under version control, referenced by identifier from every record they produced. Without this, a result cannot be attributed to the thing that produced it.

THE SYSTEM SHALL render prompts from versioned template files and record the template version on every generated record.

02 · Validation contract

A validation contract at the boundary. Model output is untyped text until a validator has accepted it. Rejection is a first-class outcome, counted and reported. A silently coerced response is a data-quality failure that surfaces much later and much more expensively.

WHEN a model response fails schema validation THE SYSTEM SHALL reject it and record the failure, and SHALL NOT coerce it into a valid shape.

03 · Provenance

Provenance on every generated record. Source record, model identifier, prompt version, timestamp, method. This is what makes a result auditable and a regression diagnosable.

THE SYSTEM SHALL NOT persist a generated record lacking a pointer to its source record, a model identifier, a prompt version and the sampling parameters used.

04 · Cache

A cache keyed on input, prompt version and model. This is what recovers reproducibility despite a nondeterministic model: a rerun of an evaluation returns identical results because it returns the same cached generations. Low temperature does not achieve this — output can still vary within a model version and certainly across them. Specify the cache, not identical output.

WHEN the same input, prompt version and model have been processed before THE SYSTEM SHALL return the cached result rather than re-calling the model.

05 · Resumability

Resumability. Long extraction runs fail. A run that cannot resume is a run you will be reluctant to repeat, and reluctance to rerun is how stale results survive.

WHEN an extraction run is interrupted THE SYSTEM SHALL resume without reprocessing completed records.

06 · Declared vs inferred

Separation of declared and inferred. Facts published by an authoritative source and facts your model produced are different kinds of statement. Keep them in separate types so they cannot be merged by accident, and so any answer built from them can declare which it rests on.

THE SYSTEM SHALL keep declared facts and inferred facts in separate types, such that no code path can merge them.

4. Measuring the system as a whole

Find ground truth you already hold

The best evaluation costs nothing to label, because the labels already exist somewhere in your source data.

The pattern: identify a relationship your source publishes explicitly, withhold it from the inference pipeline, then measure whether the pipeline recovers it. In a support system, for example, tickets already carry the product area and root-cause category an agent assigned when closing them — hide those labels, classify from the ticket text alone, and check how often the inferred categories match the ones you hid.

This yields precision and recall on the central claim with no hand-labelling and no gold set to construct. Make it the headline metric precisely because no opinion can move it.

Reuse this

Design the held-out split before you look at results, and implement the withholding as a flag in the schema rather than a step in a script, so it cannot be quietly skipped.

Separate reproduction from contribution

An inferred relationship that reproduces something the source already declares proves the pipeline runs. It adds nothing, because the fact was already available.

The contribution is relationships the system infers that were never declared and that a domain expert confirms are real. Report these separately. A system that scores well only by rediscovering published facts has demonstrated a mechanism, not a result.

Blind the judgements that need a human

Where expert judgement is unavoidable, the builder is usually the expert, and self-evaluation reliably flatters the system.

Mix generated outputs with plausible-looking distractors and judge them together without knowing which is which.

If the acceptance rate on distractors approaches the rate on real output, that is the finding — and it is invisible unblinded.

Write the rubric before seeing any output, and do not revise it after seeing the aggregate.

The distinction that matters is what is being judged. Reviewing the inputs to the model — the prompt, the plan, the research it will act on — should be done unblinded, because there your bias is the expertise you want applied. Judging the outputs of your own pipeline is where the same bias flatters, and that is the judgement to blind.

Record confidence per judgement

Expertise is uneven across subdomains. A per-item confidence rating lets results be reported stratified rather than as a uniform expert assertion. If accuracy tracks stated confidence, that is itself evidence the evaluation is functioning.

Attribute value by ablation

Systems accrete signals that nobody has verified are helping. Run the evaluation with each layer removed — base retrieval alone, then with metadata reranking, then with structural constraint rejection — so each component gets a number for what it buys.

Reuse this

Every signal you add gets its own ablation bar. The ablation is cheap compared with discovering later that half the matching logic was noise.

Report numbers, not adjectives

"The system surfaces interesting relationships" is unfalsifiable, and will be recognised as such by anyone with a reason to scrutinise it. A precision figure against a held-out set, with the split described and the ablation attached, is a claim that survives contact with a sceptical reader.

The number does a second job. Horthy argues that the main purpose of code review is mental alignment — keeping a team on the same page about what the system is and how it changes — and that once output is cheap, most of a codebase is unfamiliar to any given engineer at any given time. His answer is that nobody can read a 2,000-line diff daily, but anyone can read a 200-line plan. The same holds here: nobody can audit 50,000 generated records, but anyone can read a precision figure with its split and its ablation. The evaluation report is how the next person understands what the system actually does.

Report the failures too: the share of source rules that could not be structured, the share of records the validator rejected, the subdomains where accuracy was poor. A system that surfaces its own incompleteness is more credible than one presenting a clean surface, and considerably more useful to whoever inherits it.

5. Anti-patterns

Each of these is something I have done or watched someone do. They share a shape: a shortcut that looks free and is paid for later, by someone else.

Anti-patternWhy it fails
Routing deterministic work through the model because it's convenientDestroys the baseline, makes error attribution impossible, and costs money for no gain
Quality claims in design documentsHypotheses acquire the status of decisions
Evaluation designed after results are seenThe split stops being held out in any meaningful sense
Unit tests standing in for evaluationTests confirm output is well-formed, never that it is correct

6. Sequence

Read the stack from the bottom. Each layer is only as trustworthy as the one beneath it, and error multiplies on the way up. Horthy's version for coding agents: a bad line of code is one bad line, a bad line of a plan becomes hundreds, a bad line of research becomes thousands. For a runtime model the chain is the same shape. A bad line in the prompt becomes thousands of bad records, and a bad assumption in the evaluation design makes every one of them look fine. That is why the harness is built before the inference component, not after.

05

Build downstream. Only now build anything that acts on the inferred output.

04

Measure. Ablate. Report the number, including where it is bad.

03

Build the inference component, versioning prompts from the first run.

02

Build the evaluation harness. Deterministic software with clear inputs and outputs — the thing standing between you and believing your own results. It gets full rigour before there are results to be tempted by.

01

Build the deterministic scaffolding, including the six instruments in section 3.

the consequential layer rests on everything below it

Why step five waits

Step five is the one most often taken early. Anything that gives advice, issues a credential, or otherwise affects a person is the consequential layer. Put it on top of an unmeasured inference layer, and the first person to discover the error rate is whoever the error happens to.

That is the whole method, and it reduces to two moves. Shrink the nondeterministic surface until it is one function with a validator on its output, and then refuse to build on that function until a held-out number says what it is worth. Everything else here is just the scaffolding that makes those two moves possible.

Further reading

Two pieces argue the adjacent case for coding agents, where the model builds the software rather than running inside it. Dex Horthy's Advanced Context Engineering for Coding Agents is the source for the stateless-function framing, the error-multiplication argument and the case for review as mental alignment. Addy Osmani's Agentic Engineering (O'Reilly, early release), chapter 5, “Specs as Leverage,” covers what a spec for an agent should contain and the spec-like objects that fail on contact with a reader that won't raise its hand. Both are about the spec the model reads before it writes code; this post is about the spec for the code that surrounds a model at runtime.
